# 3. DB 덤프 최신본

2026-09-28 00:30 UTC(09:30 KST)에 운영 PostgreSQL의 `app_db`를 `pg_dump -Fc`(PostgreSQL 사용자 지정 백업 형식)로 새로 추출했다. 실행 중인 백엔드의 DB URL이 `app_db`를 가리키는 것을 **DB명만** 확인했으며 접속 주소·비밀번호는 기록하지 않았다. `pg_dump`는 일관된 시점의 스냅샷을 읽으며 운영 테이블을 수정하지 않는다.

| 항목 | 검증 결과 |
|---|---|
| 로컬 원본 파일 | `exec/app_db_exec_20260928T003005Z.dump` (Git 제외) |
| 서버 원본 파일 | 운영 서버의 사용자 전용 파일로 보관, 권한 `umask 077`로 생성 |
| 덤프 생성 완료 | 2026-09-28 00:30:47 UTC |
| 크기 | 54,406,023바이트 |
| SHA-256 | `aa53c0a8c95ce349c51c9f5a550deaf6dd780f2ea43db4d0cfb1914198679032` |
| 형식 목록 | 운영 PostgreSQL 16.4의 `pg_restore -l` 성공 |
| 전송 무결성 | 로컬 파일 SHA-256이 서버 원본과 일치 |
| 격리 DB 전체 복원 | **미실행**. 복원 성공까지 검증한 것으로 표현하지 않는다. |

이 덤프는 운영 사용자·인증·위치 등 민감한 데이터를 포함할 수 있다. `exec/.gitignore`가 원본 `.dump` 파일을 Git에서 제외하며, 메인 브랜치에는 이 설명과 파일의 해시만 올린다. 제출처가 원본을 요구하면 권한자가 별도 보호된 전달 경로를 정해 전송한다. 무단으로 공개 저장소나 메신저에 첨부하지 않는다.

## 복원 담당자 확인 사항

1. 수신 파일 SHA-256이 위 값과 같은지 비교한다.
2. PostgreSQL 16 환경에서 `pg_restore -l <덤프파일>`로 항목 목록을 읽는다.
3. 격리된 새 DB에 복원해 테이블과 필요한 데이터가 열리는지 확인한다. 운영 DB에 바로 덮어쓰지 않는다.
4. 사용이 끝난 사본의 보관 기간과 삭제 책임자를 정한다.

기존 `infra/personalization/scripts/backup-postgres.sh`는 `app_db`, `airflow_db`, `mlflow_db`와 별도 설문 DB를 주기적으로 백업한다. 이번 파일은 이 요청을 위해 별도로 만든 최신 스냅샷이다. `backend/src/main/resources/db/migration/`의 Flyway SQL은 스키마 변경 이력이며 현재 데이터 덤프를 대체하지 않는다.
