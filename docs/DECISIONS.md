> v0 선점 프로토콜 자체의 결정(두 관문, fail-closed, 불변식)은 여기가 아니라

## 이 문서가 바꾼 것 — 한 줄

> **"AI 여럿이 서로 안 부딪히게 하는 도구"에서 "사람이 AI를 이해하고 통제하는 도구"로.**

주인공이 AI에서 사람으로 옮겨갔다. v0 의 락은 버려지지 않지만 **주연이 아니라 조연**이 된다.

## D1 · 주 사용자와 두 개의 공포

**결정.** 두 부류를 노린다.

1. AI 시대에 **코드의 변화를 제어하지 못해 두려운 사람**
2. **좋은 AI를 쓸 수 없는 환경**의 사람 (은행 등 폐쇄망)

그리고 공포는 정확히 두 가지다.

- **F1** — 내가 이해 못하는 코드가 계속 쌓인다
- **F2** — AI가 뭘 망가뜨렸는지 모른다

**왜.** 이 둘이 모든 후속 결정의 판정 기준이 된다.
어떤 기능을 넣을지 말지는 "F1 이나 F2 를 줄이는가"로 판단한다.

**버린 대안.** "AI 에이전트 6명의 병렬 작업 조율"을 1순위로 두는 것.
그것은 여전히 유효한 사용처지만 **파생 사례**다. 두 공포를 가진 사람은 AI가 한 명이어도 똑같이 두렵다.

---

## D2 · 개입 시점은 두 곳이고, 둘 다 필요하다

**결정.** 사전 신고와 사후 분석을 **둘 다** 만든다.

| 화면 | 시점 | 답하는 공포 | 질문 |
|---|---|---|---|
| **작업 계획 화면** | AI 시키기 전 | F1 | "이 문제를 이해하려면 어디를 읽어야 하나" |
| **PR 화면** | 올리기 전 | F2 | "이 작업이 뭘 바꿨고 어디까지 영향 갔나" |

**왜.** 둘은 같은 일을 하는 두 방법이 아니라 **서로 다른 두 문제**를 푼다.
사전은 *이해*를, 사후는 *검증*을 위한 것이다.

**버린 대안.** "AI 협조가 필요 없으니 사후 분석만 하자."
사후 분석은 F2 만 해결한다. F1 은 작업을 시작하기 전에 지도를 봐야 풀린다.

---

## D3 · 선언과 실제의 차이가 리뷰 우선순위 지표다

**결정.** 사전 신고(선언)와 사후 관측(실제)을 **비교해서 기록**한다.

| 관계 | 뜻 | 리뷰 우선순위 |
|---|---|---|
| 선언 ⊃ 실제 | 넓게 잡고 좁게 썼다 | 낮음 |
| **선언 ⊂ 실제** | **예상 못 한 곳을 건드렸다** | **높음** |
| 선언 ∩ 실제 = ∅ | 완전히 딴짓을 했다 | 최고 |

**왜.** 이 차이는 곧 **"이 AI가 자기 작업을 얼마나 이해하고 있었나"의 측정값**이다.
F2("뭘 망가뜨렸는지 모른다")의 실체가 바로 두 번째 줄이다.
PR 이 20개 쌓였을 때 "이 3개부터 보세요"라고 말할 수 있게 된다.

**이미 절반 구현되어 있다.** `axmap verify`(pre-commit)가 정확히 이 비교를 한다.
지금은 결과를 **막을지 말지 yes/no 로만 쓰고 버린다.** 기록만 하면 그대로 지표가 된다.

## D4 · LLM 은 게이트 안이 아니라 상류에 둔다

**결정.** LLM 은 판정하지 않는다. 게이트를 통과할 수 있는 **형태를 만드는 일**만 한다.

```
① 트리거 (결정론)   겹침 감지
        ↓
② LLM (유한, 상류)  의도 해석 · 그래프 구성 · 요약 · 제안
        ↓
③ 산출물 (결정론)   파일로 남는 검토 가능한 artifact
        ↓
④ 강제 (결정론)     기존 게이트가 집행
```

**왜.** LLM 을 게이트에 넣으면 잃는 것이 크다.

| | 파서 게이트 | LLM 게이트 |
|---|---|---|
| 같은 입력 → 같은 답 | ✅ | ❌ |
| `axmap audit` 사후 증명 | ✅ | ❌ 재생 불가 |
| 애매하면 거부 | ✅ | ❌ "아마 괜찮을 듯" |

**버린 대안.** "파서 대신 LLM 이 겹침을 판정한다."
I1(상호배제)을 증명할 수 없게 된다. 락 시스템인데 락이 지켜졌는지 확신할 수 없는 상태가 된다.

**단, D5 에서 이 결정의 범위를 좁혔다.** 그래프를 *짓는* 일은 LLM 이 더 잘한다.

## D5 · 그래프 엣지는 정적 파싱 + LLM 독해로 얻고, 엣지마다 출처를 붙인다

**결정.** 두 출처를 함께 쓰고, **각 엣지에 어디서 나왔는지와 신뢰도를 표시**한다.

| 출처 | 채택 | 성격 |
|---|---|---|
| **정적 파싱** | ✅ | 확실하지만 좁다. 기반으로 깔기 좋다 |
| **LLM 독해** | ✅ | 넓지만 검증이 필요하다 |
| 런타임 관측 | ⬜ 보류 | 가장 정확하지만 실행 환경이 있어야 한다 |

**왜 LLM 이 필요한가 — 실측으로 확인했다.**
e101 ROS2 워크스페이스에서 정적 grep 만으로 토픽 그래프를 만들었더니
`/cmd_vel/autonomy`, `/cmd_vel/escape`, `/bbiyong/control_mode` 세 개가
**"아무도 발행하지 않는다"는 틀린 답**이 나왔다. 실제로는 파라미터를 통해 발행하고 있었다.

```python
self.declare_parameter("output_topic", "/cmd_vel/autonomy")     # command_snap_node
self.declare_parameter("cmd_vel_out_topic", "/cmd_vel/escape")  # escape_recovery
```

반면 `command_snap_node.py` 는 docstring 에 데이터 흐름도를 직접 그려두었고,
LLM 은 그것을 즉시 읽는다. **동적으로 배선되는 시스템에서는 그래프 구성 자체가 LLM 의 일이다.**

**왜 출처를 표시하는가.** F1 을 가진 사람에게 **확신 있게 틀린 답이 가장 해롭다.**
위의 grep 결과가 정확히 그런 답이었다. 도구는 자기 확신 수준을 절대 속이지 않아야 한다.
화면에서 "정적으로 확인됨"과 "AI 추론 — 확인 필요"를 구분해 보여준다.

**런타임 관측을 보류한 이유.** 실행 환경이 필요하고, 그때 실행되지 않은 경로는 잡히지 않는다.
나중에 **검증 소스**로 추가할 여지는 남긴다 — 이미 그린 엣지가 실제로 관측되는지 확인하는 용도.

## D6 · 노드 단위는 적응형 — 기본은 파일, 큰 파일만 함수로 펼친다

**결정.** 임계값(초기 300줄)을 넘는 파일만 함수 단위 노드로 분해한다.

**왜.** 같은 e101 워크스페이스 안에서 두 파일의 성격이 전혀 다르다.

| 파일 | 줄 수 | 파일=노드로 충분한가 |
|---|---|---|
| `cmd_mux_node.py` | 129 | ✅ 파일 하나가 곧 책임 하나 |
| `escape_recovery.py` | 800 | ❌ "이 파일이 관련있다"는 도움이 안 된다 |

둘은 **깊이 1의 이웃**이다. 같은 조사에서 둘 다 나온다.

**함의 — 우선순위가 뒤집혔다.**
심볼 단위 선점을 "Phase 3, 나중에"로 미뤄뒀었다. 그런데
**가장 도움이 필요한 코드가 정확히 파일 단위 노드가 무력한 코드다.**
깔끔한 코드는 도구 없이도 읽히고, 800줄짜리는 도구 없이 못 읽는데
도구가 파일 단위면 못 돕는다. 심볼 단위는 선택이 아니라 전제조건이다.

**버린 대안 두 개.**
- *처음부터 전부 심볼 단위* — 129줄 파일도 노드 8개로 쪼개져 잘 쪼개진 코드가 오히려 읽기 어려워진다. 76파일 → 400+ 노드.
- *파일 단위 고정* — 구현은 가장 단순하지만 800줄 파일 앞에서 아무 말도 못 한다.

## D7 · 색상은 끝까지, LLM 요약은 3단계까지, 그 이상은 클릭할 때

**결정.**

| | 비용 | 범위 |
|---|---|---|
| **색상** (영향 표시) | 밀리초 — 그래프 순회 | **끝까지, 제한 없음** |
| **요약** (LLM 설명) | 초 × N개 | 3단계까지 |
| **상세** (클릭) | 초 × 1개 | 요청한 것만 |

거기에 **prefetch** 를 더한다. 사용자가 깊이 1을 읽는 동안 깊이 2~3을 미리 만든다.

**왜 색상은 자르지 않는가.** 요약과 함께 색상도 3단계에서 잘랐다면
**"내가 모르는 영향이 어딘가 남아 있다"는 불안이 그대로 남는다.** 그건 F1 을 못 없앤다.
색상을 끝까지 칠하면 **"영향 범위는 전부 보여줬고 설명만 아꼈다"**가 된다.
싼 것은 전부, 비싼 것은 필요한 만큼.

**왜 3인가.** 종이에 적지 않고 모니터만 보며 따라갈 수 있는 깊이의 한계.
그리고 인지부하 한계와 LLM 비용 한계가 같은 지점에서 만나는 것은 우연이 아닐 수 있다 —
깊이가 늘면 노드 수가 지수적으로 늘어나므로,
**사람이 못 따라가는 양은 기계도 비싸게 만들어야 하는 양이다.**

## D8 · 거리에 따라 명암, 허브 경유는 따로 표시

**결정.** 깊이 1은 진하게, 멀수록 옅게. 허브 토픽을 경유한 연결은 점선 또는 회색.

**왜 허브를 따로 표시하나.** 거리 기반 명암만으로는 **허브 경유를 구분하지 못한다.**
`/bbiyong/estop` 을 구독한다는 이유로 이어진 노드는 거리가 1이지만 의미는 멀다.

**버린 대안.** 폴더로 접어서 칠하기.
큰 레포에서는 여전히 필요할 수 있다 — [열린 질문](#열린-질문) 참조.

---

## D9 · 허브 토픽은 엣지에서 빼고 배지로 표시한다

**결정.** N개 이상이 공유하는 토픽은 개별 연결이 아니라 **방송**으로 보고 엣지에서 제외한다.
대신 노드에 `estop 구독자` 같은 배지를 붙인다.

**왜 — 실측이 명확했다.** e101 에서 cmd_mux 로부터의 깊이별 파일 수:

| 깊이 | 그대로 | 허브 제외 |
|---|---|---|
| 1 | **+18** (누적 19) | +6 (누적 7) |
| 2 | +8 (27) | +5 (12) |
| 3 | +2 (**29**) | +6 (**18**) |
| 4~6 | — 끝 | +5 (23) |

전체가 32개인데 **깊이 1에서 이미 18개**가 걸린다. 깊이 제한이 아무것도 걸러내지 못한다.
허브를 빼야 거리가 진짜 거리를 뜻하게 된다.

**그리고 이것이 "구독자는 참고만 하는 코드"와 같은 문제다.**
`/bbiyong/estop` 을 구독하는 11개 노드는 대부분 "비상정지면 멈춰라"를 듣기만 한다.
권한 체인에 있는 것이 아니라 전역 신호를 참고할 뿐이다.
사람이 휴리스틱으로 판단하던 것이 그래프에서는 통계로 잡힌다.

**주의 — 허브가 있다는 것 자체는 나쁜 설계가 아니다.**
로봇에서 비상정지가 모든 노드에 닿는 것은 올바른 설계다.
일부 노드에만 전달되면 그것이 버그다.

## D10 · 결합도를 계측하고 추세를 경고한다

**결정.** 평균 영향 범위와 파일 크기 꼬리를 재고, 나빠지면 PR 에서 경고한다.

```
평균 영향 범위   40 → 65  ⚠
  이번 변경이 올린 이유: exploration_node.py 가 4개 모듈에 새로 연결됨
파일 크기 꼬리   600줄 이상  4개 → 5개
```

**왜.** 이것이 **F1 의 직접적인 계측**이다.
"내가 이해 못하는 코드가 쌓인다"는 느낌을 추세선으로 바꾼다.
공포는 측정되면 관리 가능해진다.

**왜 AI 시대에 더 중요한가.** **AI 는 긴 파일의 고통을 느끼지 않는다.**
사람은 800줄 파일에 함수를 하나 더 넣을 때 "쪼개야 하는데" 하는 압박을 느끼지만
AI 는 그냥 넣는다. 아무도 재지 않으면 응집도는 한 방향으로만 나빠진다.

**그리고 두 목표가 같은 방향이다.** 읽기 어려운 코드는 AI 도 잘 고치지 못한다.
컨텍스트에 다 들어가지 않고, 관련 없는 부분까지 읽느라 헤맨다.
**"사람이 읽기 좋게"가 곧 "AI 가 잘 고치게"이므로 트레이드오프가 아니다.**

**실측 근거.** e101 ros2_ws/src 76개 `.py`, 총 12,609줄:

```
<100줄    41개      68개(89%)는 300줄 미만 — 대체로 건강하다
100-300   27개
300-600    3개
600-1000   4개      그런데 파일 5개(6.6%)가
1000+      1개      전체 코드의 37%를 차지한다 (4,702줄)
```

**버린 대안.** 지표만 보여주고 경고하지 않기.
임계값을 잘못 잡으면 잔소리가 된다는 위험은 인정한다 —
그래서 임계값은 조절 가능해야 하고, 절대값이 아니라 **추세**를 경고한다.

## D11 · 규약(contract)은 전제가 아니라 협상의 산출물이다

**결정.** 작업 시작 전에 규약을 작성하도록 강제하지 않는다.
겹침이 감지되어 협상이 일어났을 때, **그 결과로** 규약이 생긴다.

**왜.** 규약을 전제로 깔면 충돌이 없는 작업에도 매번 규약 작성 의식이 붙고,
형식적 접점이 있는 일에만 쓸 수 있다.

**버린 대안 (초기 제안).** `contracts/auth-login/{contract.yaml, server.md, client.md}` 를
먼저 만들고 거기 맞춰 일하기.

**다만 잠금 메커니즘 자체는 이미 검증했다.** 규약을 경로 네임스페이스로 표현하면
**프로토콜을 한 줄도 고치지 않고** 작동한다.

- A가 `server.md`, B가 `client.md` → 형제 파일이라 안 겹침 → 병렬 진행
- 누군가 규약을 바꾸려면 `contracts/auth-login` 디렉터리를 claim → **둘 다와 충돌** → 거부

거부 메시지에 **이해관계자 전원이 이름·작업·의도와 함께 호명**되므로
그대로 중재 테이블의 재료가 된다.

## D12 · 엣지의 출처를 사분면으로 나눠 보여준다

**결정.** 정적 파싱 그래프와 git 공변경 그래프를 겹쳐, 각 엣지를 네 갈래로 나눈다.

|  | import 있음 | import 없음 |
|---|---|---|
| **함께 바뀜** | `both` — 예상대로다 | 🔴 `cochange` — **숨은 결합** |
| **따로 바뀜** | `static-stable` — 안정된 경계 | (관계 없음) |

히스토리가 부족해 판정할 수 없는 정적 엣지는 `static` 으로 따로 둔다.
**모른다를 아니다로 바꾸지 않는다.**

**왜.** D5 는 엣지 출처로 정적 파싱과 LLM 독해 둘을 채택했다. 세 번째가 있다 —
**git 히스토리**다. 결정론적이고, 값싸고, 실패하는 방식이 앞의 둘과 다르다.

| 출처 | 실패하는 곳 |
|---|---|
| 정적 파싱 | 동적 배선 — 파라미터, 문자열 키, 리플렉션 |
| LLM 독해 | 안 적혀 있는 것 · 그럴듯한 환각 |
| **히스토리** | 새 코드 · 덤프 커밋 · rename 이후 단절 |

셋의 실패 방식이 직교하므로 **둘이 합의한 엣지는 훨씬 믿을 만하다.**

**실측 — immich (커밋 10,746, server/src 520파일).**
`asset.service.ts` 는 `stack` · `trash` · `duplicate` · `timeline` 서비스를
**하나도 import 하지 않는데** 반복해서 함께 바뀐다. 실제 통로는
`eventRepository.emit('AssetRestoreAll')` 과 `JobName.AssetDelete` 라는 문자열 키다.
그리고 커밋 `a0c7b8114` 가 정확히 그 자리에서 난 버그다 —
*"자산을 지웠는데 스택이 안 풀린다"*, 고친 파일은 `asset.service.ts` 하나뿐이었다.

**좌하단도 정보다.** "import 하지만 한 번도 같이 안 바뀐" 엣지는
인터페이스가 안정적이라는 뜻이고, **영향 범위에서 가중치를 낮춰야 할 엣지**다.
이것이 [열린 질문](#열린-질문) Q1(색상 확장성)의 실마리다 — 폴더 접기 대신
역사적 가중치로 자를 수 있다.

**버린 대안.** *히스토리로 정적 파싱을 대체한다.*
히스토리는 새 코드에 침묵하고 방향도 종류도 모른다. 대체가 아니라 **세 번째 층**이다.

## D13 · `kind` 와 `origin` 은 다른 축이다

**결정.** 엣지는 두 개의 독립된 축을 갖는다. 이름이 비슷해서 계속 헷갈리므로 여기 못박는다.

| 축 | 값 | 뜻 | 정하는 곳 | 화면이 쓰나 |
|---|---|---|---|---|
| `kind` | `import` · `channel` · `reference` | **무엇으로 이어졌나** (연결의 종류) | `app/lib/analyze.mjs` | 거의 안 쓴다 |
| `origin` | `static` · `static-stable` · `both` · `cochange` | **어떻게 알아냈나** (주장의 출처) | `app/lib/cochange.mjs` | **이것으로 칠하고 거른다** |

**왜 둘 다 필요한가.** `kind` 는 "이 두 파일이 왜 이어져 있나"에 답하고,
`origin` 은 "그 주장을 얼마나 믿을 수 있나"에 답한다. 전자는 설명이고 후자는 신뢰도다.
D5 가 "엣지마다 출처를 붙인다"고 한 그 출처가 `origin` 이다.

**새 `origin` 을 추가할 때 고쳐야 하는 곳 — 이것을 안 적어두면 매번 다시 찾는다.**

| 파일 | 무엇 |
|---|---|
| `app/lib/cochange.mjs` | `overlayEdges()` 의 판정과 `quadrant` 카운트 |
| `app/web/graph.js` | `ORIGIN` 색 지도 — **빠뜨리면 조용히 회색으로 떨어진다** |
| `app/web/overlay.js` | 기본 켜짐 집합 · 좌측 목록 블록 · 상단 뱃지 |
| `app/web/index.html` | 사분면 버튼 (`data-o`, `id`, 초기 `class="on"`) |
| `app/web/overlay.css` | `--o-*` 변수와 `.row.<클래스>` |
| `test/cochange.test.mjs` | 사분면 분류 테스트 |

**남은 문제 (해결 안 됨).** 한 개념에 이름이 네 개다 —
origin `static-stable` → quadrant 키 `stable` → 버튼 id `q-stable` → CSS 클래스 `stable`.
매핑이 `overlay.js` 에 손으로 적혀 있고 단일 출처가 없다. 하나 어긋나면 **조용히 0으로 표시된다.**
지금은 표로 막아두지만, 이름을 하나로 합치는 것이 옳다.

## D14 · 제품 서사 — 네 단계, 그리고 주인공은 흐름이다

**결정.** 사용자가 겪는 순서를 이렇게 못박는다.

| | 사용자가 하는 것 | 도구가 하는 것 |
|---|---|---|
| **1. 들어온다** | 이해하고 싶은 git 주소를 넣는다 | 클론해서 로컬로 가져온다 |
| **2. 이해한다** | **도구가 주는 기본 흐름을 따라간다** | 그 흐름을 만든다 |
| **3. 함께 짠다** | 바이브 코딩을 한다 | 팀원과 AI 가 각각 어디를 잡았는지 보여 중복을 막는다 |
| **4. 확신한다** | 아키텍처에만 집중한다 | 수많은 저장소를 기준으로 "잘 하고 있는지" 판정한다 |

**🔴 이 서사가 바꾼 것 — 지표는 주인공이 아니다.**

응집도·결합도·파일 길이·아키텍처는 **부가적 요소**다. 핵심은 2단계의
**"기본 흐름을 따라가다 보면 어느샌가 이해하게 된다"** 이다.

그동안 지표를 제품으로 다뤄왔다. lift·재현율·정밀도·영향 범위를 정교하게 만들고
관찰자들에게 "이 숫자가 뭐냐"는 말을 세 번 들었다. 숫자가 정교해질수록
**무엇을 먼저 보라는 말은 여전히 없었다.**

> 지표는 흐름을 만드는 재료이지 흐름이 아니다.

**왜 이 순서인가.**

1단계가 없으면 나머지가 시작되지 않는다. 지금 뷰어는 **로컬 경로**를 인자로 받는다.
"이해하고 싶은 저장소 주소를 넣는다"는 첫 동작이 아예 없다.

3단계는 2단계 다음이다. **이해하지 못한 코드베이스에서는 중복을 막아도 의미가 없다.**
그래서 락은 여전히 조연이다 (D1 과 같은 결론이지만 이유가 다르다 — 그때는
"공포가 둘이라서", 지금은 "순서가 뒤라서").

4단계는 **새로운 것**이다. D1 은 공포를 둘로 봤다 —
F1(이해 못 하는 코드가 쌓인다) · F2(AI 가 뭘 망가뜨렸는지 모른다).
4단계는 셋째다: **F3 — 내가 잘 하고 있는지 모른다.**

F1·F2 는 "지금 무슨 일이 일어났나"를 묻고, F3 는 **"이게 정상인가"**를 묻는다.
그 답은 한 저장소 안에 없다. 코퍼스가 있어야 나온다 —
이것이 분산 파이프라인에 제품상의 이유를 준다. 그전까지 그것은 연구 장비였다.

**버린 대안 — "지표를 다 보여주고 사용자가 고르게 한다."**
지금까지 해오던 것이고, 실패했다. 관찰자 넷 중 넷이 첫 화면에서 방향을 못 잡았다.
고를 수 있는 것이 많다는 것은 어디서 시작할지 모른다는 것과 같은 말이다.

## D15 · "기본 흐름" 이 무엇인지 — 아직 정하지 못했다

D14 가 핵심이라고 정한 것을 **우리는 아직 안 만들었다.** 여기 그 사실을 적어둔다.

지금 있는 것은 [진입점 목록](#d12--엣지의-출처를-사분면으로-나눠-보여준다) 넷이다 —
자주 바뀌는 곳 · 많이 연결된 곳 · 숨은 결합이 많은 곳 · 안 이어진 곳.
**넷은 병렬이지 순서가 아니다.** "여기서부터 읽으세요" 라고 적어뒀지만
정작 *다음에 무엇을* 은 말하지 않는다.

흐름이 되려면 최소한 이런 모양이어야 한다.

```
① 이 저장소는 무엇을 하는 물건인가        ← 관찰자 4/4 가 도구로 못 얻었다
② 실행은 어디서 시작하나                  ← 진입점(main·cmd·index)
③ 그 다음에 무엇이 불리나                 ← 계층. 공변경에는 안 찍힌다
④ 어디가 활발하고 어디가 위험한가          ← 지금 있는 것
⑤ 이제 당신 차례 — 무엇을 고칠 것인가      ← 3단계로 넘어가는 다리
```

①·②·③ 이 전부 비어 있다. 그리고 ③은 정적 파싱이 살아 있어야 가능하다 —
Go·Java import 를 읽게 만든 것이 그래서 먼저였다.

**아직 정하지 못한 것.**

| | 질문 |
|---|---|
| Q7 | 흐름은 **고정된 순서**인가, 저장소마다 다르게 짜는가 |
| Q8 | 흐름의 한 걸음이 끝났다는 것을 무엇으로 판정하나 (읽었다고 체크? 시간? 안 함?) |
| Q9 | 흐름을 벗어나 자유롭게 보고 싶을 때 어떻게 돌아오나 |
| Q10 | ③(계층·호출 방향)을 정적 파싱만으로 어디까지 얻을 수 있나 |

## D16 · 데스크톱 셸은 Electron. 폐쇄망 대응은 MVP 이후로 보류한다

**결정.** 윈도우 앱은 Electron 으로 감싼다. 새 코드는 `desktop/` 에만 들어가고
자기 `package.json` 을 가진다. **루트(코어 · CLI · MCP)의 의존성은 계속 0 이다.**

경계는 규칙 한 줄로 지킨다.

> `desktop/` → 코어 단방향. `src/*` 와 `app/lib/*` 는 Electron 을 import 하지 않는다.

역방향이 한 번이라도 생기면 나중에 떼어내는 것이 진짜 작업이 된다. 이 방향만 지키면
나머지(번들링·미러·서명·오프라인 빌드)는 전부 나중에 **설정으로** 풀린다.

**왜 Electron 인가.**

- **언어는 렌더링 성능을 결정하지 않는다.** 지금 GPU 를 먹는 원인은 `app/web/graph.js:1017`
  이다 — 물리는 `frozen` 에서 멈추는데 `_draw()` 와 rAF 는 안 멈춰서 정지한 화면을 초당
  60번 다시 그린다. C++ 로 다시 써도 초당 60번 다시 그린다. 고칠 것은 언어가 아니라 루프다.
- **코어 전체가 Node 다.** `src/protocol.mjs`(판정), `bin/axmap.mjs`(git 플러밍·장부·훅),
  `src/invariants.mjs`(공유 검사기), `app/lib/*` 14개 모듈, 테스트 273개. 네이티브로 가면
  이것을 전부 다시 쓰고 fail-closed 를 처음부터 다시 증명해야 한다. 그 비용이 6주 예산 전체다.
- **Electron 메인 프로세스가 곧 Node 다.** 포팅이 없다. `app/server.mjs` 를 그대로 띄우고
  `app/web/` 을 그대로 싣는다. 사용자 PC 에 Node 가 없어도 된다 — Electron 이 들고 온다.
- **팀에 비전공자와 React 사용자가 있다.** 렌더러가 크롬 탭이라 디버깅 도구가 이미 아는
  DevTools 다. 네이티브로 가면 디버거·빌드시스템·UI 프레임워크를 동시에 배워야 하고,
  6주에 그럴 여유가 없다. 여기서 결정되는 것은 성능이 아니라 **피드백 루프의 속도**다.
- **선례.** VS Code · Slack · Discord · Notion · Obsidian · Figma 데스크톱이 Electron 이다.
  ChatGPT 윈도우 앱(약 260MB)도, Claude 윈도우 앱도 Electron 이다. macOS 판만 네이티브다.
  "잘 만들어졌다"는 느낌은 프레임워크에서 오지 않는다 (아래).

**버린 대안.**

| | 왜 버렸나 |
|---|---|
| C++ / Direct3D | 재사용 0. 실이득은 물리 연산과 상주 메모리 두 칸뿐이고, 둘 다 Web Worker·WASM 으로 대부분 회수된다 |
| C# / WinUI 3 | 재사용 0 · Windows 전용. 웹 뷰어와 화면을 두 벌 만들어야 한다 |
| Tauri | 셸은 작지만 백엔드가 Rust 다. Node 코어를 쓰려면 사이드카로 Node 런타임을 싣게 되고 최종 크기가 결국 비슷해진다. 줄어드는 것은 크기가 아니라 자랑거리다 |

**보류 · 폐쇄망 대응.**

지금 이 제약에는 **사용자가 0명**이고, 이해 경험 쪽에는 측정된 실패가 있다
(벤치 3회차 — 형식을 바꿔도 다섯 조건 전부에서 그림은 답을 못 만들었다).
증거가 있는 쪽에 시간을 쓴다.

- **재개 조건.** 실제 폐쇄망 사용자가 생길 때.
- **그때까지 유지할 것.** 위의 import 단방향 규칙 하나뿐. 이미 그런 상태라 비용이 0 이다.
- **오프라인 빌드는 지금 풀지 않는다.** `npm ci` 만 네트워크를 쓰는 것이 아니다 —
  electron-builder 는 Electron 바이너리를 GitHub Releases 에서 받아온다. 레지스트리 미러를
  갖춰도 이건 따로 막힌다. 인터넷 되는 PC 에서 exe 를 만들어 **exe 를 반입**하면 된다.
- **코드 서명은 보류 항목이 아니다.** 서명 없는 exe 는 SmartScreen 경고를 띄우고,
  그 경고는 발표 당일 남의 노트북에서 뜬다. 두 개를 같은 바구니에 넣지 않는다.

**"잘 만들어졌다"는 느낌은 어디서 오는가.** ChatGPT 윈도우 앱의 정체성은 렌더링 성능이
아니라 `Alt+Space` 로 뜨는 컴패니언 창이다 — 프로그램을 여는 느낌이 아니라 OS 의 일부처럼
느껴진다. 프레임 없는 최소 UI, 항상 위, 상주해 있어서 즉시 뜬다. 전부 **셸이 하는 일**이지
렌더러가 하는 일이 아니다. 우리가 베낄 것도 거기다.

그리고 2026-07-09 에 **맥 쪽도 Electron 이 됐다.** 네이티브 Swift 클라이언트는
Codex 앱에서 파생된 Electron 빌드로 교체되고 `ChatGPT Classic` 으로 밀려났다.
반발이 거셌지만 그 내용은 **사라진 대화와 헷갈리는 정보 구조**였지 프레임 레이트가 아니었다.
"윈도우만 Electron" 이 아니라 **네이티브였던 쪽이 예외였고 그 예외가 끝난 것**이다.

**따라온 조치 — 상주와 정지 (2026-08-21).**

| | |
|---|---|
| 닫기 → 숨기기 | Electron 이 네이티브에 지는 유일한 체감 지점이 콜드 스타트(1~3초)다. 프로세스를 살려두면 그 비용을 앱 수명에 **한 번만** 낸다. 서버가 읽어둔 저장소 상태도 함께 산다 |
| 트레이 + 전역 단축키 | 숨기기가 되려면 나가는 길과 부르는 길이 보여야 한다 |
| 요구 시 렌더링 | `app/web/graph.js` 가 정지한 화면을 다시 칠하지 않는다 |

요구 시 렌더링은 **재봤다.** 배치가 멈춘 뒤 초당 그리기 횟수:

| | 초당 그리기 |
|---|---|
| 이전 (무조건 매 프레임) | **120회** |
| 지금 (흐르는 점만 움직임) | **19회** |
| 지금 (아무것도 안 움직임) | **0회** — rAF 를 아예 안 건다 |

`desktop/main.mjs` 의 자체 점검이 이 값을 재고 25회를 넘으면 실패한다.

🔴 이 검사를 처음 넣었을 때는 **거짓으로 통과했다.** 자체 점검이 창을 안 띄웠고,
크로미움은 숨긴 창의 rAF 를 초당 1회로 줄인다. 정지 로직을 옛날 것으로 되돌려 놓고
돌려도 그대로 통과하길래 알았다. 지금은 `showInactive()` 로 창을 띄우고 잰다.
**한 번도 실패하지 않는 검사는 검사가 아니다** ([INVARIANTS.md](INVARIANTS.md) 와 같은 이유).

## D17 · 군집 알고리즘에서 spectral 은 쓰지 않는다

**결정.** 그룹(모듈·군집)을 찾는 데 **spectral clustering 을 쓰지 않는다.**
후보에서 아예 뺀다. 쓰는 것은 modularity 계열(Louvain · Leiden)이고,
싸구려 기준선이 필요하면 label propagation 을 쓴다.

**왜.** 네 가지이고, 뒤로 갈수록 이 제품에 고유한 이유다.

- **k 를 미리 알아야 한다.** spectral 은 군집 개수를 입력으로 받는다. 그런데
  우리 질문은 정확히 "이 저장소의 자연스러운 모듈이 **몇 개이고** 무엇인가" 다.
  답을 입력으로 요구하는 방법은 이 질문에 못 쓴다. modularity 는 데이터에서 k 가 나온다.
- **저장소 규모에서 안 버틴다.** 라플라시안 고유분해는 조밀 행렬에서 O(n³) 이다.
  희소 반복법으로 낮춰도 커밋마다 **처음부터 다시** 계산해야 한다. 증분 갱신이 없다.
- **작은 변화에 결과가 통째로 뒤집힌다.** 고유벡터는 부호와 순서가 불안정해서
  파일 하나가 늘어도 그룹 번호와 색이 전부 뒤바뀔 수 있다.
  이 화면은 **색(hue)으로 갈래를 인코딩하고**(`graph.js` 의 `hueOf`) 사람이 같은
  저장소를 매일 다시 연다. 어제 파랗던 덩어리가 오늘 빨개지면 그동안 쌓은
  머릿속 지도가 무효가 된다. 배치를 멈추는 데 그렇게 공을 들인 이유(D15 앞의
  온보딩 실험)와 같은 문제다 — **화면이 흔들리면 색인 노릇을 못 한다.**
- **설명할 수 없다.** 🔴 이것이 결정적이다.

  이 제품은 "왜 이 그룹인가" 에 답해야 한다. 그 답을 백엔드 한 사람만 알고 있으면
  프론트도 사용자도 심사도 설득하지 못한다. modularity 는 **엣지 하나 단위로 기여도**가
  나오므로 "이 둘이 같은 그룹인 이유는 이 import 와 이 동시수정" 이라고 짚어줄 수 있다.
  고유벡터의 좌표값은 사람에게 보여줄 수 있는 근거가 아니다.

  설명 못 하는 군집은 이 제품에서 **성능 문제가 아니라 결함**이다.

**버린 것과 남긴 것.**

| | |
|---|---|
| 버림 | spectral clustering (정규화 컷 · 고유분해 계열 전부) |
| 기본 | Louvain / Leiden — modularity 최대화. k 가 데이터에서 나오고 엣지별 기여도를 남긴다 |
| 후보 | **Infomap** — 흐름 기반. 우리 그래프는 방향 있는 호출·import 그래프이고 D14 가 "주인공은 흐름이다" 라고 정했다. 은유가 알고리즘과 맞는다 |
| 후보 | **SBM** — 비동류(non-assortative) 구조를 잡는다. modularity 는 허브를 못 본다 — D9 가 다루는 문제가 정확히 그것이다 |
| 기준선 | label propagation — 빠르고 단순해서 "휴리스틱이 실제로 이겼는가" 를 재는 대조군으로 쓴다 |

네 후보 전부 위의 네 가지 이유를 통과한다 — k 를 미리 안 받고, 증분 갱신이 가능하거나
싸고, 작은 변화에 비교적 안정적이고, **왜 이 군집인지 짚을 수 있다.**
어느 것을 고르는가는 벤치로 정한다. spectral 만이 처음부터 후보가 아니다.

**TF-IDF 의 자리 — 이름 붙이기, 그것뿐이다.**

군집이 정해진 **뒤에** 각 블록의 이름을 짓는 데만 쓴다. 군집을 *만드는* 신호에는
넣지 않는다. 이름으로 군집을 만들면 **디렉터리 구조를 다시 발견할 뿐이고**, 우리가
알고 싶은 것은 그 반대 — 폴더가 다른데 실제로 얽혀 있는 것(D12 의 `cochange`)이다.
이름을 섞으면 정확히 그 발견을 지운다.

두 실패의 무게도 다르다.

| | 신호 | 틀렸을 때 |
|---|---|---|
| 군집을 만드는 것 | import 엣지 + 공변경 (D5 · D12) | **지도가 틀린다.** 알아채기 어렵다 |
| 이름을 붙이는 것 | TF-IDF (`corpus/terms.mjs`) | 이름이 어색하다. 보면 바로 안다 |

구현은 `corpus/terms.mjs` 의 `labelBlocks()` 다. 입력이 "파일 → 블록 번호" 뿐이라
**군집을 무엇으로 만들었는지 몰라도 붙는다** — Louvain 이든 Infomap 이든 SBM 이든
그대로 쓴다. 경계를 나눠 둔 이득이 여기서 나온다.

불용어는 손으로 적지 않고 문서빈도에서 유도한다. `service` 가 잡음인지 신호인지는
저장소를 봐야 알기 때문이다. 언어 예약어만 씨앗으로 적고, 나머지는 저장소 → 언어 칸 →
전역 3단으로 유도하되 **표본이 모자란 단은 건너뛰고 그 사실을 함께 돌려준다**
(`ssot.mjs` 의 "표본이 적으면 답을 내지 않는다" 와 같은 규칙).

**이 결정이 닫는 문.** NP-hard 를 "제대로 푸는" 것처럼 보이는 완화(relaxation)를
쫓지 않는다는 뜻이기도 하다. 6주 안에 필요한 것은 최적해가 아니라 **재현 가능한
근사해와 그것이 충분하다는 증거**다. spectral 은 최적해처럼 보이지만 위의 네 가지를
그대로 안고 오고, 그중 마지막은 이 제품의 존재 이유(D1 의 F1·F2)와 정면으로 부딪친다.
