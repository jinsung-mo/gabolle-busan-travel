# 0. 이 초안을 어떻게 읽나

**Epic 을 요구사항 영역에서 그대로 뽑았다.** `GB-SRS-001` 1장이 이미 요구사항을 8개 영역(`ACC` `PLN` `REC` `ITN` `COM` `DAT` `ADM` `NFR`)으로 갈라 놓았고, 영역마다 **요구사항 ID · 담당 · 화면 매핑**이 붙어 있다. 그 경계를 새로 그리지 않고 그대로 쓴다 — **문서와 티켓이 같은 선으로 갈려 있어야 나중에 "이 기능이 어느 Epic 이었나"를 찾을 수 있다.**

거기에 **요구사항 영역에 안 들어가는데 반드시 해야 하는 것 넷**을 더했다.

| 층 | 무엇 | 개수 |
|---|---|---:|
| **0층 — 기반** | 이게 없으면 나머지가 시작조차 안 된다 | 3 |
| **1층 — 제품** | 요구사항 영역 그대로 | 7 |
| **2층 — 출시·모집** | 앱과 사용자 100명 | 2 |
| | **합계** | **12** |

> 🔴 **17 근무일에 Epic 12개는 빠듯하다.** 합치기 쉬운 자리를 3장에 적어 뒀다. 다만 **`E10 DAT` 과 `E12` 는 합치기 전에 4장(조건부)을 먼저 보셔야 한다** — 그 둘은 크기 문제가 아니라 **착수 조건** 문제다.

### 크기 표기

`요구사항`은 `GB-SRS-001` 의 `FR-`/`DR-` ID 개수이고, `화면`은 `GB-UX-001` 의 `S-` 번호다. **이 숫자는 Story 개수가 아니다** — 요구사항 하나가 Story 여러 개가 될 수 있다.

### 마일스톤 표기

`GB-PLAN-002` 2장의 네 마감을 그대로 쓴다.

| 표기 | 마감 |
|---|---|
| **M1** | 2026-09-04 (금) 웹 완성 |
| **M2** | 2026-09-09 (수) 앱 완성 |
| **M3** | 2026-09-18 (금) 사용자 100명 |
| **M4** | 2026-09-23 (수) 전 작업 완료 |

# 2. 순서 — 무엇이 무엇을 막나

```
E1 껍데기·배포 ──┐
E2 스키마·Outbox ┴─→ E4 ACC ─→ E5 PLN ─→ E6 REC ─→ E7 ITN
                                            ├─→ E11 ADM (Editor's Pick 발행)
                                            └─→ E8 COM ─→ E9 COL
E3 스토어 계정 ─────────────────────────────────→ E12 앱 ─→ E13 100명 모집
E10 DAT ──── M1: Outbox 테이블만 ──── M3: Kafka·Spark ──→ (E6·E13 의 완료 기준을 막는다)
```

**읽는 법 넷.**

1. **E1·E2 가 안 끝나면 나머지가 전부 대기다.** 9/1~9/2 에 사람을 몰아넣는다
2. **E3 의 계정 개설만 오늘 즉시 뗀다.** 나머지 인증서 작업은 E12 가 있어야 뜻이 있다
3. **E6 은 E5 없이 시작할 수 있다.** 추천 입력 DTO 만 고정되면 REC/AI 는 목 데이터로 착수한다 (계획서 3.3)
4. **E10 은 M1 에서 Outbox 테이블까지만 한다.** Kafka·Spark 를 M1 에 세우면 요청 경로가 그것들에 묶인다 (`GB-PLAN-001` 8장)

# 3. 합치고 싶다면 — 여기가 이음매다

| 합칠 것 | 합친 뒤 개수 | 잃는 것 |
|---|:-:|---|
| **E9 COL 을 E7 ITN 으로** | 11 | 그룹 기능이 일정 Epic 에 묻힌다. 다만 M3 항목이라 M1·M2 에는 영향 없다 |
| **E11 ADM 을 E6 REC 으로** | 11 | Editor's Pick 발행이 추천 Epic 안에 들어간다. 운영 화면과 추천 로직의 주인이 섞인다 |
| **E8 COM 을 E13 모집으로** | 11 | 후기가 모집 활동에 묻힌다. 후기는 제품이고 모집은 활동이다 |

🔴 **E2 와 E10 은 합치지 않는다.** 스키마는 **코드**이고 이벤트 파이프라인은 **운영 데이터**다. 한 Epic 에 넣으면 "스키마 끝났는데 왜 안 닫히나"가 반복된다.

🔴 **E1 과 E3 도 합치지 않는다.** 배포는 팀이 통제하고 스토어 승인은 통제하지 못한다. 통제 가능한 일과 대기해야 하는 일을 한 Epic 에 넣으면 진척이 안 보인다.

# 4. 🔴 조건부 Epic 셋 — 지금 끊으면 위험하다

## E10 DAT — 이벤트·파이프라인

**착수 조건이 스키마 고정이다.** `GB-SRS-001` 3.1절의 이벤트 사전(12종)이 확정되기 전에 FE·APP 이 계측을 넣으면 전부 다시 넣어야 한다. 계획서 3.3절이 이 고정 시각을 **9/3 12:00** 으로 잡았다.

그리고 **Kafka·Spark 는 M1·M2 에 세우지 않는다.** 세우는 순간 요청 경로가 그것들의 가용성에 묶이고, 17일짜리 일정에서 그 운영 비용을 감당할 사람이 없다. **첫 Story 를 "이벤트 스키마 확정과 Outbox 테이블"로 두고, Kafka Story 는 M3 에 배치한다.**

## E9 COL — 그룹 계획

**사용자가 있어야 뜻이 있다.** M3(9/18) 전까지 사용자는 팀 6명뿐이고, 그 상태에서 만든 공동 편집은 실제로 검증되지 않는다.

그리고 **`GB-SRS-001` 에서 우선순위가 Should** 다. 계획서 9장의 잘라내기 순서에서 **4번**에 있다. **일정이 밀리면 이 Epic 을 먼저 닫는다.**

## E12 앱 — 셸과 M2 화면

**E3(스토어 계정)이 착수 조건이다.** 계정·인증서 없이 만든 빌드는 올릴 데가 없다. 그리고 **iOS TestFlight 외부 테스터는 베타 앱 심사를 통과해야 한다**(계획서 7.1, 확인됨) — **심사 1~2일을 일정에 넣어야 한다.**

**첫 Story 를 "계정·인증서 확인"으로 두거나, iOS 를 후속으로 미루고 Android 만으로 M3 를 채운다.** 후자를 고르면 Play 내부 테스트 상한이 **정확히 100명**이라 여유가 0이라는 점을 감수해야 한다(계획서 7.2).

# 5. Story 쪼개기 기준

**Epic 하나에 Story 를 몇 개로 쪼갤지**는 팀이 정하되, 아래 셋은 지킨다.

| 기준 | 내용 |
|---|---|
| **하루 안에 끝나는 크기** | 17일짜리 일정에서 이틀 넘는 Story 는 진척이 안 보인다 |
| **화면–API–테이블을 세로로 관통** | "API 만" "화면만" Story 는 혼자 완료 판정이 안 된다 |
| **마일스톤을 넘지 않는다** | M1 Story 가 M2 로 걸치면 판정 회의에서 상태를 못 정한다 |

**Story 제목 형식**

```
[GB-nnn] <FR-ID> <한 문장으로 무엇이 되면 끝인가>

예) [GB-112] FR-REC-02 알레르기·식단 후보를 점수 계산 전에 제거한다
    [GB-118] FR-ITN-08 baseVersion 이 낡으면 409 와 latestVersion 을 반환한다
```
