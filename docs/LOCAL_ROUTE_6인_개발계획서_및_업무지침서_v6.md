## 1. 팀 협업 수칙

### 1.1 일일 스탠드업 (매일 10:00, 15분)

세 가지만 말한다.

1. 어제 완료한 것 — **PR 링크 기준**. "거의 다 됐다"는 완료가 아니다
2. 오늘 완료할 것 — 5장의 오늘 과업 기준
3. **막힌 것** — 이게 가장 중요하다

**규칙**

- 회의 중 문제 해결 토론은 하지 않는다. 블로커가 나오면 관련자끼리 회의 후 페어로 붙는다.
- **막힌 것을 말하지 않는 것이 6인 팀에서 가장 비싼 낭비다.** 혼자 반나절 붙잡고 있지 말고 30분 안에 말한다.
- 마감을 못 지킬 것 같으면 **마감 전날에** 알린다. 당일에 알리면 뒷사람의 하루가 사라진다.

### 1.2 데일리 데모 (매일 18:00, 5분)

**staging에서 실제로 동작시켜 보인다.** 말이 아니라 화면으로 진척을 확인한다. 코드가 있는 것과 동작하는 것은 다르다.

### 1.3 Git 브랜치와 PR

**브랜치 명명**

```
feature/ai-{기능}      예: feature/ai-ocr-pipeline
feature/db-{기능}      예: feature/db-postgres-migration
feature/infra-{기능}   예: feature/infra-eas-build
feature/be-{기능}      예: feature/be-account-delete
feature/fe-{기능}      예: feature/fe-responsive-tokens
feature/app-{기능}     예: feature/app-camera-ocr
fix/{범위}-{내용}      버그 수정
```

**PR 머지 조건**

이 저장소는 npm workspaces 모노레포다. 루트에 `tsconfig.json`이 없으므로 `npx tsc --noEmit`은 동작하지 않는다. 아래를 쓴다.

```bash
npx tsc -b web                    # 웹 타입 검사
npm run build --workspace server  # 서버 타입·빌드
npm run build --workspace web     # 웹 프로덕션 빌드
npm test --workspace server       # 테스트 12개 파일
npm audit --audit-level=high      # 취약점
```

추가 조건

1. CI 통과 (위 항목이 `.github/workflows/ci.yml`에 이미 있다)
2. 리뷰어 1인 이상 승인. **인터페이스를 바꾸면 해당 담당자 필수 승인**
3. 화면 변경 PR은 **스크린샷 첨부** (변경 전/후)
4. API 변경 PR은 **요청·응답 예시 첨부**
5. 타입을 바꾸면 **PR 제목에 `[TYPES]`** + 채널 공지

**머지 시각**: 매일 18:00 이전. 그 이후 머지는 다음 날 아침으로 미룬다. 밤중 배포 사고를 막는다.

**결측 채우기 방법 [설계 제안]**

| 필드 | 방법 |
| --- | --- |
| `nameEn` · `addressEn` | TourAPI 영문 서비스(`EngService2`)에서 `contentId`로 매칭해 1차 확보(84%가 `contentId` 보유) → 나머지는 번역 API 초벌 → **사람 검수** |

| `soloFriendly` | 1인석·바 좌석 여부. 초기값은 카테고리 휴리스틱 후 검수 |
| `breakTime` · `lastOrderTime` | 카카오 로컬 영업정보 + 수작업 |

## 6. 공유 인터페이스 계약

### 6.1 왜 `packages/shared`가 필요한가

지금 구조에 `mobile/`을 그냥 붙이면 **타입 정의가 3벌, API 클라이언트가 2벌**이 된다. 한 곳만 고치고 다른 곳을 잊으면 런타임에서 터진다.

```
현재                              v6 목표
app/                              app/
├── server/                       ├── packages/shared/     ← 신설
│   └── src/types.ts              │   └── src/
└── web/                          │       ├── types.ts     단일 진실 공급원
    ├── src/types.ts   ← 중복     │       ├── client.ts    API 클라이언트
    └── src/api/client.ts         │       ├── constants/   음식 8종·코스 10종
                                  │       ├── i18n/        한·영 딕셔너리
                                  │       └── design/      디자인 토큰
                                  ├── server/
                                  ├── web/                 shared 사용
                                  └── mobile/              shared 사용
```

### 6.2 공유하는 것과 하지 않는 것

| 공유한다 | 이유 |
| --- | --- |
| 타입 정의 | 서버 응답 모양은 플랫폼과 무관하다 |
| API 클라이언트 | `fetch`는 React Native에도 있다. 그대로 동작한다 |
| 다국어 문자열 | 같은 문장을 두 번 번역할 이유가 없다 |
| 디자인 토큰 | 색·간격 값은 숫자다. 적용 방법만 다르다 |
| 상수 (음식 8종·코스 10종) | 화면마다 다시 적으면 어긋난다 |
| 순수 계산 (거리·비용·날짜) | DOM이 필요 없다 |

| 공유하지 않는다 | 이유 |
| --- | --- |
| JSX 태그 | `<div>` ↔ `<View>` |
| 스타일 적용 | CSS ↔ StyleSheet |
| 라우터 API | react-router ↔ Expo Router |
| 브라우저 전용 API | Tesseract.js·Web Speech ↔ 네이티브 모듈 |

> **경험칙: 화면에 그리는 코드는 공유하지 않고, 화면에 그릴 내용을 만드는 코드는 전부 공유한다.**

### 6.3 도입 순서

| 순서 | 작업 | 담당 | 마감 |
| --- | --- | :-: | --- |
| 1 | 워크스페이스 추가 | BE | 8/27 |
| 2 | `web/src/types.ts` → `shared/src/types.ts`. 웹은 재수출로 호환 유지 | BE | 8/28 |
| 3 | `web/src/api/client.ts` → `shared/src/client.ts` | BE | 8/28 |
| 4 | 디자인 토큰 추가 | FE | 8/29 |
| 5 | `mobile/`에서 참조 확인 | APP | 8/28 |

**[위험] 2·3번이 늦어지면 APP이 대기한다. BE의 최우선 과제인 이유다.**

### 6.4 디자인 토큰

**현재 화면에서 실제로 쓰는 값을 추출한다.** 새 색을 도입하면 전면 리디자인이 되어 일정이 무너진다(3.5절 참조).

```typescript
// packages/shared/src/design/tokens.ts
export const tokens = {

    // 표면
    canvas:      '#f7f7f8',   // 페이지 배경
    surface:     '#ffffff',   // 카드
    surfaceAlt:  '#fafafb',   // 보조 표면

    line:        '#e8e8eb',
    lineStrong:  '#d9d9de',
    // 텍스트
    ink:         '#2c2d32',   // 본문
    inkMuted:    '#72737b',   // 보조
    inkFaint:    '#8e8f96',   // 흐림
    inverse:     '#ffffff',
    // 브랜드
    brand:       '#7265c6',
    brandStrong: '#6654c6',
    brandSoft:   '#f2f1f7',   // 활성 배경
    // 상태
    danger:      '#dc2626',
    dangerInk:   '#b42318',
    dangerSoft:  '#fef2f2',
    warning:     '#a95a19',
    warningSoft: '#fff3e5',
    // 카테고리 (장소 카드)
    catTourist:    '#b9d9f4',
    catRestaurant: '#d8cff4',
    catCafe:       '#cce9ee',
    catLodging:    '#ddd7ea',
  },
```

**[실측] 현재 `styles.css`에는 `:root` 블록이 두 개 있고 서로 다른 색 체계를 정의한다.**

```css
/* 첫 번째 :root — 초록 계열 */
--primary: #15803d;  --mint: #0d9488;  --bg: #f6f7f5;
/* 두 번째 :root — 틸 계열, 이름이 다름 */
--brand: #0f7a68;  --ink: #17251f;  --canvas: #f4f7f5;
```

그런데 화면에 보이는 색은 보라·중성 계열이다. `ux-overrides.css`(890줄)가 하드코딩으로 덮어쓰기 때문이다. **변수 두 세트는 사실상 죽어 있다.** FE의 8/27 작업은 이 세 겹을 한 겹으로 만드는 것이다.
