# 밤샘 점검 시나리오 — 2시간마다 한 바퀴

빌드 → 테스트 → 버그 발견 → 티켓 → 고침 → 머지를 **2시간 간격으로 반복**할 때 따라가는
문서다. 사람이 안 보고 있는 동안 도는 것을 전제로 쓴다.

**무인으로 돌 때 가장 큰 위험은 버그를 못 찾는 것이 아니라, 없는 버그를 찾았다고 믿고
고치는 것이다.** 그래서 이 문서의 절반은 「무엇을 눌러 보나」가 아니라 「무엇을 버그로
치나」에 쓴다.

---

## 0. 한 회차의 모양

| 단계 | 하는 일 | 끝났다고 보는 기준 |
|---|---|---|
| 0 | 전제 확인 (§1) | 기기·PC·서버가 살아 있고, 기기에 깔린 판 번호를 안다 |
| 1 | 빌드·설치 (§2) | 기기의 `versionCode` 가 직전 회차보다 크다 |
| 2 | 테스트 (§3) | 시나리오 A~L 을 한 번씩 돌고 캡처가 남았다 |
| 3 | 버그 판정 (§4) | **3관문**을 통과한 것만 버그로 센다 |
| 4 | 티켓 (§5) | `createJiraIssue` 가 돌려준 키만 쓴다 |
| 5 | 고침·머지 (§6) | CI 초록 → 머지 → 티켓에 기록 |
| 6 | 회차 기록 (§7) | 다음 회차가 읽을 한 덩어리를 남긴다 |

한 회차가 2시간을 넘길 것 같으면 **§3 을 줄이지 말고 §6 을 먼저 남긴다.** 기록이 없으면
다음 회차가 같은 것을 또 찾는다.

## 1. 전제 확인 — 매 회차 맨 앞에서 (건너뛰지 않는다)

```bash
ADB=/c/android-sdk/platform-tools/adb.exe
PEM=/c/Users/SSAFY/Downloads/J15E201T.pem

# 1) 기기가 붙어 있나
"$ADB" devices | sed -n '2p'                    # R39M202HCVV	device 여야 한다

# 2) 화면을 내가 켤 수 있나 (잠금 해제 상태 유지 확인)
"$ADB" shell input keyevent KEYCODE_WAKEUP
"$ADB" shell dumpsys window | grep -oE "mDreamingLockscreen=(true|false)"
#    → true 면 잠금이 다시 걸린 것이다. 뚫지 말고 §7 에 적고 기기 작업을 건너뛴다.

# 3) 기기에 깔린 판
"$ADB" shell dumpsys package com.gabolle.app | grep -E "versionCode|versionName"

# 4) 서버가 살아 있나 + 방금 배포 중은 아닌가
curl -s -o /dev/null -w 'anonymous %{http_code}\n' -X POST https://j15e201.p.ssafy.io/api/v1/auth/anonymous
ssh -i "$PEM" -o StrictHostKeyChecking=no ubuntu@j15e201.p.ssafy.io \
  'docker inspect backend --format "started={{.State.StartedAt}} running={{.State.Running}}"'
```

> 🔴 **배포 직후 5분 안에는 API 판정을 하지 않는다.** 백엔드가 다시 뜨는 동안 502·503 이
> 쏟아지고, 그걸 앱 버그로 적으면 다음 회차가 헛일을 한다. `StartedAt` 이 5분 이내면
> 5분 기다렸다 §3 으로 간다.


## 3. 테스트 시나리오

### 공통 규칙

- **한 번에 한 스크립트만 기기를 만진다.** 배경 작업이 살아 있는데 새로 띄우면 두 스크립트가
  같은 기기를 번갈아 조작해 결과가 섞인다(실제로 당했다 — §8).
- **캡처가 유일한 진실이다.** `uiautomator dump` 는 늦게 갱신되고 가끔 멈춘다.
  쓰더라도 `timeout 12` 를 건다.
- 화면 이동은 딥링크(`gabolle://<경로>`)로 한다. 탭 좌표는 기기 해상도(1080×2280) 기준이고
  화면이 바뀌면 깨지므로, **좌표를 쓰기 전에 캡처로 위치를 확인한다.**
- 각 시나리오는 **서버 로그를 함께 본다.** 화면이 멀쩡해 보여도 뒤에서 4xx·5xx 가 날 수 있다.

```bash
# 시나리오를 도는 동안 서버 응답을 같이 받는다
ssh -i "$PEM" ubuntu@j15e201.p.ssafy.io 'sudo timeout 180 tail -F -n0 /var/log/nginx/access.log' > /tmp/run.log &
# ... 조작 ...
grep -oE '"(GET|POST|PUT|DELETE) [^ ]+ HTTP[^"]*" [0-9]+' /tmp/run.log | sed 's/"//g' | sort | uniq -c
```

## 4. 버그 판정 — 3관문

**셋을 다 통과한 것만 버그로 센다.** 하나라도 막히면 §7 에 「버그 아님」으로 적고 넘어간다.

### 관문 1 — 지금 코드에 아직 있나

기기에 깔린 판이 낡았을 수 있다. 반드시 **`front/dev`·`back/dev` 의 현재 코드**에서 그
자리를 찾아 확인한다. 이미 고쳐져 있으면 버그가 아니라 **빌드가 낡은 것**이다.

### 관문 2 — 앱이 그린 것이 맞나

화면의 글자가 전부 앱 것은 아니다. **사용자가 올린 사진 속 글자**를 UI 로 오인한 적이
있다(피드 카드의 한국어). 의심되면 그 요소가 어느 컴포넌트에서 나오는지 코드로 확인한다.

### 관문 3 — 서버 탓인가 앱 탓인가

5xx 를 봤으면 **먼저 배포 창인지 본다.**

```bash
ssh -i "$PEM" ubuntu@j15e201.p.ssafy.io 'docker inspect backend --format "{{.State.StartedAt}}"'
```

방금 재배포였으면 앱 버그가 아니다. 재배포가 아닌데도 특정 경로만 5xx 면 **그건 진짜다**
(환율 1300 이 그렇게 나왔다).

## 5. 티켓

- **번호를 지어내지 않는다.** `createJiraIssue` 가 돌려준 키만 쓴다
- 제목은 **한 파트**로 (`[FE]`/`[BE]`). `[FE/BE]` 로 쓰면 `verify:jira-key` 가 파트를 못
  정해 노랗게 지나간다(머지는 안 막는다)
- 본문에 반드시 넣는 것
  - **실측** — 명령과 응답을 그대로. 「안 된다」가 아니라 「HTTP 502, 코드 X, 메시지 Y」
  - **왜 그런가** — 코드의 그 줄
  - **얼마나 자주** — 늘? 주말만? 특정 언어만?
  - **버그가 아닌 것** — 같이 봤지만 정상이던 것도 적는다. 다음 사람이 또 안 보게

## 6. 고침·머지

1. `ax_claim` 으로 파일을 잡는다. 거부되면 **재시도하지 말고** 다른 것으로 옮긴다
2. 고침은 **이미 팀이 쓰는 해법**을 따른다. 새 규칙을 만들지 않는다
3. **검사를 함께 넣는다.** 그리고 **옛 코드로 되돌려 빨개지는 것을 확인한다** — 이걸 안 하면
   아무것도 안 지키는 검사를 넣게 된다
4. `tsc --noEmit` · `jest` · `check:button-container` (백엔드는 `gradlew test`) 전부 0
5. MR → CI 초록 → 머지 → 티켓에 머지 커밋과 **아직 확인 못 한 것**을 적는다
6. 🔴 **「머지했으니 완료」로 닫지 않는다.** 실기기 확인이 남았으면 「진행 중」에 둔다

## 8. 오늘 실제로 당한 함정 (같은 데서 또 넘어지지 않게)

| 함정 | 무슨 일이 | 어떻게 막나 |
|---|---|---|
| **두 스크립트가 같은 기기를** | 멈춘 줄 안 배경 작업이 살아 있어 결과 파일에 모든 화면이 두 번씩 찍혔다. 「앱꺼짐 37개」라는 가짜 수치가 나왔다 | 새 기기 작업 전에 `pkill -f <스크립트>` 하고 **결과 줄 수 = 화면 수** 인지 확인 |
| **`uiautomator` 가 멈춤** | 애니메이션 중인 화면에서 영영 안 끝났다 | `timeout 12` 를 건다 |
| **`adb` 가 stdin 을 먹음** | `while read` 루프가 한 번만 돌았다 | `while read -r x <&3; do … done 3< 파일` |
| **heredoc 이 역슬래시를 먹음** | 시험 코드의 `\n` 이 진짜 줄바꿈이 돼 문법 오류 | 파일은 Write 도구로 쓴다. 꼭 heredoc 이면 `chr(92)` |
| **빌린 `node_modules`** | 다른 세션의 `npm ci` 가 꾸러미를 지워 `tsc` 가 빨개졌다 | 작업 폴더마다 junction 을 걸고, 없으면 그 꾸러미만 `npm i --no-save` |
| **가설을 코드로 바로 옮김** | `unstable_settings` 없음을 원인으로 의심했는데 기기에서 재 보니 아니었다 | **고치기 전에 기기에서 두 화면을 비교**한다(가드 있는 것 vs 없는 것) |
| **이 PC 에 `python3` 없음** | `RouteOptimizerAvailabilityCheckTest` 만 늘 빨갛다 | 그 하나는 환경 탓이다. CI 는 초록인 것을 확인하고 넘어간다 |
