### F-ACC-01 · 익명 세션 발급

| 항목 | 내용 |
| --- | --- |
| **사용자 스토리** | 처음 온 사람이 **회원가입 없이 바로** 여행 일정을 만들 수 있다 |
| **현재 상태** | **[구현됨]** |

**구현 방법**

1. 웹·앱이 최초 API 호출 전에 `POST /api/auth/anonymous`를 부른다
2. 서버가 난수 토큰을 만들고 **해시만** `AnonymousSession.tokenHash`에 저장한다. 원본은 저장하지 않는다
3. 클라이언트는 토큰을 로컬 저장소(웹 `localStorage`, 앱 `expo-secure-store`)에 보관한다
4. 이후 모든 요청에 `X-Session-Token` 헤더로 실어 보낸다
5. 서버는 헤더의 토큰을 해시해 세션을 찾는다

**필요 기술**

| 항목 | 사용 |
| --- | --- |
| 해시 | Node `crypto` (SHA-256) |
| 저장 | 웹 `localStorage` · 앱 `expo-secure-store` **[도입 필요]** |

**데이터**: `AnonymousSession(id, tokenHash, createdAt, lastSeenAt)`
**API**: `POST /api/auth/anonymous`
**화면**: 전 화면 (백그라운드)
**예외·폴백**: 발급 실패 시 재시도 1회 → 실패하면 오프라인 배너 표시. 익명 기능은 막고 열람은 허용
**수용 기준**: 브라우저 저장소를 지운 뒤 접속하면 새 세션이 발급되고 일정 생성이 가능하다
**담당·마감**: BE · 완료

### F-ACC-02 · 이메일 회원가입

| 항목 | 내용 |
| --- | --- |
| **사용자 스토리** | 여행자가 기기를 바꿔도 자기 여행 기록을 이어서 볼 수 있게 계정을 만든다 |
| **현재 상태** | **[구현됨]** — 다만 이메일 인증은 없다 |

**구현 방법**

1. 클라이언트가 이메일·비밀번호·이름·언어를 `POST /api/auth/register`로 보낸다
2. 서버가 비밀번호 규칙을 검사한다 — **8~64자, 영문·숫자·특수문자 포함**. 위반 시 `WEAK_PASSWORD`
3. `randomBytes(16)`로 계정별 salt를 만들고 `scrypt(password, salt, 64)`로 해시한다
4. 트랜잭션 안에서 `User`를 만들고, **현재 익명 세션이 만든 여행을 이 계정으로 승계**한다
5. `AccountSession` 토큰을 발급해 반환한다

**필요 기술**

| 항목 | 사용 |
| --- | --- |
| 비밀번호 해시 | Node `crypto.scrypt` (구현됨) |
| 비교 | `timingSafeEqual` — 타이밍 공격 방지 (구현됨) |
| 트랜잭션 | Prisma `$transaction` |
| 이메일 발송 | **[도입 필요 · v1.1]** |

**데이터**: `User(email, name, passwordHash, passwordSalt, ownerSessionId, locale)` · `AccountSession(tokenHash, userId)`
**API**: `POST /api/auth/register`
**화면**: `/auth/signup`
**예외·폴백**

| 상황 | 응답 |
| --- | --- |
| 이메일 중복 | `409 EMAIL_TAKEN` · "이미 가입된 이메일입니다" |
| 비밀번호 규칙 위반 | `400 WEAK_PASSWORD` · 규칙을 그대로 안내 |
| 서버 오류 | 입력값을 유지한 채 재시도 버튼 |

**수용 기준**: 가입 직후 익명 상태에서 만든 여행이 `/me/trips`에 그대로 보인다
**담당·마감**: BE · 완료 (이메일 인증은 v1.1)

### F-ACC-03 · 로그인·로그아웃

| 항목 | 내용 |
| --- | --- |
| **현재 상태** | **[구현됨]** |

**구현 방법**

1. `POST /api/auth/login` — 이메일로 사용자를 찾고 `verifyPassword`로 검증
2. 실패 시 **이메일이 없는 경우와 비밀번호가 틀린 경우를 구분하지 않는다** (`401 INVALID_CREDENTIALS`). 계정 존재 여부를 노출하지 않기 위함
3. 성공 시 `AccountSession` 발급
4. `POST /api/auth/logout` — 해당 세션 행 삭제

**필요 기술**: Node `crypto.scrypt` · Prisma
**데이터**: `User` · `AccountSession`
**API**: `POST /api/auth/login` · `POST /api/auth/logout` · `GET /api/auth/me`
**화면**: `/auth/login` · 사이드바 계정 메뉴
**예외·폴백**: 5회 연속 실패 시 rate limit이 걸린다(`express-rate-limit`). 화면에 "잠시 후 다시 시도" 안내
**수용 기준**: 로그아웃 후 보호된 API 호출이 401을 반환한다
**담당·마감**: BE · 완료

### F-ACC-05 · 계정·데이터 삭제 **[심사 필수]**

| 항목 | 내용 |
| --- | --- |
| **사용자 스토리** | 사용자가 앱 안에서 자기 계정과 데이터를 스스로 지울 수 있다 |
| **현재 상태** | **[미구현]** — App Store 지침 5.1.1(v) 위반 상태다 |

**구현 방법**

1. 화면: `/me/settings`에 `계정 삭제` 버튼. 누르면 **2단계 확인** — ① 결과 설명 ② 비밀번호 재입력
2. `DELETE /api/auth/me` 호출 (본문에 비밀번호)
3. 서버가 비밀번호를 재검증한다
4. 트랜잭션으로 삭제·익명화

| 대상 | 처리 |
| --- | --- |
| `AccountSession` | 전부 삭제 |
| `Story` · `StoryReport` | 삭제 (이미지는 스토리지에서도 삭제) |
| `Review` · `VisitVerification` | **익명화** — 사용자 연결만 끊고 장소 통계는 유지 |
| `Trip` · `Itinerary` 이하 전부 | 삭제 |
| `Follow` | 양방향 삭제 |
| `LocalProfile` | 삭제 |
| `User` | 삭제 |

5. 완료 후 클라이언트 저장소를 비우고 `/welcome`으로 이동

**필요 기술**: Prisma `$transaction` · 스토리지 SDK (이미지 삭제)
**데이터**: 위 표 전체
**API**: `DELETE /api/auth/me` **[신규]**
**화면**: `/me/settings` (웹·앱 모두)
**예외·폴백**

| 상황 | 처리 |
| --- | --- |

### F-REC-02 · 로컬 점수 산출

| 항목 | 내용 |
| --- | --- |
| **사용자 스토리** | "현지인이 다시 가는 곳"이라는 주장에 숫자 근거가 있다 |
| **현재 상태** | **[부분]** — 로직은 있으나 실사용 데이터가 거의 없다 (리뷰 1건, 방문 인증 1건, 카카오 평점 0건) |

**구현 방법**

1. 입력 3종을 합성한다

| 입력 | 처리 |
| --- | --- |
| GPS 방문 인증 | 인증된 방문 횟수 · 재방문 비율 |
| 인증 기반 리뷰 | 평점 평균 |
| 카카오 집계 | **권한이 확인된 집계만.** 후기 30건·평균 4.0을 사전값으로 둔 **베이지안 보정** |

2. 베이지안 보정식

```
adjusted = (priorCount * priorMean + reviewCount * rating)
         / (priorCount + reviewCount)
   where priorCount = 30, priorMean = 4.0
```

후기 3건에 5.0점인 곳이 후기 500건에 4.5점인 곳을 이기지 못하게 한다.

3. `localScoreSource`에 근거(`VISIT` / `KAKAO_LICENSED` / `SEED`)를 남기고 `localScoreUpdatedAt`을 갱신한다

**필요 기술**: TypeScript · 배치 재계산 스크립트 **[신규]**
**데이터**: `VisitVerification` · `Review` · `Place.kakaoRating` 외 6종 · `Place.localScore*`
**API**: 내부 · `POST /api/places/:id/visits/verify`
**화면**: 장소 카드 `로컬 점수 4.6/5`
**예외·폴백**: 카카오 집계가 없으면 **그 축을 아예 빼고** 나머지로 계산한다. 화면에도 카카오 카드를 띄우지 않는다
**수용 기준**: 카카오 데이터가 있는 곳과 없는 곳이 화면에서 구분된다. 근거 없는 별점이 표시되지 않는다

### F-SYS-08 · 이미지 오브젝트 스토리지 **[미구현]**

| 항목 | 내용 |
| --- | --- |
| **현재 상태** | **[미구현]** — 스토리 이미지를 **base64로 DB에** 저장한다 |

**왜 문제인가**: 이미지 1장이 3MB면 base64로 4MB가 된다. 사용자 100명이 10장씩 올리면 DB가 4GB가 된다. 조회할 때마다 이 데이터가 메모리를 지나간다.

**구현 방법**

1. 오브젝트 스토리지 버킷 생성 (INFRA)
2. `POST /api/uploads/story-image` — 서버가 **presigned URL을 발급**하거나 직접 프록시 업로드
3. 클라이언트가 스토리지에 직접 업로드
4. `Story.imageUrl`에 **URL만** 저장
5. **기존 base64 데이터 마이그레이션 스크립트** 작성 — DB에서 꺼내 스토리지에 올리고 URL로 교체
6. 삭제 시 스토리지 객체도 제거

**필요 기술**

| 항목 | 상태 |
| --- | --- |
| 오브젝트 스토리지 | **[도입 필요]** S3 호환 |
| SDK | **[도입 필요]** |
| CDN | v1.1 |

**데이터**: `Story.imageUrl` (URL로 변경)
**API**: `POST /api/uploads/story-image` **[신규]**
**예외·폴백**: 업로드 실패 시 작성 내용을 보존하고 재시도
**수용 기준**: 새 이미지가 DB에 base64로 저장되지 않는다. 마이그레이션 후 기존 이미지가 정상 표시된다
**담당·마감**: INFRA · BE · **9/2**

## 18. 공통 상태·오류 규격

화면마다 다르게 만들지 않는다. **아래 규격을 전 화면이 공유한다.**

### 18.1 4가지 상태

모든 데이터 화면은 네 상태를 반드시 처리한다.

| 상태 | 규격 |
| --- | --- |
| **로딩** | 스켈레톤 (스피너보다 나은 이유: 레이아웃이 흔들리지 않는다). 300ms 이내 응답이면 표시하지 않는다 |
| **비어 있음** | 아이콘 + 한 줄 설명 + **다음 행동 버튼**. "데이터가 없습니다"로 끝내지 않는다 |
| **오류** | 사람이 읽는 문장 + 재시도 버튼. 기술 용어·스택 트레이스 노출 금지 |
| **성공** | 정상 콘텐츠 |

### 18.2 오류 메시지 규칙

| 원칙 | 나쁜 예 | 좋은 예 |
| --- | --- | --- |
| 무엇이 안 됐는지 | "오류가 발생했습니다" | "일정을 불러오지 못했습니다" |
| 무엇을 하면 되는지 | (없음) | "다시 시도하거나 잠시 후 접속해 주세요" |
| 기술 용어 금지 | "500 Internal Server Error" | "서버에 문제가 생겼습니다" |
| 사용자 탓 금지 | "잘못된 값을 입력했습니다" | "예산은 10,000원 이상이어야 합니다" |

### 18.3 HTTP 상태별 화면 처리

| 코드 | 처리 |
| --- | --- |
| 400 | 해당 필드 아래 구체적 안내 |
| 401 | `/auth/login`으로 유도 (원래 가려던 곳 기억) |
| 403 | "권한이 없습니다" 화면. 홈 링크 |
| 404 | "찾을 수 없습니다" + 상위로 |
| 409 | 충돌 안내 + 최신 내용 보기 (공동 편집) |
| 429 | "요청이 많습니다. 잠시 후 다시 시도해 주세요" |
| 500 | "서버에 문제가 생겼습니다" + 재시도 |
| 네트워크 단절 | 상단 배너 + 캐시된 내용 유지 |

### 18.4 반드시 지키는 것

| 항목 | 규칙 |
| --- | --- |
| **흰 화면 금지** | `ErrorBoundary`가 최상위를 감싼다. 어떤 렌더 오류도 안내로 바뀐다 |
| **가짜 데이터 금지** | 실제 값이 없으면 그 영역을 숨긴다. 하드코딩한 값을 보여주지 않는다 |
| **추정값 표기** | 이동시간·비용이 추정이면 화면에 "예상"을 붙인다 |
| **안전 정보** | 알레르기·식단 정보가 없으면 "확인 필요"를 표시한다. 침묵하지 않는다 |
| **권한 거부 대응** | 위치·카메라·마이크를 거부해도 앱이 죽지 않고 대체 경로를 준다 |

## 결론

이 문서는 두 가지 질문에 답한다.

**① 무엇을 만드는가** — 56개 기능. 그중 **42개는 이미 동작하고, 7개는 가짜이며, 8개는 없다.** 가짜인 7개(날씨·음성 통역·메뉴판·이미지 저장·예약·광고·날씨 위젯)를 진짜로 바꾸는 것이 이번 프로젝트의 핵심이다.

**② 어디에 놓는가** — 44개 화면. 그중 **23개는 완성됐고, 17개가 남았다.** 남은 것 중 7개는 스토어 심사 필수 화면이라 자를 수 없다.

작업 순서를 정할 때 기준은 하나다.

> **심사에서 막히는 것 → 사용자가 매일 쓰는 것 → 나머지**

그래서 `/legal/*` 3종(8/29)과 계정 삭제(9/1)와 신고 검토 큐(9/2)가 화면 개수로는 작은데도 마감이 가장 이르다. 이것들이 없으면 나머지를 아무리 잘 만들어도 앱이 스토어에 올라가지 않는다.
