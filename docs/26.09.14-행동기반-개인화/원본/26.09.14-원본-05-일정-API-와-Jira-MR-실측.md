`AddItemRequest.java`:

```java
/**
 * 장소를 일정에 더하는 요청 — S15P21E201-467.
 * POST /api/v1/itineraries/{itineraryId}/items.
 * baseVersion 은 화면이 보고 있던 판이다. 그 사이 다른 편집이 있었으면 409 다.
 */
public record AddItemRequest(
		@NotNull String placeId,
		@NotNull @Min(0) Integer dayIndex,
		@NotNull Integer baseVersion) {
}
```

→ 일정에는 **버전(낙관적 동시성) + 요일 인덱스 + placeId** 를 갖춘, 실제로 동작하는 편집
API 가 있다(추가/잠금/재정렬/되돌리기 컨트롤러가 각각 존재). "일정을 뺐다/바꿨다/건너뛰었다"
를 판단할 안정적인 대상(trip/itinerary/day/placeId)은 이미 있는 것으로 보인다.

🔴 **확인 못 함**: 이 `placeId` 가 화면에 실제로 검색해서 고른 진짜 장소 UUID인지,
아니면 홈 화면처럼 목업이 섞여 들어갈 수 있는지는 프론트엔드 코드까지 따라가야
확실하다 — 이번 조사에서는 백엔드 API 존재만 확인했다. 장소 목업 문제(EventType.java
주석)는 "홈 화면·장소 상세·체크인 화면"을 지목했지, 일정 추가 플로우를 지목하지
않았다는 점도 함께 적어 둔다.
