# 03 — 구상: 전체를 어떻게 풀 것인가 (제안, 사실 아님)

🔴 **이 문서 전체는 제안이다.** 02 문서의 실측 막힘 목록을 근거로 순서를 짜 본 것이지,
팀이 합의한 로드맵이 아니다. 각 단계 끝에 "왜 이 순서인가"를 적었으니 다른 순서가
더 맞다고 판단되면 그쪽을 따라가면 된다.

## 순서를 정하는 기준

1. **결정 없이 코드부터 짜면 버리는 코드가 생긴다** — A1·A2·A3(02 문서)를 코드보다 먼저 정리
2. **막혀 있는 것 위에 쌓지 않는다** — 장소 4종(C1)은 place_id 문제가 안 풀리면 그 위에
   무엇을 얹어도 의미가 없다
3. **이미 도는 것을 안 건드리는 순서** — 개인화 on/off, event_outbox 파이프, 일정 편집
   API 는 이미 완성돼 있으니 그 위에 얹기만 하면 된다

## Phase 0 — 지금 하던 것 마무리 (진행 중)

- MR !736(787 고침) 머지 확인 → 그 다음 916 착수(사전 밖 낱말 재점검)
- 이 단계는 이미 이번 대화에서 진행 중이던 것이라 별도 설명 생략

## Phase 1 — 장소 식별자를 진짜로 만든다 (제안 우선순위 최상위)

**왜 1순위인가**: 장소 관련 4종(PLACE_*)이 취향 신호 7종 중 4개, 즉 절반 이상을 차지한다.
이걸 안 풀면 아무리 다른 걸 고쳐도 "장소를 좋아했다/봤다"는 신호 자체가 안 생긴다.

- 홈 화면·장소 상세 화면이 실제 장소 검색/추천 결과의 UUID 를 쓰도록 프론트엔드 수정
  (지금 목업값 — 확인 못 함: 정확한 컴포넌트/파일)
- 체크인 화면에 장소 식별자를 넘기는 경로 설계(지금 아예 없음)
- 이건 **백엔드 문제가 아니라 프론트-백엔드 계약 문제**일 가능성이 높다 — 프론트 쪽
  조사가 별도로 필요함(이번 조사는 백엔드 위주였다)

## Phase 2 — 행동 → 무게 변환 규칙을 정하고 연결한다

**왜 2순위인가**: A1 결정 없이 B3(코드)을 먼저 만들면 나중에 규칙이 바뀔 때 다시 짜야
한다. 결정이 먼저다.

- (제품 결정) A1: 신호별 sign/decay 규칙표를 만든다. 예시 스케치(제안일 뿐):
  - `PLACE_LIKE` → +1.0, 즉시 확정 (설문 태그와 동일 취급)
  - `PLACE_DISLIKE` → -1.0
  - `PLACE_VIEW`(그냥 봄, 안 누름) → 신호 자체가 약하다 — 안 넣거나 아주 작은 +값
  - `ROUTE_SKIP`/`ITINERARY_REMOVE` → 대화에서 나온 질문 그대로: "그 항목의 취향 방향으로
    -값"과 "그 항목이 대변하던 차원의 가중치만 살짝 낮춤" 둘 다 구현 가능. 후자가
    "안 물어본 것과 싫어하는 것을 섞지 않는다"는 `UserTasteWeight` 의 기존 설계 철학
    (0 을 안 넣는다)과 더 잘 맞아 보인다는 게 이 문서 작성자의 의견(확인 안 됨, 제안)
  - `support`(관측 수) 는 같은 (차원,코드) 에 여러 행동이 쌓일 때 이동평균/가중치로
    합치는 데 씀 — 이미 필드는 있음(`fromInteraction`)
- (코드) B3: `TasteVectorFoldService` 에 `foldBehavior` 류 메서드 추가, `countTasteSignals`
  자리에서 실제 이벤트 행을 읽어 `fromInteraction` 호출
  - 건드릴 파일: `TasteVectorFoldService.java`(같은 파일 안에 나란히),
    `UserTasteWeight.java`(이미 있음, 안 고쳐도 될 수 있음)

## Phase 6 (낮은 우선순위) — 일정 3종

**왜 마지막인가**: 취향 신호 7종 중 3개뿐이고, 대체(태그+슬라이더)로도 상당 부분
커버되는 "약한 신호"에 가깝다는 게 이 문서의 추정(확인 안 됨). 반대로 Phase 1 과
달리 **밑바탕(일정 편집 API)은 이미 있어서** 나중에 붙이기는 상대적으로 쉬워 보인다.

- 일정 편집 컨트롤러(`ItineraryEditController` 등)에서 삭제/교체/건너뛰기 발생 시
  `POST /api/v1/events` 호출 추가(서버 발행) — Phase 2 의 sign/decay 결정에 의존
