# 01 — 지금 아키텍처 지도 (행동 기반 개인화)

원본: `원본/26.09.14-원본-01-접기-배치와-무게-팩토리.md` · `원본/26.09.14-원본-02-이벤트-종류와-수집-경로.md` · `원본/26.09.14-원본-03-추천-채점기가-읽는-것.md` · `원본/26.09.14-원본-04-개인화-onoff-와-배치-스케줄.md`

## 한 줄

**"설문 → 추천"은 실제로 도는 하나의 길이고, "행동 → 추천"은 중간에 세 군데가 끊긴 완전히 다른 길이다 — 심지어 안 끊긴 부분(취향 벡터)조차 아직 추천에 안 이어져 있다.**

## 전체 경로를 5단계로 나누면

```
[1: 신호 발생]  →  [2: event_outbox 수집]  →  [3: 접기 배치]  →  [4: 저장(벡터)]  →  [5: 추천 소비]
   클라이언트         POST /api/v1/events      TasteVectorFold        user_taste_          BaselineCandidate
   또는 서버                                   Service                 weight/vector          Scorer
```

NotebookLM 에 그려 달라고 할 그림: **위 5단계를 가로로 놓고, 설문(survey) 경로와 행동
(behavior) 경로를 위아래 두 줄로 나란히 그려서 각 칸을 초록/회색/빨강으로 칠하는 다이어그램.**

## 단계별 상태 (초록 = 실제로 돈다 · 회색 = 그릇은 있는데 안 씀 · 빨강 = 아예 없음)

| 단계 | 설문(survey) 경로 | 행동(behavior) 경로 |
| --- | --- | --- |
| **1. 신호 발생** | 🟢 온보딩 화면에서 답을 고르면 `preference_answer` 에 저장됨 | 🔴 프론트엔드 전체에서 이벤트 전송 호출 0건(taste 신호 7종 전부 포함). 서버가 스스로 만드는 추천 요청/실패 이벤트만 예외적으로 🟢 |
| **2. 수집 표** | 🟢 `preference_snapshot`/`preference_answer` (EAV 표) | ⚪ `event_outbox` 표·접수 엔드포인트(`POST /api/v1/events`)는 있고 어떤 종류든 받을 수 있다(범용 설계) — 근데 1단계에서 안 보내니 행동 신호로는 안 채워짐 |
| **3. 접기 배치** | 🟢 `TasteVectorFoldService.foldSurvey` — 787 고침으로 정상 동작(맨 배열·슬라이더 정규화 모두 처리) | 🔴 `countTasteSignals` 로 **개수만 셀 뿐**, 개수를 무게로 바꾸는 코드가 없다(`fromInteraction` 팩토리는 있지만 호출자 0건) |
| **4. 저장(벡터)** | ⚪ `user_taste_vector`/`user_taste_weight` 에 저장은 됨 — 근데 배치 자체를 부르는 스케줄러가 없어서(아래) 운영에는 안 쌓인다 | 🔴 위와 동일 이유로 애초에 만들어질 값이 없음 |
| **5. 추천 소비** | 🔴 **추천 채점기(`BaselineCandidateScorer`)는 이 벡터를 안 읽는다.** 매 요청마다 `preference_snapshot`/`preference_answer` 를 직접 다시 읽어서 계산한다 | 🔴 (4가 비어 있으니 소비할 것도 없음) |

## 가장 중요한 발견 — 벡터 자체가 아직 "고립된 섬"이다

787/916/918 은 전부 "접기 배치가 올바로 벡터를 만드는가"에 대한 티켓이다. 그런데
**그 벡터를 실제 추천이 읽는 코드가 지금 존재하지 않는다.** `BaselineCandidateScorer.score()`
의 인자에 `UserTasteVector`/`UserTasteWeight` 가 없고, `preference_snapshot` 을 직접
읽는다(원본 03). 즉:

- 787 을 고쳐서 벡터가 정확해져도, 918 을 고쳐서 배치가 매일 돌아도, **지금 이 순간
  추천 결과는 단 1도 바뀌지 않는다.** 벡터는 아직 아무도 안 읽기 때문이다.
- 이건 "MLOps Phase 1" 이라는 이름 그대로 — 벡터 파이프라인이 **미래의 소비자(아마
  Phase 2 의 개인화 모델)를 위해 먼저 만들어지고 있는 중**이라는 뜻일 수 있다.
  🔴 확인 못 함 — 이 벡터를 언제/무엇이 읽을 계획인지는 이번 조사 범위 밖의 문서에
  있을 수 있다(예: `docs/gabolle/GABOLLE_개인화_인프라_구축_가이드.docx` — 열어보지
  않았다).

## 반대로 확실히 "잘 만들어져 있는" 부분

- **개인화 on/off 스위치**: `BehaviorPersonalizationReset` 이 `ConsentUpdateService` 에
  실제로 연결돼 있고, 끌 때 벡터·피드·이벤트 원본까지 지운다(원본 04). 이 부분은
  이미 완성돼 있다 — 손댈 필요 없음.
- **event_outbox 파이프 자체**: 종류별 표가 아니라 범용 표+엔드포인트라서, 새 이벤트
  종류를 추가할 때 **DB 스키마를 더 안 만들어도 된다.** 없는 건 "보내는 코드"뿐.
- **일정 편집 API**: 버전(낙관적 동시성)·요일 인덱스·장소ID 를 갖춘 진짜 API 가 있다
  (원본 05) — 일정 관련 행동 신호(`ITINERARY_REMOVE`·`REPLACE`·`ROUTE_SKIP`)를 만들 때
  이 위에 얹을 수 있어 보인다(확인 못 함: 프론트가 이 API 에 진짜 placeId 를 넘기는지).
