## 1. 러너(Runner)가 무엇인가

**러너 = CI 검사를 실제로 실행하는 컴퓨터.**

여기가 제일 많이 오해되는 곳이다. GitLab 은 **무엇을 언제 돌릴지만 정하고, 실제로
돌리지는 않는다.** 코드를 push 하면 GitLab 은 `.gitlab-ci.yml` 을 읽어 *이런 일을 해야
한다* 는 목록(**파이프라인** — 한 번의 push 에 딸린 검사 묶음)을 만들어 두고, 누가
가져가기를 기다린다.

그 목록의 항목 하나하나를 **잡(job)** 이라고 부른다. 잡을 가져가서 실제로 `npm test`
를 치는 것이 러너다. 러너는 GitLab 서버와 별개의 프로그램이고, 보통 다른 컴퓨터에서 돈다.

```
push ──▶ GitLab ─────────────▶ pending ┄┄┄▶ 러너
         할 일 목록을 만든다     가져갈 러너를      (지금은 없다)
                                기다린다
                                   │
                                   └── 러너가 없으면 여기서 영원히 멈춘다
```

GitLab 은 목록을 만들 뿐이다. 실행은 러너가 한다.

### 러너가 없으면 어떻게 보이나

> 🔴 **여기서 대부분 헷갈린다.**
> `failed`(실패)가 아니라 **`pending`(아직 시작 안 함)** 으로 멈춘다.
> 실패한 게 아니라 *시작을 못 한 것*이라, 화면만 보면 "곧 되겠지" 로 읽힌다.
> 며칠이 지나도 그대로다. MR(**머지 리퀘스트** — 내 브랜치를 다른 브랜치에 합쳐
> 달라는 요청) 화면의 파이프라인 칸이 계속 회색이면 십중팔구 러너 문제다.

### 러너의 종류 — 셋 중 하나만 있으면 된다

| 종류 | 누가 관리하나 | 확인하는 곳 |
|---|---|---|
| **Instance(공유)** | SSAFY GitLab 관리자 | `Settings → CI/CD → Runners` 의 "Instance runners" |
| **Group** | 그룹 관리자 `s15-bigdata-dist-sub1` | 같은 화면의 "Group runners" |
| **Project** | **우리가 직접 등록** | 같은 화면의 "Project runners" |

**먼저 위의 둘을 확인한다.** 공유 러너가 이미 켜져 있으면 아무것도 안 해도 된다.
2026-08-25 에 본 것: 프로젝트 러너는 없었고, 위의 둘은 확인하지 못했다.

### 직접 등록해야 한다면

러너를 설치할 컴퓨터가 하나 필요하다. 각자 PC 도 되고 서버도 된다 — **켜져 있어야
잡을 가져간다.** (이게 왜 머지를 막을 수 있는지는 5절 마지막에 있다.)

```bash
# 1. 러너 프로그램 설치 (리눅스)
curl -L https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh | sudo bash
sudo apt install gitlab-runner

# 2. 이 프로젝트에 붙인다
#    토큰은 Settings → CI/CD → Runners → "New project runner" 에서 받는다
sudo gitlab-runner register \
  --url https://lab.ssafy.com/ \
  --token <프로젝트 러너 토큰> \
  --executor docker \
  --docker-image node:20-alpine
```

### `--executor docker` 를 고른 이유

**executor(실행기)** — 러너가 잡을 *어떤 환경에서* 돌릴지 정하는 설정이다.

- `shell` — 러너가 깔린 컴퓨터에서 그냥 명령을 친다. 빠르지만 **이전 잡의 찌꺼기가
  남는다.** 누가 전역으로 뭘 설치해 두면 그 뒤 모든 잡이 그 상태를 물려받고,
  "내 PC 에선 되는데" 가 CI 에서 재현된다
- `docker` — 잡마다 **깨끗한 컨테이너**(그 잡만 쓰고 버리는 일회용 리눅스)를 새로
  띄운다. 우리 설정은 잡마다 `image:`(그 컨테이너의 바탕이 될 리눅스 종류)를 다르게
  지정하는데, 그게 되려면 docker 여야 한다. 자세한 것은 4절

## 2. 버전이 자동으로 올라가는 원리

**어느 브랜치에 머지되었는지가 `major.minor.patch` 중 어느 자리를 올릴지를 정한다.**

| 머지된 곳 | 올라가는 자리 | 예 |
|---|---|---|
| `<파트>/dev`<br>`back/dev` · `front/dev` | patch | 1.0.0 → 1.0.1 |
| `<파트>/main` 또는 `<파트>/func` | minor (patch 는 0) | 1.0.3 → 1.1.0 |
| **최상위 `main`** (접두사 없음) | major (아래 전부 0) | 1.2.0 → 2.0.0 |
| `feat/…` 기능 브랜치 | **안 올린다** — 단계가 없다 | |

판정은 `ci/axmap/src/version.mjs` 의 `levelOf()` 가 한다. 규칙은 **브랜치 이름의 마지막
조각**을 본다 — `main`·`master`·`func` 이면 파트 단계(minor), `dev` 면 patch,
그 외에는 안 올린다. 첫 태그는 단계와 무관하게 `v1.0.0` 이다.

> 🔴 **`back/main` 은 최상위가 아니다.**
> 규칙에서 제일 미끄러지기 쉬운 곳이다. 파트 브랜치가 `back/main` · `front/main` 인데
> "이름에 main 이 들어가면 최상위" 로 짜면 **파트에 머지할 때마다 major 가 올라간다.**
> 하루 두 번 머지하면 이틀 만에 5.0.0 이고, 그 숫자는 아무것도 가리키지 않는다.
> **슬래시가 있으면 최상위가 아니다.**

### 왜 날짜가 아니라 병합인가

원래 요구는 *하루가 지나면 minor, 한 주가 지나면 major* 였다. 그런데 달력으로 올리면
**아무 일도 안 한 날에도 버전이 올라간다.** 금요일에 2.0.0 을 찍었는데 그 주에 머지된
게 하나도 없으면 그 숫자는 무엇도 가리키지 않는다.

팀의 실제 리듬이 이미 그 주기다 — dev 는 수시로, dev→func 는 하루 한 번, func→main 은
주 한 번. 그래서 **병합이 일어난 그 순간** 올린다. 결과는 요구한 것과 같고, 다른 점은
그 숫자가 언제나 실제로 들어간 코드를 가리킨다는 것이다.

### 왜 파일이 아니라 git 태그인가

`VERSION` 파일이나 `package.json` 의 `version` 을 올리는 방식이 흔한데, 그렇게 하면
**머지마다 텍스트 충돌이 난다.** `back/dev` 와 `front/dev` 가 각자 1.0.1 로 올리면 같은
줄이 부딪히고, 사람이 손으로 푸는 순간 어느 숫자가 맞는지 아무도 모른다.

태그는 파일이 아니라 **ref**(git 이 커밋 하나에 붙여 두는 이름표)라 같은 줄을 다투지
않는다. 그리고 git 이 이름 충돌을 막아준다 — 이미 있는 태그는 두 번 만들 수 없어서,
두 파이프라인이 동시에 같은 번호를 만들려 하면 **한쪽이 반드시 실패한다.**
조용히 덮어쓰이지 않는다.

### 손으로 확인하려면

```bash
npx -y axmap-cli@latest version current                  # 지금 버전
npx -y axmap-cli@latest version next --branch back/dev   # 계산만 (아무것도 안 바꿈)
npx -y axmap-cli@latest version bump --branch back/dev   # 로컬에 태그를 만든다
npx -y axmap-cli@latest version bump --branch back/dev --push   # 원격까지 올린다
```

`--push` 를 빼면 태그는 이 PC 에만 생긴다. CI 의 `version` 잡은 `--push` 까지 붙여 부른다.

**MR 에서는 안 올린다.** 머지되어 브랜치에 실제로 들어온 것만 버전을 갖는다.

규칙의 전문(`docs/VERSIONING.md`)은 **axMap 저장소** 안에 있다 —
`https://lab.ssafy.com/rleaderjoon/axmap`. 이 저장소에는 그 파일이 없다.
위에 적힌 것이 팀이 실제로 쓰는 부분의 전부다.

## 3. 봇 — `axmap-bot` 은 무엇이고 왜 필요한가

### CI 는 저장소에 push 할 수 없다

버전을 올린다는 것은 **태그를 만들어 저장소에 push 한다**는 뜻이다. 그런데 CI 잡이
기본으로 들고 있는 자격증명(`CI_JOB_TOKEN` — GitLab 이 잡마다 자동으로 넣어 주는
임시 열쇠)은 **읽기는 되지만 push 는 안 된다.** 일부러 그렇게 돼 있다 — CI 가 자기
저장소를 마음대로 고칠 수 있으면 위험하기 때문이다.

그래서 push 할 수 있는 자격증명을 따로 만들어 줘야 하고, 그게 **Project Access Token**
(프로젝트 하나에만 쓰는 자동화용 계정. 사람에게 묶이지 않는다)이다.
이 저장소에서는 그 이름을 `axmap-bot` 으로 쓴다.

### 만드는 절차

| 어디 | 무엇 |
|---|---|
| `Settings → Access Tokens` | Name `axmap-bot` · Role **Maintainer** · Scope(**그 토큰이 무엇까지 할 수 있는지의 범위**) 는 아래 "scope 는 `api` 가 아니어도 된다" 를 먼저 읽는다<br>태그를 push 하려면 Role 은 Maintainer 여야 한다 |
| 토큰 문자열 | **한 번만 보인다.** 그 자리에서 복사한다 |
| `Settings → CI/CD → Variables` | Key `AXMAP_BOT_TOKEN` · **Masked**(로그에 값이 안 찍히게 가리는 표시) + **Protected**(보호 브랜치에서 도는 잡에만 값을 내려주는 표시) |

#### 🔴 넣을 변수는 하나가 아니라 **넷**이다 (2026-09-01 기준)

`jira` 잡과 `vote:recheck` 잡이 생기면서 늘었다. **Type 은 `Variable`, Environments 는
`All` 그대로** 두고 아래만 채운다.

| Key | Value | Visibility | Protect |
|---|---|---|---|
| `AXMAP_BOT_TOKEN` | 위에서 만든 토큰 | **Masked** | ✅ |
| `JIRA_BASE_URL` | `https://ssafy.atlassian.net` | **Visible** | ✅ |
| `JIRA_EMAIL` | 토큰을 만든 계정 메일 | **Visible** | ✅ |
| `JIRA_TOKEN` | `id.atlassian.com` → Security → API tokens | **Masked** | ✅ |

- 🔴 **`Masked and hidden` 을 고르지 않는다.** 저장 뒤로는 값을 **다시 볼 수 없어서**
  잘못 넣으면 지우고 새로 만드는 수밖에 없다
- 주소와 메일은 **`Visible`** 로 둔다. `Masked` 는 값에 형식 조건이 있어 **저장이
  거부될 수 있고**, 그 둘은 애초에 비밀이 아니다
- 🔴 **`AXMAP_BOT_TOKEN` 의 scope 는 `api` 여야 한다.** 표 트리거(`vote:recheck`)가
  **GitLab API 로 MR 파이프라인을 만들기** 때문이다. `read_api` 로는 그것을 못 한다

**이 넷이 들어가면 셋이 함께 산다** — 버전 태그 · Jira 자동 전환 · 표 트리거.

### 토큰이 없으면 — 조용히 건너뛰지 않는다

의도적인 설계다. 토큰이 없으면 `version` 잡은 **다음 버전이 무엇이었을지 계산해 로그에
찍고, 설정하는 법을 안내한 뒤 `passed`(초록) 로 끝난다.** 실제 코드는 `.gitlab-ci.yml`
의 `version` 잡에 있고, `AXMAP_BOT_TOKEN` 이 빈 값이면 `next` 만 부르고 `exit 0` 한다.

*버전 자동화가 안 돌고 있다는 것을 아무도 모르는 상태* 가 제일 나쁘기 때문이다.
빨갛게 막지도 않고 — 그러면 아무도 머지를 못 한다 — 아무 말 없이 넘어가지도 않는다.

### 🔴 여기서 실제로 밟게 되는 함정

이 아래는 **원본 인수인계 화면에 없던 것**이다. 토큰을 만들 때 함께 확인한다.

#### `Protected` 변수와 보호 브랜치가 어긋나면 태그가 조용히 안 붙는다

`AXMAP_BOT_TOKEN` 을 **Protected** 로 만들면, **보호 브랜치**(GitLab 의
`Settings → Repository → Protected branches` 에 등록해서 아무나 push 하거나 지울 수
없게 잠근 브랜치)가 **아닌** 곳에서 도는 잡에는 **빈 값**이 간다.

`version` 잡은 브랜치 이름의 마지막 조각이 `main`·`func`·`dev` 인 곳 전부에서 돈다 —
지금 팀 컨벤션대로면 `front/dev` · `back/dev` · `front/main` · `back/main` · 최상위
`main` 이고, `ai/` 파트가 붙으면 거기도 포함된다. **이 중 보호 브랜치로 등록 안 된
곳에서는** 잡이 "토큰이 없습니다" 경로로 빠져 **초록으로 끝난다. 빨갛지 않다.**

→ 토큰을 넣을 때 **그 브랜치들이 전부 보호 브랜치인지 함께 확인해야 한다.**

| `main` | ✅ 등록됨 | merge=Maintainers · push=No one |
| `til` | ✅ 원래 등록됨 | 배운 것을 적는 자리 |
| `*/dev` | ✅ **이날 등록함** | 5개 브랜치. merge·push 둘 다 **Developers + Maintainers** 로 두어 **지금 동작이 하나도 안 바뀐다** — 목적은 Protected 변수를 여기까지 오게 하는 것뿐이다 |
| `*/main` (파트) | ✅ **이날 등록함** | 5개 브랜치. `*/dev` 와 같은 설정이다. 이걸 안 하면 **파트 승격 때 minor 태그가 조용히 안 붙는다** — 초록인데 태그만 없는 그 모양이다 |

> 보호 브랜치를 만든다고 **꼭 잠그는 것은 아니다.** `Allowed to push and merge` 를
> `Developers + Maintainers` 로 두면 **누구나 밀어 넣을 수 있는 상태 그대로**이면서
> GitLab 이 그 브랜치를 "보호됨" 으로 취급한다. `*/dev` 를 그렇게 열어 둔 이유가
> 이것이다 — `dev` 는 일부러 연 자리다(`.gitlab-ci.yml` 의 `governance` 잡 주석).

#### 토큰 만료일이 곧 자동화의 수명이다

GitLab 은 Project Access Token 에 만료일을 강제한다. 만료되면 바로 위 항목과 **똑같은
모양으로** 죽는다 — 초록인데 태그만 안 붙는 상태. 어디에도 빨간 표시가 안 뜬다.

→ **만료일을 [`docs/HANDOVER.md`](HANDOVER.md) 에 적고 달력에 넣는다.**

#### ~~SSAFY GitLab 이 Project Access Token 을 꺼 뒀을 수 있다~~ — 살아 있다 (2026-08-26 확인)

인스턴스 관리자가 끌 수 있는 기능이라 걱정했는데, **켜져 있는 것을 확인했다.**
목록 조회가 정상 응답했고 지금 만들어진 토큰은 없다. 이 걱정은 소거됐다.

아래는 나중에 이 기능이 막혔을 때를 위해 남긴다. 대안은 둘인데 둘 다 대가가 있다.

| 대안 | 대가 |
|---|---|
| 개인 PAT(**Personal Access Token** — 사람 계정에 묶인 열쇠) | **그 사람이 팀을 나가면 CI 가 죽는다** |
| write 권한 deploy key(**저장소 하나에 붙이는 SSH 열쇠**) | 사람에는 안 묶이지만 관리 창구가 또 하나 늘어난다 |

**실물을 본 뒤에 정한다.** 탭이 있는지 없는지가 먼저다.

#### scope 는 `api` 다 — 승격을 봇에게 맡기기로 정했기 때문이다

태그 push 만 놓고 보면 `write_repository`(**https 로 git 을 밀 수 있는 권한**)로
충분하다. 태그를 만드는 건 결국 git push 이기 때문이다.

그런데 **봇이 승격 MR 을 만들고 머지까지 한다**(2026-08-26 결정 — `<파트>/dev →
<파트>/main` 하루 한 번, `<파트>/main → main` 주 한 번). MR 을 만들고 머지하는 것은
git 이 아니라 GitLab API 를 부르는 일이라 **`api` 가 필요하다.**

그래서 토큰은 하나만 만들고 scope 는 `api` 로 준다. 태그도 승격도 같은 토큰이 한다.

> ⚠️ scope 는 GitLab 설정이지 저장소 파일에서 읽는 값이 아니다. 그래서 어느 문서에
> 무엇이 적혀 있든 **실제 동작을 바꾸는 것은 토큰을 만들 때 고른 체크박스뿐**이다.
> `write_repository` 로 만들면 태그는 붙지만 **승격 봇이 MR 을 못 만들고 조용히
> 실패한다.** `api` 로 만들어라.

#### `v*` 를 Protected tags 로 잠글 거면 봇을 그 규칙에 넣어야 한다

**Protected tags**(`Settings → Repository → Protected tags`) — 특정 이름 모양의 태그를
누가 만들 수 있는지 제한하는 설정이다. 2026-08-26 기준 이 저장소에는 태그가 아직
하나도 없다(`git tag -l` 이 빈 출력이다).

**2026-08-26 확인: Protected tags 규칙은 비어 있다.** 그래서 지금은 봇이 태그를
그냥 만들 수 있다. 나중에 `v*` 를 잠글 때만 신경 쓰면 된다.

나중에 `v*` 를 잠글 때 **`axmap-bot` 을 "Allowed to create" 에 넣지 않으면 그날부터
태그가 안 붙는다.** 그리고 이번에도 증상은 같다 — 잡은 실패하지만, 아무도 태그를
안 보고 있으면 며칠이 지나야 알아챈다.

### "봇만 머지한다" 와 헷갈리면 안 된다

문서 여기저기에 *봇만 머지 버튼을 누르게 한다* 는 이야기가 나온다.
**그건 아직 구현된 게 아니고, 권한으로는 구현할 수도 없다.**

이 GitLab 은 **Community Edition**(무료판)이라 보호 브랜치의 "Allowed to merge" 를
**사람 한 명 단위로 지정하는 것이 유료 기능**이다. 무료판에는 역할 단위
(`No one` / `Maintainers` / `Developers`)밖에 없고, 봇도 Maintainer 라 사람 Maintainer
와 구분되지 않는다.

| | `axmap-bot` 토큰 | "봇만 머지" (미구현) |
|---|---|---|
| **하는 일** | 태그를 push 한다 | 머지 버튼을 누른다 |
| **상태** | 토큰만 만들면 바로 된다 | 무료판에서는 만들 수 없다 |

무료판에서 Maintainer 까지 실제로 묶는 장치는 **필수 파이프라인 하나뿐**이다 (5절).

## 4. 도커 — 기존 프로젝트와 무엇이 다른가

### "도커" 가 여기서 두 가지를 가리킨다

이 구분이 안 되면 이 절 전체가 안 읽힌다.

| | **검사가 도는 컨테이너** | **배포되는 서비스 이미지** |
|---|---|---|
| **무엇** | 테스트를 돌릴 일회용 리눅스 | 서버에 올라가 사용자 요청을 받는 것 |
| **어디 적나** | `.gitlab-ci.yml` 의 `image:` | `Dockerfile` |
| **언제 사라지나** | 잡이 끝나면 즉시 | 계속 떠 있다 |
| **이 저장소에** | **있다** | **없다** |

보통 "도커 작업" 이라고 하면 **배포되는 서비스 이미지** 쪽을 말한다. 서버
애플리케이션을 `Dockerfile` 로 빌드해 배포하는 것.
**이 저장소에는 그게 없고, 지금은 필요하지도 않다.**

지금 이 저장소의 CI 가 부르는 것은 **선점 장치의 사본**(`ci/axmap/`)뿐이고, 그건
**배포되는 서비스가 아니라 개발할 때 쓰는 도구**다. 각자 PC 에서
`npx -y axmap-cli@latest` 로 돌린다. 서버에 올라가지 않으니 이미지를 만들 이유가 없다.

**여행 서비스 파트(`frontend/` · `backend/`)가 붙으면 그때 서비스 이미지가 필요해진다.**
그건 그 파트의 CI 로 따로 만든다 — 섞으면 프론트 빌드가 깨졌을 때 선점 검사까지
같이 빨개진다.

### 검사가 도는 컨테이너 쪽에서 이 저장소가 특이한 점

일반적인 Node 프로젝트라면 `image: node:20` 한 줄이면 끝난다. 여기는 아니다.

```yaml
default:
  image: node:20-alpine
  before_script:
    - apk add --no-cache git bash        # ← 이 줄이 특이한 부분
```

`before_script` 는 **그 잡의 진짜 명령을 돌리기 전에 컨테이너에 먼저 치는 준비 명령**
이고, `apk` 는 alpine(**용량을 극단적으로 줄인 리눅스 배포판**)의 패키지 설치 명령이다.

- **컨테이너 안에 `git` 이 있어야 한다.** 여기서 도는 검사는 거의 전부 git 위에서 돈다 —
  `claims` 는 장부 브랜치의 이력을 처음부터 재생하고, `governance` 는 소스와 타깃의
  갈림점을 구하고, `version` 은 태그를 만들어 push 한다. `node:20-alpine` 에는
  **git 이 안 들어 있어서** 그냥 돌리면 이 잡들이 통째로 죽는다. 보통의 백엔드 CI 는
  소스를 받아오기만 하면 되니 이런 일이 없다
- **`bash` 는 지금 아무도 안 쓴다.** `default: before_script` 에 `apk add ... git bash`
  로 아직 함께 깔려 있는데, bash 를 요구하던 것(axMap 의 데모 스크립트)은 axMap 과 함께
  저장소를 떠났다. 남은 잡의 셸 조각은 전부 alpine 기본 `sh` 로 돈다.
  **지우자는 말은 아니다** — 여행 서비스 파트가 붙으면 다시 필요해질 수 있다.
  다만 *"왜 bash 를 까나"* 의 원래 이유는 이제 없다는 것을 적어 둔다

> 🔴 **브라우저를 띄우는 잡은 이제 없다.** 전에는 `verify:screen` 이 alpine 대신
> `node:20`(데비안 기반)을 쓰고 `apt-get` 으로 크롬을 깔았는데, 그 잡은 axMap 의
> 화면을 검사하던 것이라 axMap 과 함께 나갔다.
> **여행 서비스 파트가 화면 검사를 붙일 때 그 방식을 다시 쓰게 된다.** 그때 밟을 함정
> 하나만 남겨 둔다 — 데비안 계열 이미지는 패키지 목록을 비워 둔 채로 배포되므로
> `apt-get update` 없이 `apt-get install` 을 치면 **"그런 패키지 없음" 으로 실패한다.**

> 그리고 그 잡이 있던 이유도 남겨 둔다. **단위 테스트는 브라우저 코드를 실행하지
> 않으므로 화면이 죽어 있어도 초록이다.** 실제로 하룻밤에 두 번 겪었다 — 주석 안의
> `*/` 가 파일을 닫았고, `let` 선언이 첫 사용처보다 아래에 있어 부트스트랩이 통째로
> 죽었다. **둘 다 문법 검사와 단위 테스트를 전부 통과했다.** 화면을 만드는 파트는
> 화면이 실제로 뜨는지 보는 잡을 따로 가져야 한다.

### 잡이 언제 도는지 — 파일에 적힌 그대로

| 잡 | 무엇을 돌리나 | 언제 도나 |
|---|---|---|
| `ci:vendor` | `npx -y axmap-cli@latest doctor` — `ci/axmap/` 사본이 손으로 바뀌지 않았는지 | **모든 MR**, 그리고 이름이 `main`·`func`·`dev` 로 끝나는 브랜치의 커밋 |
| `claims` | `npx -y axmap-cli@latest audit --fetch` — 선점 없이 고친 것이 들어왔는지 | **모든 MR** |
| `verify:mr-target` | `npx -y axmap-cli@latest mr-target` — MR 이 한 칸씩 올라가는지 | **모든 MR.** 컨테이너를 띄우고 node 를 한 번 부르는 게 전부라 제일 먼저 끝난다 |
| `governance` | `npx -y axmap-cli@latest gate` — 정족수를 채웠는지 | **모든 MR** |
| `version` | 버전 태그 계산 · 생성 · push | 이름이 `main`·`func`·`dev` 로 끝나는 브랜치의 커밋. **MR 에서는 안 돈다** |
| `promote` | `node ci/axmap/tools/promote.mjs --step "$PROMOTE_STEP"` — 봇이 단계를 올린다 | **스케줄 파이프라인**(GitLab 이 정해진 시각에 스스로 돌리는 것)에서만. 6절 |

`.gitlab-ci.yml` 은 이 조건을 정규식 `/(^|\/)(main|func|dev)$/` 로 적는다 —
브랜치 이름 전체가 그 셋 중 하나거나, 슬래시 뒤 마지막 조각이 그 셋 중 하나면 걸린다.
`back/dev` 는 걸리고 `feat/S15P21E201-144-login` 은 안 걸린다.

`claims` 와 `governance` 에는 `GIT_DEPTH: 0` 이 붙어 있다. GitLab 은 기본으로
**얕은 클론**(최근 몇 커밋만 받아오는 것)을 하는데, 이 둘은 이력 전체나 갈림점이
있어야 판정할 수 있다. 얕으면 틀린 답을 자신 있게 낸다.

### `ci:vendor` — 사본이 손으로 바뀌지 않았는가

`ci/axmap/` 은 axMap 저장소에서 복사해 온 사본이고, 위 표의 잡들이 부르는 것이 전부
그 사본이다. 누가 사본을 직접 고치면 **팀 CI 의 동작이 조용히 갈라진다** — axMap
저장소에는 없는 코드가 팀 파이프라인에서 도는 상태가 된다.

이 잡은 `ci/axmap/manifest.sha256`(파일마다의 지문 목록)과 실제 파일을 대조한다.
지문이 어긋나면 빨개진다. 고치는 올바른 길은 [`CONTRIBUTING.md`](../CONTRIBUTING.md) 0.3 절에 있다 —
**axMap 저장소에서 고치고 벤더 명령을 다시 돌린다.**

> 🔴 **이 잡은 막지 못한다. 보이게 만들 뿐이다.** `manifest.sha256` 까지 다시 만들면
> 통과한다. 다만 그때는 `SOURCE.json` 과 `manifest.sha256` 이 diff 에 떠서 리뷰어가
> *"업스트림 커밋은 그대로인데 사본만 바뀌었다"* 를 본다.
> 거버넌스 잡과 같은 태도다 — 강제 장치가 아니라 **부인 불가능성 장치**다.

### `claims` — 선점 없이 고친 것이 들어왔는가

장부(`axmap/claims` **브랜치** — 폴더가 아니다)의 이력을 처음부터 재생하면서, 어느
시점에도 아무도 잡고 있지 않던 파일이 고쳐진 적이 있는지 본다.

> 🔴 **왜 이 잡이 필요한가.** 선점 강제는 지금까지 **각자 PC 의 커밋 훅**뿐이었다.
> setup 을 안 돌린 사람, `--no-verify` 를 쓴 사람, 웹 IDE 로 고친 사람에게는 아무
> 보호가 없다. 훅은 *"설치했는가"* 에 달려 있고, 한 사람이 안 하면 그날의 보호가
> 사라진다. **이 잡만은 설치 여부와 무관하다.**

### `verify:mr-target` — MR 은 한 칸씩만 올라간다

2026-08-26 에 붙었다. 기능 브랜치를 최상위 `main` 으로 바로 올리는 것 같은 **단계
건너뛰기를 막는다.**

| 소스 | 올릴 수 있는 대상 |
|---|---|
| `feat/…` `fix/…` 등 기능 브랜치 | `<파트>/dev` 하나뿐 |
| `<파트>/dev` | **같은 파트의** `<파트>/main` (= `<파트>/func`) |
| `<파트>/main` | 최상위 `main` |

거부되면 파이프라인이 빨개지고, 출력이 **어디로 올려야 하는지 함께 알려준다.**
코드를 고칠 일이 아니라 MR 의 대상 브랜치를 바꾸면 되는 일이다.

```bash
# 손으로 미리 확인
npx -y axmap-cli@latest mr-target --source front/dev --target back/main
# → 거부. "파트가 다릅니다 — front 에서 back 로 건너뛸 수 없습니다"
```

> 🔴 **왜 설정이 아니라 잡인가.** Community Edition 에는 *"이 브랜치로는 MR 을 못
> 연다"* 는 설정이 아예 없다. 있는 것은 기본 대상 브랜치를 정해 두는 것뿐이고,
> 그건 사람이 드롭다운에서 바꾸면 그만이다. 그래서 조건으로 만들었다.

> ⚠️ **`front/dev → back/main` 이 제일 미끄러운 자리다.** 둘 다 "dev 에서 파트
> 브랜치로" 라 규칙을 대충 짜면 통과한다. 그러면 프론트에서만 검토된 코드가 백엔드
> 파트의 릴리스 후보로 들어간다. 그 조합은 테스트로 고정해 뒀다.

## 5. 필수 파이프라인 — 그리고 켜는 순서

`Settings → Merge requests → Merge checks → Pipelines must succeed` —
**"MR 을 머지하려면 그 브랜치의 CI 검사가 전부 초록이어야 한다"** 는 설정이다.
켜 두면 검사가 빨간 동안은 **누구도** 머지 버튼을 못 누른다. Maintainer 도 마찬가지고,
이 규칙을 만든 사람도 예외가 아니다.

| | 보호 브랜치 권한 | 필수 파이프라인 |
|---|---|---|
| **막는 것** | **누가** 누르는가 | **무엇이** 통과했는가 |
| **Maintainer 에게** | 안 걸린다 (권한 가진 사람이 곧 예외) | **걸린다** |
| **바꾸려면** | 설정 화면 클릭 한 번 | `.gitlab-ci.yml` 수정 = MR 을 지나야 한다 |

권한은 **사람의 목록**이고 파이프라인은 **코드의 조건**이다. 목록은 가진 사람이 조용히
고칠 수 있고, 조건은 고치는 것이 기록에 남는다. 그래서 팀이 지키기로 한 것은 전부
잡으로 만든다.

### 이걸 켜면 지금 무엇이 걸리나

**잡을 하나 늘릴 때마다 이 설정이 강제하는 것도 함께 늘어난다.** 지금 붙어 있는 것:

| 걸리는 것 | 어느 잡이 |
|---|---|
| `ci/axmap/` 사본을 손으로 고친 MR | `ci:vendor` |
| 선점(claim) 없이 파일을 고친 MR | `claims` |
| 단계를 건너뛴 MR (`feat/… → main` 등) | `verify:mr-target` |
| 정족수(**통과에 필요한 최소 찬성 수**)를 못 채운 MR | `governance` |

**아직 안 걸리는 것:** 여행 서비스 파트(`frontend/` · `backend/`)의 코드가 실제로
빌드되고 테스트를 통과하는가. **그걸 보는 잡이 하나도 없다.** 각 파트가
`.gitlab-ci.yml` 에 자기 잡을 더하면 여기 줄이 는다.

**그리고 axMap 자체의 테스트는 여기서 안 걸린다** — axMap 은 별도 저장소에 있고
그쪽 CI 가 돌린다. 여기 있는 것은 사본뿐이라, 이 저장소가 보는 것은
*"사본이 손으로 안 바뀌었는가"*(`ci:vendor`) 하나다.

> 🔴 **그리고 MR 을 안 거치면 위의 어느 줄도 안 걸린다.** 2026-08-26 실측 기준
> 보호 브랜치는 `main` 하나뿐이라, `front/dev`·`back/dev`·`front/main`·`back/main`
> 에는 **누구나 MR 없이 직접 push 할 수 있다.** 위 표는 전부 MR 파이프라인에서만
> 도는 잡이다.

### 순서를 틀리면 팀 전체가 멈춘다

1. **러너 확인 / 등록** — 이게 안 되면 파이프라인이 `pending` 에서 안 움직인다
2. **MR 하나로 초록 확인** — 실제로 통과하는지 눈으로 본다
3. **`AXMAP_BOT_TOKEN` 설정** — 없어도 파이프라인은 돈다. 태그만 안 붙는다
4. **`Pipelines must succeed` 켜기** — 마지막이다

> 🔴 **마지막 단계를 첫 단계보다 먼저 켜면 아무도 머지를 못 한다.**
> 러너가 없으면 파이프라인이 영원히 `pending` 이고, pending 은 성공이 아니므로 머지
> 버튼이 잠긴다. 되돌리려면 설정을 다시 꺼야 하는데, 그 사이 팀 전원이 막힌다.

### 🔴 러너가 누군가의 노트북에 있으면 그 노트북이 꺼진 시간에는 아무도 머지를 못 한다

위와 같은 이유가 **매일 밤 반복되는** 형태다.

`Pipelines must succeed` 는 파이프라인이 초록일 때만 머지 버튼을 연다. 러너가 잡을
가져가지 못하면 파이프라인은 **실패가 아니라 `pending`** 이고, pending 은 초록이 아니다.
러너가 팀원 노트북에 깔려 있다면, 그 노트북이 켜져 있는 시간(예: 9시~18시) **밖에서는
머지가 막힌다.**

**이건 버그가 아니라 러너를 어디에 둘지의 결과다.** 고르는 것은 둘 중 하나다.

- **상시 켜져 있는 서버에 러너를 둔다** — 그룹·인스턴스 공유 러너가 있으면 이게 공짜로
  해결된다. 1절에서 그 둘을 먼저 확인하라고 한 이유가 이것이다
- **밤에는 머지가 필요 없다는 것을 팀이 받아들인다** — 받아들이는 것도 결정이다.
  다만 **말해 두지 않으면** 밤 11시에 막힌 사람이 CI 가 고장 난 줄 알고 설정을 끈다

> ✅ **2026-09-03 — 2대로 늘리고 실제로 껐다 켰다 확인했다** (S15P21E201-201·441).
>
> `ci/runner-up.sh` 한 줄(`AXMAP_RUNNER_TOKEN=glrt-xxxx bash ci/runner-up.sh`)로
> 이예승 로컬 PC에 두 번째 러너(id 2064)를 띄웠다. 등록 절차는 API로도 된다 —
> `POST /user/runners`(project_type, `run_untagged: true`)가 `Maintainer` 가 아닌
> Developer 권한으로도 됐다. 위 표의 "박재현" 담당은 낡았다 — 이제 아무나 할 수 있다.
>
> **검증**: 원래 러너(2037)를 API로 잠깐 멈추고(`paused: true`) `common/dev`에
> 파이프라인을 하나 새로 띄웠더니, `claims`·`version`·`jira` 세 잡이 전부 2064로만
> 배정돼 pending 없이 끝까지 성공했다. 2037을 다시 켠 뒤 정상 복귀 확인.
>
> ✅ **같은 날, 세 번째 러너를 EC2 백업 서버(`j15e201a.p.ssafy.io`)에 올려서
> "상시 켜져 있는 서버" 쪽도 채웠다** (id 2065, `axmap-runner-j15e201a-backup`).
> 절차는 위와 같다 — `ci/runner-up.sh` 그대로, Docker만 새로 설치
> (`sudo apt install docker.io`).
>
> **더 강한 검증**: 2037·2064(노트북 둘)를 **동시에** 멈추고 `common/dev`에
> 파이프라인을 새로 띄웠더니, `claims`·`version`·`jira` 세 잡 전부 **2065(EC2)
> 단독으로** pending 없이 성공했다. 즉 이제 노트북이 **둘 다** 꺼져도 CI가 안 멈춘다.
>
> 지금 상태: 2037(위치 미상) · 2064(이예승 로컬) · 2065(j15e201a, 상시 가동) —
> 3대. 셋 중 상시 가동은 2065 하나뿐이라, 나머지 둘이 다 꺼져도 안전망은 있지만
> **평상시 CI 속도**는 노트북들이 켜져 있을 때 더 빠르다(잡이 여러 러너로 분산).
>
> 🔴 **정정 (같은 날) — 2064는 제거했다.** 개인 작업용 PC가 켜져 있을 때마다
> 팀원 아무나 올린 코드의 Docker 빌드·테스트가 그 PC에서 조용히 도는 것이
> (예상 못 한 리소스 소모·디스크 점유) 상시 가동 러너(2065)를 확보한 뒤로는
> 이득보다 부담이 컸다. `docker rm -f gitlab-runner` + GitLab에서 러너 삭제
> (`DELETE /runners/2064`)로 정리했다. **최종 상태: 2037 · 2065 두 대.**
