# Jira 협업 규칙

## 1. 기본 원칙

- 코드를 변경하기 전에 Jira 이슈를 만든다.
- Task는 가능하면 1~2일 안에 완료할 크기로 나눈다.
- 모든 이슈에는 담당자, 작업 목적, 작업 항목, 완료 기준을 적는다.
- Jira의 실제 계층 설정을 확인한 뒤 Epic, Story, Task 관계를 적용한다.

## 2. 이슈 유형

- `Epic`: 5주 동안 관리할 큰 기능 또는 목표
- `Story`: 사용자가 이용하는 기능 단위
- `Task`: 구현, 설정, 문서화처럼 담당자가 수행할 작업 단위
- `Bug`: 기대 동작과 실제 동작이 다른 결함

## 3. 제목

```text
[Type][Scope] 작업 내용
```

예시:

```text
[Feat][Front] 여행 검색 화면 구현
[Feat][Back] 여행지 검색 API 구현
[Chore][Infra] Jenkins 배포 파이프라인 구성
[Docs][Common] Git 협업 규칙 작성
```

## 4. 본문

```markdown
## 목적
- 이 작업이 필요한 이유

## 작업 내용
- 구체적인 작업 목록

## 완료 기준
- 테스트 또는 화면에서 확인할 수 있는 조건
```

`구현 완료`처럼 검증할 수 없는 표현만 적지 않는다.

## 5. 상태 변경

```text
해야 할 일 → 진행 중 → 리뷰 중 → 완료
```

- 브랜치를 만들 때 `진행 중`으로 변경한다.
- MR을 생성하면 `리뷰 중`으로 변경한다.
- MR 병합과 완료 기준 확인이 끝나면 `완료`로 변경한다.
- MR이 열렸다는 이유만으로 완료 처리하지 않는다.

## 6. 최초 이슈 권장안

```text
[Chore][Common] 프로젝트 초기 구조 및 협업 규칙 구성
```

완료 기준:

- `backend/`, `frontend/`, `docs/` 기본 구조가 저장소에 존재한다.
- Git, Jira, MR 규칙 문서가 작성되어 있다.
- `main`과 파트별 `main`, `dev` 브랜치가 생성되어 있다.
- 보호 브랜치의 직접 push와 force push가 제한되어 있다.
