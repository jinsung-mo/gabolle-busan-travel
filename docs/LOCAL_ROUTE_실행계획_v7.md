## 0. 왜 v6 계획서를 갈랐나 — 세 줄

1. v6 계획서는 **"이미 돌아가는 Node 코드가 절반 넘게 있다"** 는 전제 위에 세워졌다.
2. 그 뒤 팀이 **백엔드는 Spring, 프론트는 처음부터** 로 정했다. 그래서 그 전제가 사라졌다.
3. **기능·화면 설계는 스택과 무관하므로 그대로 살리고**, 스택에 매달린 실행 규격만 이 문서로 옮겨 다시 썼다.

즉 v6 이 **틀려서** 가른 것이 아니다. v6 이 쓰인 뒤에 **전제가 바뀌어서** 가른 것이다.

### 2.2 왜 Node 가 아니라 Spring 인가

이유가 셋이고, **셋 다 코드의 성질이 아니라 팀의 성질이다.** 그래서 기술 비교표로는 안 나온다.

| | |
| --- | --- |
| **사람** | **모진성 님이 Node.js 를 못 쓴다.** 6명 중 한 명이 첫날부터 못 들어오는 스택은 고를 수 없다. 6인 팀에서 한 명이 놀면 손실은 6분의 1이 아니라, 그 사람 몫을 나머지가 나눠 지느라 **전원이 느려지는 것**이다 |
| **취업** | Spring 이 취업 관점에서 훨씬 잘 쓰인다. 프로젝트가 끝난 뒤에도 남는 이득이라, **같은 값이면 이쪽이 맞다** |
| **속도** | **우리가 이미 익숙하다.** 마감이 있는 판에서 배우면서 만드는 것은 두 배로 비싸다 — 만드는 시간에 배우는 시간이 더해지고, 배우면서 만든 코드는 나중에 다시 만진다 |

그리고 저장소가 **이미 그렇게 선언돼 있었다.** `backend/README.md` 가 2026-08-25 부터
"Spring Boot + Gradle · Java 18 · MySQL" 이라고 적고 있다. 새로 정한 것이 아니라
**원래 자리로 돌아온 것**에 가깝다.

> **참고 코드가 Node 인 것은 문제가 아니다.** `ref/local-route` 는 **"이런 화면과
> 이런 API 가 필요하다"를 이미 한 번 만들어 본 견본**이다. 견본이 Node 로 쓰였다고
> 우리가 Node 를 써야 하는 것은 아니다. 견본에서 가져오는 것은 **문법이 아니라 설계**다.

### 2.3 Java 버전 — 17 [실측 · 2026-09-04, S15P21E201-388]

> 🔴 **이 절이 한동안 "아직 정해야 한다 [미정]" 으로 적혀 있었다.** 그 사이 백엔드
> 첫 커밋이 이미 여러 번 들어갔고(back/dev), 아래에 적힌 권장(Java 21)과는 **다른
> 값(17)이 코드로 먼저 굳어 있었다.** 사람이 이 문서에서 골라 정한 것이 아니라,
> 실제로 쓰인 값을 뒤늦게 이 문서에 반영하는 것이다 — 지어내지 않고 실측한다.

| | |
| --- | --- |
| Java 18 (`backend/README.md`) | 자리표시 값이었다. 실제로 쓰이지 않는다 |
| Java 21 | 이 문서가 원래 권장했던 값. **채택되지 않았다** |
| **실제 — Java 17** | `backend/build.gradle`의 toolchain(`JavaLanguageVersion.of(17)`)과 `backend/Dockerfile`(`eclipse-temurin:17-jdk`/`17-jre`)이 실제로 쓰는 값. **17도 LTS다** — 21보다 한 주기 이른 LTS를 골랐다는 차이지, LTS가 아닌 값으로 간 것은 아니다 |

**쓰이는 자리**: `backend/build.gradle`(toolchain), `backend/Dockerfile`(멀티스테이지
빌드·런타임 이미지 둘 다), `backend/Jenkinsfile`이 그 Dockerfile로 이미지를 빌드하므로
간접적으로 CI/배포 환경도 17을 따른다. 팀원 로컬 환경도 17로 맞춰야 `./gradlew` 빌드가
동일하게 재현된다.

> **21로 왜 안 갔는지는 기록에 없다.** 결정 마감(백엔드 첫 커밋 전)을 지나 코드로
> 먼저 정해졌기 때문이다. 굳이 21로 바꿀 이유가 새로 생기지 않는 한, 지금은 이
> 실측값을 그대로 인정하고 넘어간다 — 바꾸면 Gradle 설정·CI 이미지·팀원 로컬
> 환경을 전부 다시 맞춰야 하는 비용은 여전히 유효하다.

### 2.4 앱 — Expo 로 간다 [확인함 · 2026-08-27]

**왜 이걸 따로 조사했나.** Expo 에는 오래된 평판이 하나 있다 —
*"쓰기는 편한데 네이티브 기능이 필요해지면 결국 걷어내야 한다"*.

우리 앱은 지도·카메라·음성·위치를 **전부** 쓴다. 그 평판이 지금도 맞다면
**Expo 는 초반만 빠르고 후반에 일정을 통째로 날린다.** 그래서 확인이 필요했다.

**용어부터.**

| 말 | 뜻 |
| --- | --- |
| **React Native** | 자바스크립트로 안드로이드·iOS 앱을 만드는 틀 |
| **Expo** | 그 위에 얹은 도구 묶음. 카메라·위치·알림 같은 것을 미리 싸 놓아 설정 없이 쓰게 해 준다 |
| **bare(맨몸) React Native** | Expo 없이 React Native 만 쓰는 것. 안드로이드·iOS 네이티브 프로젝트를 직접 관리한다 |
| **eject(걷어내기)** | Expo 로 시작했다가 Expo 를 벗겨 내고 bare 로 옮기는 것. **한 번 하면 되돌리기 어렵다** |
| **EAS** | Expo Application Services. **맥북 없이도 iOS 빌드를 만들어 주는 서비스** |

**조사 결과 — 그 평판은 이제 틀렸다.**

| 확인한 것 | 내용 |
| --- | --- |
| **CNG** (Continuous Native Generation) | 네이티브 프로젝트를 **설정 파일에서 그때그때 만들어 내는 방식.** 그래서 Expo 가 안 싸 주는 네이티브 모듈도 **걷어내지 않고 그대로 붙일 수 있다** |
| **config plugin** (설정 플러그인) | 네이티브 설정을 코드로 적어 두는 자리. 남이 만든 것을 가져다 쓰거나 직접 쓸 수 있다 |
| **Expo Modules API** | **Swift·Kotlin 코드를 Expo 프로젝트 안에서 직접 쓸 수 있다.** 걷어내지 않아도 된다 |
| 업계 정리 | 2026 기준 글들이 공통으로 *"'네이티브가 필요하면 bare 로 가라'는 예전 판단 기준은 더 이상 적용되지 않는다"* 고 말한다 |

**→ Expo 로 간다.** 결정적인 이유 하나를 덧붙이면, **EAS 가 맥북 없이 iOS 빌드를
만들어 준다.** 팀에 맥북이 몇 대인지가 곧 일정이 되는 구조를 피할 수 있다.

> 🔴 **다만 이건 일반론이고, 우리 요구로 직접 돌려본 것이 아니다.** 아래 둘은
> **[미정]** 으로 두고 실기기에서 확인한 뒤 이 표기를 `[돌려봄]` 으로 바꾼다.
>
> | 확인할 것 | 왜 |
> |---|---|
> | **카카오맵 네이티브 SDK** 가 Expo 설정 플러그인으로 붙는가 | 국내 지도가 핵심 기능이다. 구글맵으로 대체하면 서비스 정의가 흔들린다 |
> | **한국어 음성 인식(STT)** 이 양 OS 에서 되는가 | 음성 통역이 핵심 기능이다. iOS 에서만 안 되는 일이 잦다 |
>
> 확인 전까지는 문서 어디에도 "된다" 고 적지 않는다.

> 그 값들은 **버릴 데모 UI 에서 뽑은 것**이다. 무엇으로 정하든 값의 주인은
> 디자인 시스템이 된다. **값을 적어 두면 정하는 순간 문서가 통째로 낡는다.**

### 3.1 [실측] 지금 세 가지가 동시에 돌고 있다

브랜치 규칙을 문서에서 베끼지 않고 **저장소를 직접 열어 확인했다.** 결과는 이랬다.

| 어디에 적혀 있나 | 모양 | 예 |
| --- | --- | --- |
| `docs/git-convention.md` | `{종류}/{파트}/{Jira키}-{설명}` | `feature/front/S15P21E201-123-search-page` |
| 루트 `CONTRIBUTING.md` 2절 | `{종류}/{Jira키}-{설명}` — **파트 칸이 없다** | `feat/S15P21E201-144-login` |
| `LOCAL_ROUTE_…계획서_v6.md` 1.3절 | `feature/{역할}-{기능}` — **Jira 키가 없다** | `feature/ai-ocr-pipeline` |

그리고 **실제 브랜치도 섞여 있다.**

docs/common/S15P21E201-32-design-system      ← 세 칸 (종류/파트/키-설명)

### 3.2 정하는 것 — 세 칸으로 통일한다

```
{종류}/{파트}/{Jira키}-{짧은설명}
```

```
feat/back/S15P21E201-140-trip-generate-api
feat/front/S15P21E201-141-trip-schedule-screen
feat/ml/S15P21E201-142-route-optimizer-bridge
fix/front/S15P21E201-143-date-picker-range
docs/common/S15P21E201-144-execution-plan-v7
chore/common/S15P21E201-145-gradle-ci
```

**가운데 칸은 파트 이름이다.** 프론트면 `front`, 백엔드면 `back`, 머신러닝이면 `ml`.

> 🔴 **가운데 칸에 `feat` 이라는 글자를 넣는 것이 아니다.** 사다리를 `main → feat → dev`
> 라고 부를 때의 그 `feat` 은 **"파트 단계"를 가리키는 자리 이름**이지 브랜치에
> 그대로 쓰는 글자가 아니다. 실제 브랜치는 `front/main` · `back/main` · `ml/main` 이다.
>
> 🔴 **역할 이름을 넣는 것도 아니다.** v6 계획서의 `feature/ai-…` `feature/db-…`
> `feature/infra-…` 는 **역할(누가)** 을 넣은 것인데, 여기 들어갈 것은
> **파트(어느 코드 트리)** 다. 역할은 여섯이고 파트는 넷이라 대응이 1:1 이 아니다 (5.4절).

### 3.3 파트 이름 [일부 미정]

| 파트 | 무엇을 담나 | 브랜치 | 상태 |
| --- | --- | --- | --- |
| `front` | `frontend/` — 웹 화면 | `front/main` · `front/dev` | 원격에 있다 |
| `back` | `backend/` — Spring 서버 | `back/main` · `back/dev` | 원격에 있다 |
| `common` | 루트 문서 · CI · 공용 설정 | `common/dev` **만** | 🔴 **`common/main` 이 없다** — 아래 |
| **`ml`** | 최적화 엔진 · 데이터 분석 | **[미정]** | 아래 |

> 🔴 **2026-08-27 정정 — `common/main` 이 원격에 없다. 앞의 [실측] 표기가 틀렸다.**
>
> `git ls-remote --heads origin` 에 `front/main` · `back/main` 은 있는데 `common/main` 만 없다.
> 예전에는 있었다 — 커밋 `191f42a`(`Merge branch 'common/main' into 'main'`)가 그 흔적이고,
> 한 번 쓰이고 지워졌다.
>
> **이게 왜 문제인가.** 판정 코드(`ci/axmap/src/mrtarget.mjs` 의 `checkTarget`)는
> `<파트>/dev` 를 **같은 파트의 파트 브랜치로만** 보낸다. `common/dev → main` 은
> `dev-must-target-part` 로 거부된다. 즉 **지금 `common/dev` 에 있는 이 문서들이
> `main` 까지 올라갈 길이 없다.** 사다리의 가운데 칸이 비어 있다.
>
> **그런데 정말 만들어야 하는지는 따로 정할 일이다.** `common` 은 제품 파트가 아니라
> 문서·CI·공용 설정 자리인데, `ci/axmap/src/version.mjs` 의 `levelOf` 는 이름의 마지막 칸만
> 보므로 `common/main` 을 **파트 브랜치(minor)** 로 판정한다. 문서만 고쳐도 제품의
> minor 버전이 오른다는 뜻이다. **[미정] 로 남긴다 — 10.1절 목록에 넣었다.**
>
> 🔴 **`ml` 과 `bigData` 가 같은 것인지 정해야 한다.** 원격에는 이미 `bigData/main` ·
> `bigData/dev` 가 있고 거기서 실제 작업이 돌고 있다(버스 실시간 수집·경사 계산·현장 실험).
> 그런데 팀이 부르는 파트 이름은 `ml` 이다.
>
> | 안 | 뜻 | 대가 |
> |---|---|---|
> | **A** | `bigData` 를 `ml` 로 **이름만 바꾼다** | 지금은 브랜치 둘을 다시 만들면 끝난다. **커밋이 쌓일수록 비싸진다** |
> | **B** | `bigData` 와 `ml` 을 **다른 파트로 둔다** | 파트가 다섯이 된다. 무엇이 어느 쪽인지 매번 판단해야 한다 |
> | **C** | `bigData` 를 그대로 쓰고 `ml` 이라는 말을 안 쓴다 | 문서와 대화가 어긋난다 |
>
> **결정 마감: 이번 주.** 파트 이름은 브랜치·CI·문서에 동시에 박히므로 **늦게 바꿀수록 비싸다.**

### 3.4 사다리 — 한 칸씩만 올라간다

```
main                          ← 최상위. 여기가 종점이다
 └── <파트>/main              ← 파트 단계. "feat 단계" 라고 부르는 그 자리
      └── <파트>/dev          ← 파트 개발
           └── 작업 브랜치     ← feat/back/S15P21E201-140-…
```

| 소스 | 올릴 수 있는 대상 |
| --- | --- |
| 작업 브랜치 (`feat/…` `fix/…` 등) | **`<파트>/dev` 하나뿐** |
| `<파트>/dev` | 같은 파트의 `<파트>/main` |
| `<파트>/main` | 최상위 `main` |
| `hotfix/…` | `<파트>/dev`, **또는 `main` 자체가 고장 났을 때만 `main` 으로 바로** |

**이건 약속이 아니라 검사다.** `.gitlab-ci.yml` 의 `verify:mr-target` 잡(job — 파이프라인이
돌리는 작업 하나)이 실제로 막는다. 손으로 먼저 확인할 수 있다.

```bash
node ci/axmap/tools/mr-target.mjs --source feat/back/S15P21E201-140-trip-api --target main
# → 거부. 이 브랜치가 갈 수 있는 곳을 함께 알려준다
```

### 3.5 🔴 이름 규칙은 지금 **아무도 강제하지 않는다** [실측]

이게 이 절에서 제일 중요하다. 판정 코드(`ci/axmap/src/mrtarget.mjs`)를 직접 읽어 보면,
**브랜치 이름을 전혀 보지 않는다.** 보는 것은 딱 하나다 — 브랜치 이름의 **마지막 칸**이
`main` 이냐 `func` 이냐 `dev` 냐, 아니면 그 밖이냐.

그래서 `feat/S15P21E201-9-…` 도 `feature/ai-ocr-pipeline` 도 `asdf` 도
**전부 똑같이 "작업 브랜치"로 통과한다.**

**즉 지금 이름 규칙은 코드가 지키는 규칙이 아니라 아무도 안 지켜도 되는 관습이다.**
그래서 세 가지가 동시에 돌게 됐다. 관습은 사람이 늘면 반드시 갈라진다.

**대응 — 잡을 하나 만든다 [제안].**

루트 `CONTRIBUTING.md` 3절이 말하는 그대로다. *"팀이 지키기로 한 것은 전부 CI 잡으로 만든다.
권한은 사람의 목록이고 파이프라인은 코드의 조건이다."* 이름 규칙도 예외가 아니다.

```
verify:branch-name  (신설 제안)
  · 작업 브랜치가 {종류}/{파트}/{Jira키}-{설명} 모양인가
  · 종류가 허용 목록에 있는가
  · 파트가 존재하는 파트인가
  · Jira 키가 S15P21E201-<숫자> 모양인가
  → 어긋나면 거부하고, 올바른 모양을 예시와 함께 출력한다
```

> **거부할 때 갈 곳을 함께 말한다.** 이 저장소의 관례다 — 선점이 거부할 때 점유자·작업·
> 남은 시간을 함께 주고, MR 대상 검사가 거부할 때 갈 수 있는 곳을 함께 준다.
> **이유 없는 거부는 같은 요청을 다시 보내게 만든다.**

**담당·마감: [미정] — 4장 리뷰 규칙과 함께 정한다.**

## 4. 리뷰 — 지금은 1명, 나중에 2명

### 4.1 무엇이 문제인가

`docs/git-convention.md` 5절은 **"최소 1명의 승인"** 이라고 적고 있다.
지금 사람이 적을 때는 이게 맞다. 그런데 **6명이 다 붙으면 1명 승인은 약해진다.**

이유는 숫자가 아니라 **쌓이는 것**에 있다. 한 명이 보고 통과시키면
**"왜 이렇게 만들었는가"가 그 한 명의 머릿속에만 남는다.** 그 사람이 시험 기간이거나
다른 파트에 붙어 있으면, 그 판단은 팀에서 사라진다.

### 4.2 정하는 것 — 인원을 방아쇠로 삼는다

| 단계 | 조건 | 파트 `dev` 로 가는 MR |
| --- | --- | --- |
| **지금** | `governance/policy.json` 의 투표권자가 **5명 미만** | **승인 1명** |
| **전환** | 투표권자가 **5명 이상**이 되는 날 | **승인 2명** |
| 상시 | — | 작성자는 자기 MR 을 승인하지 않는다 |

> **왜 지금 바로 2명이 아닌가.** 지금은 저장소에 커밋이 있는 사람이 적고 그중 둘이
> Maintainer(저장소 관리자)다. 지금 2명을 요구하면 **모든 MR 에 Maintainer 둘이
> 항상 붙어야 한다.** 그러면 규칙이 품질을 지키는 게 아니라 **줄을 만든다.**
> 줄이 길어지면 사람은 규칙을 우회하고, **우회는 흔적이 안 남는다.**
>
> 그래서 **사람 수를 방아쇠로 건다.** 날짜가 아니라 조건이라 저절로 전환된다.
>
> 🔴 **여기 사람 수를 적지 않고 파일을 가리키는 이유** — 명단이 지금 실제로 늘고 있다.
> 문서에 숫자를 박으면 **그 줄이 하루 만에 낡는다.** `governance/policy.json` 의
> `voters` 를 세는 것이 언제나 맞는 답이다.

### 4.3 "이유를 쌓는다" — 무슨 뜻인가

승인 버튼만 누르면 **아무것도 안 남는다.** 남는 것은 "통과됨" 이라는 사실뿐이고,
그건 석 달 뒤에 아무 도움이 안 된다.

**승인 코멘트에 한 줄을 적는다.** 형식은 하나면 충분하다.

```
승인 — 무엇을 보고 승인하는가 / 무엇을 안 봤는가
```

```
승인 — 일정 생성 API 의 시간창 제약이 기존 견본과 같은 결과를 내는지 확인.
      성능은 안 봤음 (동시 요청 미검증)

승인 — 화면만 확인. 서버 계약은 백엔드 담당이 봐야 함
```

**"무엇을 안 봤는가"가 더 중요하다.** 두 명이 승인했는데 **둘 다 화면만 봤다면
서버는 아무도 안 본 것**이다. 그 사실이 적혀 있어야 다음 사람이 안다.

**모으는 자리 [제안].** 승인 코멘트는 MR 이 닫히면 찾기 어려워진다.
설계 판단이 갈렸던 것만 골라 `docs/` 아래 한 파일에 모은다. 전부 옮기지 않는다 —
**전부 옮기면 아무도 안 읽는다.**

### 4.4 🔴 리뷰 승인과 정족수는 다른 것이다

이 둘이 자주 헷갈린다. **막는 지점이 다르다.**

| | 리뷰 승인 | 정족수 (`governance` 잡) |
| --- | --- | --- |
| 무엇인가 | GitLab 화면의 **Approve 버튼** | `governance/policy.json` 이 세는 **표** |
| 어디에 걸리나 | 모든 MR | **최상위 `main` 으로 가는 MR**, 그리고 `governance` · `.gitlab-ci.yml` · `ci` 경로를 바꾸는 MR |
| 지금 값 | 1명 | **2표** |
| 바꾸려면 | 문서·GitLab 설정 | `governance/policy.json` 을 고치는 MR — **그 MR 자체가 2표를 받아야 한다** |

즉 **파트 `dev` 로 가는 일상 MR 에는 정족수가 안 걸린다.** 4.2절이 정하는 것은
그 일상 MR 의 승인 수다. 둘은 서로를 대체하지 않는다.

> 🔴 **투표권자 명단이 아직 다 안 찼다.** 저장소에 커밋이 없는 사람은 **이메일을
> 확인할 수 없어서** 명단에 못 넣는다. 투표는 **커밋 저자 이메일 완전일치**로만
> 집계되므로(`ci/axmap/src/governance.mjs`), **지어낸 이메일을 넣으면 그 사람은
> 영영 한 표도 못 던진다.** 첫 커밋이 들어오는 대로 추가한다.
>
> 🔴 **그리고 "팀 명단에 적힌 이메일"과 "git 이 실제로 찍는 이메일"이 다를 수 있다.**
> 실제로 한 번 그랬다 — 명단에 알려진 주소와 커밋에 찍힌 주소가 달라서,
> 명단 쪽으로 "고쳤다면" 그 사람이 투표를 못 하게 될 뻔했다.
> **바꾸려면 본인의 새 커밋에서 그 이메일이 실제로 찍히는지를 먼저 확인한다.**
> 이 규칙은 `governance/policy.json` 안에도 주석으로 적혀 있다.

## 5. 6인 역할 — 소유가 아니라 첫 순번이다

### 5.1 역할

v6 계획서의 여섯 역할을 그대로 쓴다. **바뀐 것은 스택뿐이다.**

| 코드 | 역할 | 한 문장 | 주 기술 | 백업 |
| :-: | --- | --- | --- | :-: |
| **BE** | 백엔드 코어 API | 서버 계약과 도메인 로직을 책임진다 | Spring Boot · JPA · MySQL | ML |
| **ML** | 최적화·데이터 | 일정을 계산하는 엔진과 데이터 파이프라인을 책임진다 | Python · OR-Tools | BE |
| **DB** | 데이터 · 스키마 | 데이터가 정확하고 **채워져 있게** 한다 | MySQL · JPA · Redis | INFRA |
| **FE** | 웹 프론트엔드 | 웹 화면과 반응형, 디자인 규격을 책임진다 | React · TypeScript (디자인 시스템 [미정] — 2.6) | APP |
| **APP** | 모바일 앱 | Expo 앱과 네이티브 기능, 스토어 빌드를 책임진다 | React Native · Expo · EAS | FE |
| **INFRA** | 인프라 · 배포 · QA | 코드가 사용자에게 도달하는 모든 경로를 책임진다 | Docker · Nginx · GitLab CI | BE |

**담당자 배정: [미정].** 세 분이 아직 저장소에 안 들어와 있어 이름을 못 박지 않는다.
**이름을 지어내지 않는다** — 지어낸 배정은 배정이 아니라 오해다.

### 5.2 🔴 역할이 벽이 되면 기간을 못 지킨다

이 문서에서 제일 중요한 절이다.

역할을 나누는 목적은 **"누구에게 물어볼지"를 분명히 하는 것**이지
**"내 것만 하는 것"이 아니다.** 그런데 역할표를 주면 사람은 자연스럽게 뒤쪽으로 읽는다.
*"나는 FE 니까 서버는 안 건드린다."*

**그러면 기간 안에 못 끝낸다.** 이유는 단순하다.

기능 하나는 **세로로** 되어 있다 — 화면 하나에 API 하나에 테이블 하나. 그런데
역할은 **가로로** 나뉘어 있다 — 화면은 FE, API 는 BE, 테이블은 DB.
**세로로 된 일을 가로로 나누면 기능 하나에 인계가 세 번 생긴다.**

인계 한 번은 반나절이다. 기다리는 쪽은 그동안 논다. 기능이 열 개면 인계가 서른 번이다.

**그래서 이렇게 한다.**

| | |
| --- | --- |
| ❌ | "FE 는 화면만, BE 는 API 만" |
| ✅ | **"기능 하나를 한 사람이 화면–API–테이블까지 세로로 끝까지 끌고 간다."** 역할은 **그 사람이 막혔을 때 물어볼 사람**이다 |

**역할이 하는 일은 셋이다.**

1. **그 영역의 첫 순번이다.** 새 일이 생기면 그 사람에게 먼저 간다
2. **그 영역의 판단을 책임진다.** 남이 그 영역을 건드리면 **리뷰어로 들어간다**
3. **그 영역의 규격을 정한다.** 남이 따를 것을 만든다

**역할이 안 하는 일은 하나다 — 그 영역을 독점하지 않는다.**

### 5.3 막혔을 때 — 30분 규칙

> **혼자 30분 넘게 막혀 있으면 담당자에게 넘긴다.** 반나절 붙잡고 있는 것이
> 6인 팀에서 가장 비싼 낭비다.

이 저장소에는 그걸 위한 도구가 이미 있다.

```
ax_send   — 담당자에게 쪽지. 커밋도 MR 도 필요 없다. 즉시 간다
ax_inbox  — 나에게 온 쪽지를 읽는다
ax_status — 지금 누가 어디를 잡고 있나
```

**쪽지는 요청하지 않아도 알려준다.** 나에게 온 쪽지가 있으면 아무 axMap 도구를 불러도
결과 끝에 뜬다. 그래서 **"물어봤는데 답이 없다"가 "못 봤다"인지 "안 된다는 뜻"인지
헷갈리지 않는다.**

**쪽지에 적을 것은 셋이다.**

1. **무엇을 하려다 막혔나** (내 의도)
2. **무엇을 시도했나** (같은 걸 다시 시켜서 시간 낭비하지 않게)
3. **네가 답해 주면 나는 무엇을 할 수 있나** (급한지 아닌지가 여기서 갈린다)

### 5.4 파트 ↔ 역할 대응 — 1:1 이 아니다

브랜치의 파트 칸(3.3절)과 역할(5.1절)은 **개수가 다르다.** 역할은 여섯, 파트는 넷이다.

| 역할 | 주로 쓰는 파트 |
| :-: | --- |
| FE | `front` |
| APP | `front` (앱 코드가 어디 살지는 [미정] — 5.6절) |
| BE | `back` |
| DB | `back` (JPA 엔티티·마이그레이션이 백엔드 코드다) |
| ML | `ml` |
| INFRA | `common` (CI·배포 설정), 파트별 설정은 그 파트 |

> **한 사람이 여러 파트를 오간다.** 그건 정상이다. **파트는 코드가 사는 곳이고
> 역할은 사람이 책임지는 것**이라 애초에 다른 축이다.

### 5.5 일하는 방식 — 기능 단위로 붙는다 **[제안 · 확정 아님]**

> 🔴 **이 절은 확정된 규칙이 아니다.** 팀에서 나온 안을 적어 둔 것이고,
> 스크럼에서 한 번 이야기한 뒤에 정한다. **"이런 안이 있다"까지가 이 절의 지위다.**

#### 무엇이 문제인가 — 일자별 계획은 안 지켜진다

v6 계획서는 **날짜마다 6인 각자의 과업과 완료 기준**을 다 적어 뒀다.
문서로는 훌륭한데, **실제로는 지키기 어렵다.** 이유가 셋이다.

| | |
| --- | --- |
| **하나가 밀리면 뒤가 다 밀린다** | 계획이 촘촘할수록 그렇다. 그리고 **다시 짜는 데 또 하루가 든다** |
| **계획을 지키는 것이 목표가 된다** | 그러면 막혔을 때 말을 안 하게 된다. *"오늘 것만 끝내면 되는데"* 하면서 혼자 붙잡는다. **6인 팀에서 가장 비싼 낭비가 그거다** |
| **누가 무엇을 하는지가 문서에 있다** | 문서는 어제 것이다. **지금 누가 무엇을 잡고 있는지는 문서가 모른다** |

#### 대안 — 계획을 문서가 아니라 그날 아침에 만든다

```
1. 사람이 [기능] 단위로 붙는다      ← 화면–API–테이블을 한 줄기로 (5.2절)
2. 그날 아침 스크럼에서
   각자 "오늘 무엇을 붙잡는다" 를 말한다
3. 말한 것을 그 자리에서 ax_claim 한다   ← 겹치면 여기서 터진다
4. 막히면 ax_send 로 담당자에게 넘긴다   ← 30분 규칙 (5.3절)
```

**문서에 미리 적어 두는 것은 "무엇을 만드나"(기능 목록)까지고,
"오늘 누가 무엇을"은 그날 아침에 정한다.**

#### 겹침은 사람이 아니라 도구가 막는다

일자별 계획이 하려던 일 중 하나가 **"두 사람이 같은 파일을 건드리지 않게 하는 것"** 이었다.
그건 이제 도구가 한다.

| | |
| --- | --- |
| `ax_claim` | 고칠 파일을 **미리 선언**한다. 겹치면 **그 자리에서 거부**되고, **누가 무엇을 왜 잡고 있는지**와 남은 시간이 함께 온다 |
| `ax_status` | 지금 누가 어디를 잡고 있나 |
| `ax_release` | 끝나면 즉시 반납 |

**그래서 조율표를 사람이 만들 필요가 없다.** 거부당하면 **비어 있는 다른 기능으로 간다.**
같은 요청을 다시 보내지 않는다 — 몇 번을 보내도 같은 답이 온다.

#### 🟢 그리고 이제 컨텍스트를 넘길 수 있다

이 안이 지금 가능해진 이유가 여기 있다. **쪽지가 실제로 돈다.**

```
ax_send   — 담당자에게 즉시. 커밋도 MR 도 필요 없다
ax_inbox  — 나에게 온 것을 읽는다
```

**요청하지 않아도 알려준다.** 나에게 온 쪽지가 있으면 아무 axMap 도구를 불러도
결과 끝에 뜬다.

이게 왜 중요한가. **예전에는 "막혔다"를 넘기는 비용이 컸다.** 말로 설명하면
맥락이 반쯤 빠지고, 문서로 쓰면 쓰는 데 시간이 든다. 그래서 사람은 그냥 혼자 붙잡는다.
**쪽지는 그 비용을 낮춘다** — 내가 무엇을 하려다 무엇을 시도했고 어디서 막혔는지를
그대로 넘기면, 받는 사람이 **같은 것을 다시 시도하지 않는다.**

#### 이 안이 노리는 것 — **FE 가 BE 를 기다리지 않는다**

역할대로 가로로 나누면 이렇게 된다.

```
FE: 화면 만듦 → API 기다림 → 기다림 → 기다림 → 붙임
BE: 다른 것 하는 중 ────────→ API 만듦 →
```

**기다리는 시간이 곧 손실이다.** 기능 단위로 세로로 붙으면 그 줄이 없어진다.

```
사람 A: [일정 생성] 화면–API–테이블 끝까지  ← 막히면 그때 BE 담당에게 쪽지
사람 B: [장소 상세] 화면–API–테이블 끝까지
```

**"내 기능의 API 는 내가 만든다. 막히면 담당자에게 넘긴다."**
그러면 **기능이 무엇이든 일정 한도 안에서 각자 최대로 나아간다.**

#### 🔴 이 안이 잘 안 될 수 있는 자리 — 미리 적어 둔다

**좋은 점만 적으면 그건 제안이 아니라 광고다.** 확인해야 할 것 셋.

| 위험 | 왜 생기나 | 대비 |
| --- | --- | --- |
| **아무도 안 잡는 기능이 남는다** | 각자 잡고 싶은 것을 잡으면 어려운 것이 마지막까지 남는다 | **남은 기능 목록이 한 곳에 보여야 한다.** Jira 백로그가 그 자리다. 스크럼에서 "안 잡힌 것" 을 먼저 본다 |
| **코드 모양이 갈린다** | 여섯이 각자 세로로 끌고 가면 서버 코드 스타일이 여섯 가지가 된다 | **리뷰가 그걸 잡는다** (4장). 그리고 **처음 두세 기능은 같이 만들어 본보기를 세운다** |
| **말한 것과 잡은 것이 다르다** | 스크럼에서 말하고 claim 을 안 하면 겹침이 다시 사람 몫이 된다 | **말한 자리에서 바로 claim 한다.** 말과 선언이 같은 행동이 되게 한다 |

> **판정 방법.** 이 방식이 되는지 안 되는지는 **일주일 돌려 보면 안다.**
> 볼 것은 하나다 — **"누가 무엇을 기다리며 논 시간이 있었나."**
> 있었으면 어디서 막혔는지를 보고 고친다.

### 5.6 🔴 앱 코드가 어디 살지 [미정]

| 안 | 뜻 | 대가 |
| --- | --- | --- |
| **A** | `frontend/mobile/` — 프론트 파트 안에 | 파트가 안 늘어난다. 웹·앱이 한 CI 잡에 묶여 서로의 빌드 실패에 영향받는다 |
| **B** | `mobile/` — 새 파트 `app` | 웹과 앱이 독립한다. 파트가 다섯이 된다 |

**결정 마감: 앱 첫 커밋 전.** 3.3절의 `ml`/`bigData` 결정과 함께 한 번에 정하는 게 좋다 —
파트 목록은 한 번에 정해야 CI 설정을 한 번만 고친다.

### 6.1 무엇이 바뀌나

### 6.2 🔴 MySQL 로 옮길 때 실제로 깨지는 자리

옮기기 전에 알고 있어야 한 번에 끝난다. **모르고 옮기면 증상만 보고 원인을 못 찾는다.**

| 자리 | 무슨 일이 나나 | 대응 |
| --- | --- | --- |
| **문자 집합** | `utf8` 로 만들면 **이모지가 안 들어가고, 한글 정렬이 이상해진다.** MySQL 의 `utf8` 은 진짜 UTF-8 이 아니다 | 처음부터 **`utf8mb4`** 로 만든다. 나중에 바꾸면 테이블 전체를 다시 써야 한다 |
| **시각** | 저장할 때와 읽을 때 시간대가 다르면 **일정이 통째로 9시간 밀린다.** 여행 앱에서 이건 치명적이다 | 서버·DB·연결 문자열의 시간대를 **한 곳으로 통일**하고, 옮긴 직후 같은 조건으로 일정을 만들어 **견본 결과와 대조표를 만든다** |
| **JSON 칼럼** | 견본이 `Json` 타입으로 쓰던 자리 | MySQL 의 `JSON` 타입으로 간다. **그 안의 값으로 검색해야 하는 자리는 미리 골라 둔다** — JSON 안은 인덱스가 기본으로 안 걸린다 |
| **문자열 길이** | 인덱스를 걸 칼럼이 너무 길면 **MySQL 이 인덱스 생성을 거부한다** | 인덱스 대상 칼럼의 길이를 미리 정한다 |
| **불리언** | MySQL 에 진짜 불리언이 없다 | JPA 가 알아서 처리하지만, **직접 SQL 을 쓸 때 0/1 인 것을 기억한다** |

> **판정 방법은 하나다.** 옮긴 뒤 **같은 조건으로 일정을 만들어 견본과 대조한다.**
> 시각·비용·방문지가 같은지 표로 남긴다. **표가 없으면 옮긴 것이 아니라 옮긴 것 같은 것이다.**

### 6.3 추가할 칼럼 — v6 판단 그대로 유효하다

> **님의 지적 그대로다** — *"DB는 추가 칼럼 설정이 필요해 보이지만 아직 기획이니까 OK"*.
> 스택이 바뀌어도 **"이 기능을 하려면 이 값이 필요하다"는 판단은 그대로**다.

| 칼럼 | 없으면 무엇이 안 되나 |
| --- | --- |
| `soloFriendly` | 코스 테마 `SOLO_FRIENDLY`(혼밥·혼행 안심)를 **판정할 근거가 없다.** 테마가 이름만 있고 내용이 없어진다 |
| `breakTime` | 브레이크타임에 식사 일정이 잡힌다. **가서 문이 닫혀 있다** |
| `lastOrderTime` | 라스트오더 지나서 도착한다 |
| `subwayExit` | 지하철 출구 번호가 없어 현장 안내가 반쪽이 된다 |

**추가로 검토할 것 [제안]** — 7장 캐시 설계에서 필요해진 자리다.

| 칼럼·모델 | 왜 |
| --- | --- |
| 사용자 **출발지**를 저장하는 자리 | 7.3절 — 출발지가 매번 달라지면 이동시간 캐시가 안 맞는다. **자주 쓰는 출발지를 저장해 두면 캐시가 맞기 시작한다** |
| `PasswordResetToken` | 비밀번호 재설정 경로가 없다 |

> 🔴 **칼럼은 지금 정하는 게 가장 싸다.** 데이터가 쌓인 뒤에 칼럼을 추가하면
> **기존 행을 전부 채우는 일**이 따라온다. 지금은 표 한 줄이다.

### 6.4 공간 검색 — 특별한 것을 도입하지 않는다

장소가 277곳~수천 곳 규모다. 이 규모에서는 **네모 상자로 한 번 거르고
직선거리로 정렬**하면 충분하다.

```
1. 위도·경도의 최소·최대로 네모 상자를 만들어 후보를 좁힌다   ← (위도, 경도) 인덱스가 여기 쓰인다
2. 좁혀진 후보만 하버사인(지구가 둥근 것을 고려한 두 점 사이 거리 공식)으로 정렬
```

**전용 확장(PostGIS 같은 것)은 안 쓴다.** 설치·학습 비용이 이 규모에서 값을 못 한다.
필요해지는 시점은 **"수십만 건에서 반경 검색이 느려질 때"** 이고, 그때 다시 본다.

## 7. 캐시 — Redis 를 무엇으로 가르나

### 7.1 질문 — 계정마다 캐시를 따로 둬야 하나

> **팀에서 나온 질문 그대로다** — *"이동시간·날씨를 사람들이 자주 볼 거란 계산에 Redis 를
> 쓰는 건가? 그런데 각자의 위치가 다르면 각 계정마다 캐시를 쓸 수 있게 해야 할 것 같은데."*

**질문의 앞부분은 맞고, 뒷부분은 반만 맞다.** 갈라서 답한다.

### 7.2 🔴 캐시를 계정으로 가르면 캐시가 죽는다

**캐시의 값은 "여러 사람이 같은 답을 다시 쓴다"는 데서만 나온다.**

| | 계정으로 안 가를 때 | 계정으로 가를 때 |
| --- | --- | --- |
| 100명이 부산 날씨를 본다 | 기상청 호출 **1번**, 나머지 99번은 캐시 | 기상청 호출 **100번** |
| 메모리 | 1칸 | **100칸** |
| 결과 | 캐시가 일한다 | **캐시가 없는 것과 같으면서 메모리만 100배 쓴다** |

**날씨는 개인 정보가 아니다.** 내가 보는 해운대 내일 날씨와 남이 보는 해운대 내일 날씨는
**같은 값**이다. 같은 값을 사람 수만큼 따로 저장할 이유가 없다.

이동시간도 같다. **해운대 → 광안리는 누가 물어도 같은 답**이다.

### 7.3 그럼 지적의 어느 부분이 맞나 — **키를 무엇으로 잡느냐**

*"각자의 위치가 다르다"* 는 지적은 **정확히 맞는 문제를 짚었다.** 다만 답이 "계정" 이
아니라 **"좌표를 얼마나 뭉개서 키로 쓰느냐"** 다.

문제는 이렇게 생긴다. 사용자가 찍은 출발지 좌표를 **그대로** 키로 쓰면,
1미터만 달라도 다른 키가 된다. 그러면 **아무도 남의 캐시를 못 쓴다** — 계정으로
가른 것과 결과가 똑같아진다.

**해결은 반올림이다.**

| 무엇 | 키를 무엇으로 잡나 | 왜 그렇게 잡나 | 얼마나 두나 |
| --- | --- | --- | --- |
| **날씨** | `날씨:{기상청격자}:{날짜}` | **기상청이 애초에 격자 단위로 예보를 준다.** 부산 전체가 격자 몇 개다. 사람이 몇 명이든 격자는 그대로 | 1시간 |
| **장소↔장소 이동시간** | `경로:{출발장소id}:{도착장소id}:{이동수단}` | 장소가 유한하니 쌍도 유한하다. **가장 잘 맞는 캐시** | 24시간 |
| **좌표↔장소 이동시간** | `경로:{반올림한좌표}:{도착장소id}:{이동수단}` | 🔴 **여기가 지적하신 자리.** 좌표를 소수점 아래 3자리로 반올림하면 약 100미터 칸이 된다. **같은 동네에서 출발한 사람들이 한 칸을 같이 쓴다** | 24시간 |
| **장소 사진** | `사진:{장소id}` | 사람과 무관 | 24시간 |
| **메뉴판 인식 결과** | `인식:{이미지해시}` | **같은 메뉴판 사진이면 같은 결과.** 누가 찍었는지는 상관없다 | 24시간 |

> **반올림을 얼마나 할지는 맞바꿈이다.** 크게 뭉갤수록 캐시는 잘 맞고 답은 부정확해진다.
> 100미터 칸은 도보 1~2분 차이라 이동시간 추정에서 무시할 만하다.
> **[미정] — 실제 데이터로 한 번 재보고 정한다.** 지금 숫자를 못 박지 않는다.

### 7.4 🔴 계정으로 갈라야 하는 것 둘 — 캐시가 아니다

혼동을 없애기 위해 분명히 적는다. **계정별로 나눠야 하는 것이 있긴 한데, 그건 캐시가 아니다.**

| | 무엇 | 왜 계정별인가 |
| --- | --- | --- |
| **쿼터** (사용량 제한) | `쿼터:{사용자id}:{날짜}` | 메뉴판 인식·번역은 **호출당 돈이 든다.** 한 사람이 하루에 몇 번 썼는지는 **사람마다 달라야 한다.** 이건 캐시가 아니라 계량기다 |
| **세션** | `세션:{토큰}` | 로그인 상태는 사람마다 다르다 |

### 7.5 🔴 그리고 진짜 위험한 것 하나

**개인 데이터가 든 응답을 캐시할 때는 계정 키가 필수다.**

```
❌ 내여행목록                 ← 남의 여행이 보인다
✅ 내여행목록:{사용자id}
```

**이건 성능 문제가 아니라 사고다.** 캐시 키에서 계정을 빠뜨리면
**한 사람의 데이터가 다른 사람 화면에 뜬다.**

> **그래서 규칙을 한 줄로 정한다.**
>
> **"이 값이 사람마다 달라야 하는가?"**
> · 아니다 → **계정을 키에 넣지 않는다** (날씨·이동시간·사진·인식결과)
> · 그렇다 → **계정을 키에 반드시 넣는다** (내 여행·내 설정·쿼터·세션)
>
> 애매하면 **넣는 쪽**이다. 잘못 넣으면 느려지고, 잘못 빼면 **남의 데이터가 샌다.**

### 7.6 Redis 가 없을 때

**캐시가 없어도 서비스는 돌아야 한다.** Redis 가 죽었다고 일정 생성이 실패하면
캐시가 아니라 의존이다.

```
캐시 조회 실패 → 원본을 부른다 → 결과를 돌려준다 (캐시 저장만 조용히 건너뛴다)
```

### 8.4 마일스톤 [미정]

**날짜를 여기 적지 않는다.** 8.3 이 안 정해졌고, 담당자 배정도 안 끝났다.
**모르는 것을 적어 두면 다음 사람이 그것을 믿는다.**

대신 **순서**만 정한다. 이건 지금 정할 수 있다.

```
1. 스택·파트·리뷰 규칙 확정          ← 이 문서가 하는 일. 코드 한 줄 전에 끝낸다
2. 껍데기 세우기                     ← Spring 프로젝트 · React 프로젝트 · CI 잡
                                       "빈 것이 배포까지 도는 것" 을 먼저 만든다
3. 데이터 옮기기                     ← 장소 277곳을 MySQL 로. 결측은 그 뒤에
4. 한 줄기 관통                      ← 조건 입력 → 생성 → 결과 확인. 화면 하나 API 하나부터
5. 나머지 기능을 세로로 붙인다        ← 5.2절 방식
6. 앱                                ← 웹이 서 있어야 앱이 빨라진다
```

> **왜 2번(껍데기)이 3번(데이터)보다 먼저인가.** 배포 경로가 없으면 만든 것이
> 로컬에만 있고, **로컬에만 있는 것은 다른 사람이 확인할 수 없다.**
> "내 PC 에서는 됩니다" 가 나오는 지점이 정확히 여기다.

### 8.5 🔴 날짜를 하루 단위로 못 박지 않는 이유

v6 계획서는 **날짜마다 6인 각자의 과업**을 다 적어 뒀다. v7 은 그 방식을 쓰지 않는다.

**대신 5.5절의 방식을 제안한다** — 문서에 미리 적는 것은 **무엇을 만드나(기능 목록)**
까지고, **오늘 누가 무엇을**은 **그날 아침 스크럼에서 정하고 그 자리에서 선점한다.**

| | 일자별로 못 박기 | 5.5절 방식 |
| --- | --- | --- |
| 계획을 만드는 시점 | 미리, 한 번 | **매일 아침** |
| 하나가 밀리면 | 뒤가 다 밀리고 다시 짜야 한다 | 그날 것만 다시 정한다 |
| 겹침을 막는 것 | 사람이 만든 조율표 | **`ax_claim` 이 그 자리에서 거부한다** |
| 막혔을 때 | 계획을 지키려고 혼자 붙잡는다 | **30분 규칙 → `ax_send`** |

**아직 확정이 아니다.** 5.5절에 위험 세 가지와 함께 적어 뒀다.

## 9. 품질 게이트 — GitLab CI 기준

### 9.1 🔴 v6 계획서의 머지 조건은 이 저장소에서 안 돈다

v6 계획서 1.3절이 적은 명령들은 **`ref/local-route` 안에서만** 도는 것이다.

```bash
npx tsc -b web                     ← 그런 폴더가 없다
npm run build --workspace server   ← 그런 워크스페이스가 없다
npm test --workspace server        ← 없다
```

그리고 v6 은 **`.github/workflows/ci.yml`** 을 가리키는데, 이 저장소는 **GitLab** 이고
설정 파일은 **`.gitlab-ci.yml`** 이다. **PR 이 아니라 MR 이다.**

### 9.2 이 저장소에서 실제로 도는 것 [실측]

`.gitlab-ci.yml` 에 있는 잡들이 지금도 돈다. **파일 종류에 따라 걸리는 것이 다르다.**

| 잡 | 무엇을 보나 | `ref/` 만 바뀐 MR |
| --- | --- | :-: |
| `verify:mr-target` | MR 이 한 칸씩 올라가는가 (3.4절) | 돈다 |
| `claims` | 선점하지 않고 고친 파일이 있는가 | 안 돈다 |
| `governance` | 정족수를 채웠는가 (4.4절) | 안 돈다 |
| `ci:vendor` | `ci/axmap/` 사본이 손으로 바뀌었는가 | 안 돈다 |

누구나 손으로 돌려볼 수 있는 검사 둘도 그대로다.

```bash
node ci/verify-vendor.mjs            # 사본이 손으로 바뀌지 않았는가
node ci/axmap/bin/axmap.mjs doctor   # 이 PC 에서 선점이 실제로 도는가
```

### 9.3 새로 만들어야 하는 잡 [제안]

지금 CI 에는 **제품 코드를 검사하는 잡이 하나도 없다.** `backend/` · `frontend/` 가
비어 있었으니 당연하지만, **코드가 들어오는 순간 이게 구멍이 된다.**

| 잡 | 무엇 | 언제 |
| --- | --- | --- |
| `back:build` | Gradle 빌드 + 테스트 | `backend/` 가 바뀐 MR |
| `front:build` | 타입 검사 + 프로덕션 빌드 | `frontend/` 가 바뀐 MR |
| `verify:branch-name` | 브랜치 이름 모양 (3.5절) | 모든 MR |

> **파일 종류로 잡을 가른다.** 프론트만 고친 MR 에서 백엔드 빌드를 돌리면
> **관계없는 실패로 머지가 막힌다.** 관계없는 실패가 몇 번 반복되면 사람은
> 빨간불을 안 읽기 시작하고, **그때부터 CI 는 있으나 마나가 된다.**

### 9.4 판정은 종료 코드로 한다

**"테스트가 몇 개 통과했다"를 이 문서에 적지 않는다.** 판정은 종료 코드다.
0이면 통과, 그 밖이면 실패. 그 숫자만이 늘어나는 테스트를 따라 낡지 않는다.

## 결론

이 문서가 v6 계획서와 다른 점은 하나다. **규칙을 문서에서 베끼지 않고 저장소에서 읽었다.**

그 결과 알게 된 것 중 제일 중요한 것은 이거다.

> **이 저장소의 브랜치 이름 규칙은 지금 아무도 강제하지 않는다.**
> 그래서 세 가지가 동시에 돌고 있다.

이건 누가 안 지켜서가 아니다. **지킬 방법이 문서뿐이었기 때문이다.**
루트 `CONTRIBUTING.md` 3절이 이미 답을 적어 뒀다 —
*"권한은 사람의 목록이고 파이프라인은 코드의 조건이다. 그래서 팀이 지키기로 한 것은
전부 CI 잡으로 만든다."* **이름 규칙도 예외가 아니다.**

그리고 역할에 대해 한 가지. **역할표는 벽을 세우라고 있는 것이 아니라
물어볼 사람을 정해 두라고 있는 것이다.** 기능은 세로로 되어 있고 역할은 가로로
나뉘어 있어서, 그대로 나누면 기능 하나에 인계가 세 번 생긴다.
**한 사람이 화면부터 테이블까지 끌고 가고, 막히면 30분 안에 담당자에게 넘긴다.**
