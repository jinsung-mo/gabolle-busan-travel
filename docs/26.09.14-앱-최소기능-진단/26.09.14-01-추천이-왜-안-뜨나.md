## 0. 한 문장

**코드는 다 만들어져 있다. 막는 것은 셋인데, 셋 다 코드가 아니라 데이터와 어휘다.**

---

## 1. 길 전체 — 답이 어디를 거쳐 추천이 되나

```
앱 온보딩 화면
   │  취향 답 (갈래·분위기·음식·경사·그늘 …)
   ▼
POST /api/v1/trips            여행을 만들 때 취향도 같이 저장된다
   │                          → preference_snapshot (한 벌)
   │                          → preference_answer  (차원마다 한 줄)
   ▼
POST /api/v1/trips/{id}/recommendation-jobs      추천을 주문한다 (바로 안 준다)
   │
   ▼
후보 고르기   반경 안에서 + 고른 갈래에 해당하는 장소만
   │          ← place 표
   ▼
채점         거리 0.30 · 갈래 0.20 · 분위기 0.15 · 음식 0.15
   │          · 정렬형 5축 묶음 0.10 · 인기 0.10
   │          ← place_feature 표 · user_place_code_map 대조표
   ▼
GET /api/v1/recommendation-jobs/{jobId}          결과를 받아 간다
```

🔴 **"추천" 이라는 말이 앱 안에서 두 가지를 가리킨다.**

| | 무엇 | 어디서 오나 |
|---|---|---|
| 홈 화면의 추천 장소 3장 | 사람이 고른 큐레이션(해운대·광안리·감천) | 이름으로 장소를 찾아 붙인다. 위 파이프라인과 **무관** |
| 여행 일정의 추천 | 위 그림의 파이프라인 | 취향 답을 실제로 쓴다 |

**오늘 "추천이 잘 뜨는지" 를 확인한다는 것은 아래쪽을 말한다.**

---

## 2. 🔴 막는 것 셋

### (가) 재고가 쏠려 있다 — 이게 제일 크다

`원본/…-03` 의 어제 실측이다.

| 갈래 | 장소 수 |
|---|---|
| 음식 | 2,355 |
| 문화·사찰 | 162 |
| 도심 | 47 |
| 카페·힐링 | 26 |
| 자연·산책 | 23 |
| **바다·해변** | **2** |

**온보딩에서 바다를 고른 사람에게 줄 수 있는 장소가 2곳이다.** 반경 조건까지 걸리면
0곳이 된다. 그러면 추천은 `ENGINE_NO_CANDIDATES`(**반경 안에 그 갈래 장소가 없음**)로
끝나고, 이건 **다시 시도해도 같은 답이 오는 종류**라고 코드가 표시해 둔다.

> 🔴 **이건 버그가 아니다. 재고 부족이다.** 코드를 아무리 고쳐도 안 없어진다.
> 고치는 자리가 완전히 다르다 — 장소를 더 넣거나, 화면에서 못 고르게 하거나 둘 중 하나다.

적재기 코드 자신이 이 사실을 적어 놓았다 — *"지금은 카페·힐링만 고른 사용자의 후보가
0건이다."*

### (나) 어휘를 지키는 사전이 한 갈래에만 있다

취향 답의 낱말과 장소 표식의 낱말이 **글자 그대로 같아야** 점수가 붙는다.
어제·오늘 작업(-904, -915)으로 **갈래(CATEGORY)** 에는 사전과 잠금장치가 생겼다.
그런데 나머지는 아직이다.

| 차원 | 사전이 있나 | 어긋나면 |
|---|---|---|
| 갈래 | ✅ 있다 (어제 생김) | 저장 자체가 거부된다 |
| 분위기 | ❌ 없다 | **조용히 그 축 점수가 0/누락** |
| 음식 | ❌ 없다 | 위와 같다 |
| 경사·그늘 | ❌ 낱말 자체를 아직 못 읽는다 | **항이 계산에서 통째로 빠진다** |

> **가장 나쁜 고장은 조용한 고장이다.** 오류가 안 나고 점수만 빠지므로,
> 추천이 이상해도 왜 이상한지 아무도 모른다.

### (다) 가격은 물어보고 저장까지 하는데 결과에 영향이 0이다

계정 첫 실행에서 묻는 **씀씀이 3문항**(오는 교통·숙소·식사)은 저장된다.
그런데 그 답이 점수에 곱해지는 배수가 **아직 1.0 이다 — 곱해도 아무것도 안 바뀐다.**
문서가 그렇게 못 박아 두었다: *"배수 크기는 아직 안 정해져 1.0(변화 없음)이다."*

장소 쪽에 가격대 값은 이미 들어와 있다. **잇는 대조표만 없다.**

## 3. 표가 비면 각각 무슨 일이 생기나

| 표 | 무엇을 담나 | 비면 |
|---|---|---|
| `place` | 장소 정본 | 후보 0건 → 매번 실패 |
| `place_feature` | 장소의 속성들 | 점수 항이 **0점이 아니라 빠진다** |
| `user_place_code_map` | 취향 낱말 ↔ 장소 표식 대조표 | 🔴 **갈래 거르기가 통째로 꺼진다** — 오류 없이 아무거나 나온다 |
| `preference_snapshot` / `preference_answer` | 취향 답 | 거리·인기만으로 뽑는다 (개인화 없음) |

🔴 **셋째 줄이 특히 위험하다.** 막히는 게 아니라 **거르기가 사라진다.** 결과는 나오는데
개인화가 안 된 결과다. 화면만 봐서는 정상과 구별이 안 된다.

---

## 4. 확인 못 한 것

- **운영 DB 의 오늘 값.** 도구 권한(운영 읽기)이 막혀 못 쟀다. 위 재고 숫자는 어제자다.
- ~~실제로 추천을 한 번 받아 본 결과~~ → 🟢 **쟀다. 아래 5절을 보라.**
- 온보딩 화면 둘(여행 만들 때 묻는 취향 / 계정 첫 실행의 씀씀이 3문항) 중
  **사용자가 실제로 먼저 마주치는 것이 무엇인지** — 화면 순서는 안 봤다.

## 5. 🟢 실제로 돌려 봤다 — 장소만 넣었더니 뜬다 (2026-09-14)

원본: `원본/26.09.14-원본-04-추천-전후-실측.md`

로컬에 백엔드와 DB 를 띄우고 **앱이 보내는 것과 같은 요청**을 두 번 보냈다.
사이에 **장소 200곳만 넣었다. 요청은 글자 하나 안 바꿨다.**

| | 장소 0곳 | 장소 200곳 |
|---|---|---|
| 결과 | 🔴 `FAILED` | 🟢 `COMPLETED` |
| 이유 | `ENGINE_NO_CANDIDATES` | — |
| 후보 생성 → 통과 → 반환 | 0 → 0 → 0 | **66 → 66 → 10** |
| 걸린 시간 | 41ms | 75ms |
| 일정 | 없음 | **1개 · 8칸** |

**추천 파이프라인은 끝까지 동작한다.** 점수 매기기도, 다양성 재정렬도, 일정 조립도
전부 돈다. 이유 코드까지 제대로 붙는다 (`NEAR_ORIGIN` · `TAG_MATCH_INTEREST` ·
`DIVERSITY_RERANKED`).

🔴 **그래서 「추천 품질」 과 「맞는 장소 없음」 은 완전히 다른 문제다.**
실패는 **첫 단계에서** 끝난다 — 후보가 0건이라 채점은 돌지도 않는다. 점수 로직을
아무리 고쳐도 이 실패는 안 없어진다.

> 표본 200곳은 전부 음식이라, 바다·자연처럼 재고가 적은 갈래에서 무슨 일이
> 생기는지는 이 시험으로 알 수 없다 — **확인 못 함**.
