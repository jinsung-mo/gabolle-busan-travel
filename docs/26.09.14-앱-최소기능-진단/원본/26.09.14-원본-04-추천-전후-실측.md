# 원본 04 — 장소를 넣기 전과 후, 같은 요청을 보냈다 (2026-09-14)

가공하지 않았다. **요청은 글자 하나도 안 바꿨다. 바뀐 것은 DB 의 장소뿐이다.**

## 무엇을 했나

로컬에 백엔드와 DB 를 띄우고(원본 01), 앱이 실제로 보내는 것과 같은 모양으로
**계정 만들기 → 로그인 → 온보딩 취향을 담은 여행 만들기 → 추천 주문 → 결과 받기**
를 두 번 돌렸다. 사이에 장소만 넣었다.

취향 답은 이렇게 보냈다.

```
category         ["FOOD"]
atmosphere       ["LIVELY"]
foodPreference   ["KOREAN"]
locality 3 · quietness 3 · touristPreference 3
출발지            35.1046, 129.0357  (부산 중구)
제약              걷기 최대 1200m · 휠체어/유아차/짐/계단 = 해당 없음
```

## 두 번을 DB 에서 나란히 본 것

```
 job_status |      error_code      | 생성 | 통과 | 반환 | 걸린ms 
------------+----------------------+------+------+------+--------
 FAILED     | ENGINE_NO_CANDIDATES |    0 |    0 |    0 |     41
 SUCCEEDED  |                      |   66 |   66 |   10 |     75
```

일정도 실제로 만들어졌다.

```
 일정 | 일정칸 
------+--------
    1 |      8
```

## 이 실측이 말하는 것

1. **추천 파이프라인은 끝까지 동작한다.** 점수 매기기·다양성 재정렬·일정 조립까지
   전부 돈다. 이유 코드(`NEAR_ORIGIN` · `TAG_MATCH_INTEREST` · `DIVERSITY_RERANKED`)도
   제대로 붙는다
2. **성패를 가른 것은 오직 「그 갈래에 장소가 있는가」 하나다.** 요청은 동일했다
3. **실패는 첫 단계에서 끝난다.** 생성 0 · 통과 0 · 반환 0 — 채점은 돌지도 않는다.
   그래서 「추천 품질」 문제와 「맞는 장소 없음」 문제는 **완전히 다른 문제다**
4. 통과 66 중 **반환은 10** 이다. 거르기와 다양성 재정렬이 실제로 일하고 있다

🔴 **이것은 로컬 실측이다.** 표본 200곳은 전부 음식이라, 바다·자연처럼 재고가 적은
갈래에서 무슨 일이 생기는지는 이 시험으로 알 수 없다 — **확인 못 함**.
