# 스토어 심사 반려 방지 체크리스트

**S15P21E201-247.** Google Play·Apple App Store 제출 전 훑는 체크리스트다. 정책은
스택(Node 든 Spring 이든)과 무관하므로, `docs/LOCAL_ROUTE_6인_개발계획서_및_업무지침서_v6.md`
8장에 이미 있던 항목을 그대로 버리지 않고 옮겨 왔다 — 다만 그 문서는 v6(옛 Node
스택 전제)라 지금 실제 코드와 맞는지 하나씩 다시 확인했다. 확인 결과는 **실측**
칸에 있다.

**각 항목에 확인 방법을 적는다.** 체크박스만 있으면 "확인했다"는 사실만 남고
**어떻게 확인했는지**가 안 남는다 — 심사에 다시 넣을 때 뭘 다시 봐야 하는지 알 수
없다.

> 🔴 **실측이 이 문서를 쓴 시점(2026-09-04) 기준이라는 뜻이다.** 코드가 바뀌면
> 이 표도 낡는다. 제출 직전에 다시 한 번 실측한다.

## 0. 지금 바로 막힌 것 — 실측으로 발견한 것 셋

이 셋은 "확인이 안 됐다" 가 아니라 **아직 존재하지 않는다.** 체크리스트를 돌리기
전에 먼저 구현이 필요하다.

| # | 무엇이 없나 | 왜 심사에 걸리나 | 실측 근거 |
| :-: | --- | --- | --- |
| 1 | **계정 삭제 API** | Apple 5.1.1(v) — 앱 안에서 계정을 삭제할 수 있어야 한다. Google Play도 데이터 삭제 경로를 요구한다 | `backend/.../auth/api/AuthController.java`에 `DeleteMapping` 이 하나도 없다 (전체 매핑 grep 결과 0건) |
| 2 | **권한 사용 목적 문구** | iOS는 `Info.plist`에 각 권한의 목적 문구(`NS*UsageDescription`)가 없으면 심사 자체가 안 된다. Android도 목적 없는 권한 선언은 리젝 사유다 | `frontend/app.json`에 `ios.infoPlist`·`android.permissions` 자체가 없다 — 카메라·마이크·위치·사진 중 아무 것도 선언 안 됨 |
| 3 | **약관·개인정보 처리방침 화면**, **신고 검토 경로(UGC)** | 둘 다 심사 필수 항목 — 방침 URL이 앱 내에도 있어야 하고, 사용자 생성 콘텐츠(여행 기록 등)가 있으면 신고·처리 경로가 있어야 한다 | `frontend/app/` 라우트 전체(`git ls-tree`)에 `legal/terms`·`legal/privacy`·`admin/moderation`류 화면이 없다 |

**이 셋은 각자 티켓이 있거나 있어야 한다** — S15P21E201-197(약관)·203(개인정보
처리방침)이 이미 있다. 계정 삭제·권한 문구·신고 경로는 아직 전용 티켓이 없다면
이 문서를 근거로 새로 낸다.

### 🔴 정정 (2026-09-10) — Apple 로그인, 다시 만들기로 뒤집었다

2026-09-04(S15P21E201-602)에 "Apple 로그인은 만들지 않는다"고 확정했었다. 아래
문단은 그때 그대로 남겨 둔다 — 왜 처음에 뺐는지, 무슨 위험을 감수하려 했는지는
여전히 유효한 기록이다.

그런데 실제로 iOS 스토어 제출을 앞둔 지금(2026-09-10), 그 문서가 예견한 순간이
왔다 — "이 위험을 다시 마주하게 된다"고 적어 둔 바로 그 시점이다. 이번에는
위험을 감수하는 대신 **결정을 뒤집었다.** Sign in with Apple을 Google·Kakao와
같은 방식(OAuthProviderClient 패턴, PKCE + provider 서명 JWT)으로 만든다.

아래는 2026-09-04에 적었던 원래 결정 — **더 이상 유효하지 않다.**

> 원래 여기 4번 항목으로 "Sign in with Apple 없음"을 gap으로 적어 뒀었다. 그런데
> `docs/gabolle/GABOLLE_통합_서비스_기획서_v1.1.docx` MVP 결정표를 다시 보니
> "이메일/Apple 로그인"이 이미 명시적으로 제외 범위였다 — 팀이 실수로 빠뜨린
> 게 아니라 원래 정한 것이었다. 그래서 이번에 그대로 확정했고, Apple 로그인은
> 만들지 않는다.
>
> 남는 위험은 사라지지 않았다. Google·Kakao 로그인은 있고 Apple 로그인이
> 없는 채로 iOS 앱스토어에 제출하면 Apple 가이드라인 4.8 위반으로 반려될 수
> 있다. 이번 결정은 그 위험을 인지한 채로 받아들인 것이다 — iOS 스토어 제출을
> 실제로 진행할 때 이 위험을 다시 마주하게 된다. 그때 가서 "왜 안 만들었지"를
> 다시 묻지 않도록 여기 남긴다.

## 1. Google Play

| # | 항목 | 확인 방법 |
| :-: | --- | --- |
| 1 | Target API level — 제출 시점 Google 최소 요구치 이상 | Google Play Console → 앱 → "출시 → 앱 콘텐츠"에서 요구 레벨을 확인하고, `frontend/app.json`(EAS 빌드 설정)의 `android.compileSdkVersion`/`targetSdkVersion`과 대조한다 |
| 2 | AAB(App Bundle) 형식, 64비트 지원 | EAS 빌드 산출물 확장자(`.aab`)와 빌드 로그의 ABI 목록(`arm64-v8a` 포함) 확인 |
| 3 | 비공개 테스트 인원·기간 요건 충족 | Play Console → "테스트 → 비공개 테스트" 화면의 테스터 수·경과일 표시를 캡처 |
| 4 | 개인정보처리방침 공개 URL 연결 | Play Console 스토어 등록정보에 넣은 URL을 브라우저로 직접 열어 200 확인 |
| 5 | **데이터 안전(Data safety) 양식** — 수집 항목·목적·삭제 경로 | 실제로 수집하는 필드를 백엔드 엔티티(`backend/src/main/java/.../domain`)에서 하나씩 대조하고, 양식 제출 전 스크린샷을 이 문서에 첨부 |
| 6 | 서명 키 이중 백업 | 키스토어 파일 체크섬을 두 곳(예: 팀 비밀 저장소 + 담당자 개인 백업)에서 대조 |
| 7 | 아이콘·그래픽·스크린샷 규격 | Play Console 업로드 화면이 자체 검증(규격 안 맞으면 업로드 자체가 막힘) |

## 2. Apple App Store

| # | 항목 | 확인 방법 |
| :-: | --- | --- |
| 1 | **계정 삭제 기능** (5.1.1(v)) | 앱 내 설정 화면에서 실제로 계정을 삭제해보고, DB에서 해당 사용자 행이 지워지거나 익명화되는지 백엔드 로그·DB 조회로 확인 |
| 2 | 권한 사용 목적 문구 (`NSCameraUsageDescription` 등) | `frontend/app.json`의 `ios.infoPlist`를 열어 실제 사용하는 권한(카메라·마이크·위치·사진)마다 문구가 있는지, **쓰지 않는 권한은 없는지** 대조 |
| 3 | 요청하지 않는 권한 미선언 | 위와 같은 파일에서 실제 코드가 부르는 권한 API(`expo-camera`, `expo-location` 등 package.json 의존성)와 선언된 권한 목록을 1:1 대조 |
| 4 | **Sign in with Apple 대응 (4.8)** | 🔴 **2026-09-10 결정 번복으로 구현 중**(0절 참고) — Google/Naver/Kakao와 같은 OAuthProviderClient 패턴. Apple Developer Program에 Services ID·Sign in with Apple capability·redirect URI 등록, Jenkins에 `gabolle-apple-*` 크리덴셜(Team ID·Key ID·private key) 등록까지 끝나야 실제로 켜진다 |
| 5 | 심사 메모·심사용 계정 | App Store Connect 심사 정보란에 실제로 로그인되는 테스트 계정을 넣고, 그 계정으로 핵심 플로우(일정 생성 등)가 끝까지 되는지 직접 재현 |
| 6 | App Privacy(개인정보 수집 유형) 응답 | 데이터 안전 양식과 동일하게 실제 수집 필드 기준으로 작성 — 두 스토어 답변이 서로 다르면 그 자체가 리스크다 |
| 7 | 스크린샷·아이콘 규격 | App Store Connect 업로드 화면 자체 검증 |
| 8 | 지원 URL·개인정보처리방침 URL | 브라우저로 직접 열어 200 확인, 앱 내 링크와 동일 URL인지 대조 |

## 3. 공통 리젝 방지 (플랫폼 무관)

> 근거: 상위 리젝 사유 — 심사 중 크래시, 개인정보처리방침 누락, 데모 계정 미제공,
> 오도적 스크린샷, 접근성 미흡. (`docs/LOCAL_ROUTE_6인_개발계획서_및_업무지침서_v6.md`
> 8.3절에서 이월, 근거는 그대로 유효 — 정책 자체는 스택과 무관하다)

| # | 항목 | 확인 방법 |
| :-: | --- | --- |
| 1 | 전 화면 실기기 진입 시 크래시 0건 | 화면 목록(`frontend/app/` 전체 라우트)을 하나씩 실기기에서 열어 크래시 로그(Sentry 등)를 확인 |
| 2 | 네트워크 차단 상태에서도 안내 표시 | 기기 비행기 모드로 전환 후 각 주요 화면 진입 — 흰 화면·무한 로딩이 아니라 안내 문구가 뜨는지 확인 |
| 3 | 개인정보처리방침이 앱 내 링크·스토어 등록란 양쪽에 있다 | 앱 내 링크 탭 → 브라우저로 정상 이동하는지, 스토어 등록 URL과 같은 주소인지 대조 |
| 4 | 로그인 없이 쓸 수 있는 범위를 심사 메모에 명시 | 실제로 로그인 없이 핵심 플로우(일정 생성 등)가 어디까지 되는지 재현해보고 그 결과를 메모에 반영 |
| 5 | 스크린샷이 실제 화면과 일치 | 제출용 스크린샷과 최신 빌드 화면을 나란히 놓고 다른 점 확인 |
| 6 | 인앱 결제 없음 · 예약은 외부 링크임을 명시 | 실제 예약 관련 화면(있다면)에서 외부 브라우저로 이동하는지 확인 — 이 프로젝트는 현재 예약/광고 영역 존치 여부가 S15P21E201-350·173으로 미정이라, 그 결정이 나면 이 항목도 다시 확인해야 한다 |
| 7 | 권한 목적 문구가 모든 권한에 있고, 안 쓰는 권한은 삭제 | 위 "Apple #2/#3"과 동일 확인 |
| 8 | **권한을 거부해도 핵심 기능이 동작** | 위치·카메라·마이크 권한을 모두 거부한 상태로 온보딩부터 다시 시작 — 일정 생성까지 막히지 않는지 확인 |
| 9 | UGC 신고·차단·검토 경로가 앱 내에 있고 약관에 기재 | 여행 기록 등 사용자 생성 콘텐츠에 신고 버튼이 있는지, 그 신고가 어디로 가는지(운영 콘솔·큐) 추적 — **지금은 이 경로 자체가 없다(0절 참고)** |
| 10 | 빈 상태에서 흰 화면이 아니라 안내가 뜬다 | 데이터가 없는 계정으로 각 탭(`(tabs)/trips`·`saved` 등) 진입해 빈 상태 UI 확인 |
