## 3. 기준선 — 지금 로직 그대로 돌리면 **무작위보다 나쁘다**

### 3.1. 먼저: 지금 로직은 3,039곳에 **거의 같은 점수**를 준다

제품 코드(`ref/local-route/server/src/services/recommend.ts`)를 그대로 옮겨
(LOCAL 모드 · 사용자가 취향을 안 고름), 제품 **자신의 임포터**
(`prisma/import-tourapi.ts`)가 정해 둔 대로 각 칸을 채웠다.

| 점수 축 | 3,039곳에서 실제로 무엇이 되나 |
|---|---|
| `taste` (0.45) | 사용자가 취향을 안 고르면 `preferenceSimilarity` 가 **0** → 전원 동일 |
| `local` (0.30) | `localScore` = **0.5 고정** (임포터의 콜드스타트 중립값) → 전원 동일 |
| `travel` (0.10) | 🔴 `TRAVEL_EFFICIENCY_PLACEHOLDER = 0.5` → **전원 동일** |
| `mode` (0.20) | `localScore` 에서 나온다 → 전원 동일 |
| `budget` (0.05) | `priceTier` = 2 고정 → **식당/카페 두 값**뿐 |
| `foreign` (0.05) | 영문 이름 있음 / 해운대·서면 등 지명 포함 → **두세 값** |

즉 **가중치 여섯 개 중 넷이 상수**다. 순위를 실제로 가르는 것은 *"카페인가"* 와
*"영문 이름이 있나"* 둘뿐이다. 앞 조사 문서가 *"배관이 끊겨 있다"* 고 한 것의
숫자로 된 모습이다.

동점이 대부분이므로 **동점은 POI id 해시로 섞어** 깨뜨렸다. 파일 순서로 세우면
OSM id 순서(= 먼저 그려진 동네 = 원도심)가 몰래 신호가 되기 때문이다.

**순열 검정**(permutation test — *정답 자리를 무작위로 바꿔 놓고 같은 값이 몇 번

🔴 **그런데도 판정용에서 무너졌다.** 그 이유가 다음 절이다.

### 16.5.1. 🔴 정답의 강도 — 미쉐린 가격대와 블루리본 리본수를 쓸 수 있나

과제가 물은 것이다. 답을 나눠서 적는다.

**먼저 누출(leakage — 정답에서 나온 값을 몰래 신호로 쓰는 것) 경계선을 못 박는다.**
가격대·리본수·출처 수는 **정답에만 붙어 있는 값**이다. 후보 53,716곳 중 정답이 아닌
곳에는 그 값이 아예 없다. 그래서 **입력(신호)으로는 절대 못 쓴다** — 쓰는 순간
*"정답인 것만 아는 값"* 으로 정답을 맞히는 부정행위가 된다.

**무게로 쓰는 것은 다르다.** 무게는 *"이 정답을 얼마나 중요하게 배울 것인가"* 를
정할 뿐이고, 점수를 매길 때는 쓰이지 않는다. 판정용 정답의 무게는 한 번도 보지
않는다 — Recall 은 맞힌 **개수**를 세지 무게를 세지 않기 때문이다.

그래서 무게 방식 셋을 **조정용 교차검증으로** 견주었다.

| | 무게 방식 | 최고 CV R@200 | 최고 CV 중앙% |
|---|---|---|---|
| A | 무게 없음 — 정답은 다 같다 | 6.4% | 12.7% |
| **B** | **출처 수** — 두 곳이면 ×2, 셋이면 ×3 | **6.4%** | **12.1%** ← 골랐다 |
| C | 출처 수 + 블루리본 리본 2개면 +1 | 6.4% | 13.7% |

**Recall@200 은 셋이 같고 중앙 백분위만 조금 갈린다.** B 를 골랐지만 🔴 **차이가
의미 있다고 말할 수 없다** — 조정용 정답이 110곳뿐이라 이 정도 차이는 잡음이다.
"출처가 여러 곳이면 더 확실한 정답" 이라는 생각은 그럴듯하지만, **이 표본으로는
증명되지 않았다.**

데이터에 **하나도 없다.** 상위 200위는 후보의 0.37% 라, 그 좁은 칸에 들어가려면
가게 하나하나를 가르는 신호가 있어야 한다. Recall@200 ≥ 20% 는 그것을 요구한다.

그런 신호는 **영업 지속기간 · 재방문 · 대기줄 · 리뷰 수** 같은 것인데,
지금 손에 있는 공개 데이터에는 없다. 라운드4 를 연다면 **모델이 아니라 그 신호를
구하는 일**부터 해야 한다.

| **K6** | 취향 전부 SKIPPED 계정·엔진 실패 요청의 첫 결과가 비어 있지 않다 | 비어 있지 않다 | 백엔드 통합 테스트 영역 — 이 채점 장치로는 못 잰다 | ⚪ **미측정** |

🔴 **K4·K5 는 "쟀는데 나빴다" 가 아니라 "잴 재료가 없다" 다.** K4 는 팀이 손으로
60곳을 적어야 하고(사람의 판단이라 자동화할 수 없다), K5 는 `editorial_pick` 에
사람이 고른 목록을 넣어야 한다. 둘 다 **사람이 먼저 해 줘야 하는 일**이다.

> **K1~K6 을 다 넘으면 "개인화 없이 쓸 만한 상태" 다. 하나라도 못 넘으면 개인화를
> 얹지 않는다** — 나쁜 순위 위에 개인화를 얹으면 **개인마다 다르게 나쁘다.**
> K3a·K3b 가 실패했으므로 🔴 **지금은 개인화를 얹을 때가 아니다.**

### 22.2. ② 실제 배포 흐름 — 참고로만 적는다

| 시나리오 | 후보 200 안에 든 정답 | 사용자가 보는 상위 20 안에 든 정답 |
|---|---|---|
| 무작위 | **0.26%** | 0.02% |
| `asis` | **0.26%** | **0.00%** |
| `cuisine-한식` | **0.26%** | 0.02% |
| `cuisine-일식` | **0.26%** | 0.06% |

🔴 **네 시나리오의 "후보 200 안" 이 소수점까지 같다.** 이것이 21.3 의 증거다 —
자르는 기준이 점수가 아니라 거리이기 때문에 **채점기를 무엇으로 바꿔도 이 값은
안 움직인다.** 채점기를 아무리 잘 만들어도 이 위에서는 0.26% 가 천장이다.

그리고 `asis` 의 상위 20 은 **0.00%** — 판정용 정답 47곳 × 출발지 100곳 = 4,700번
중 **한 번도** 사용자 화면에 정답이 안 들어왔다.

### 22.3. 🔴 예상이 맞았나 — 하나는 맞고 하나는 틀렸다

선등록에 적은 예상과 실제:

| 항목 | 예상 | 실측 | |
|---|---|---|---|
| `asis` R@200 | 0 ~ 2% (중심 0.3%) | **0.3%** | 🟢 맞았다 |
| `asis` 중앙 백분위 | 44 ~ 58% (중심 51%) | **61.4%** | 🔴 **틀렸다 — 예상보다 나빴다** |
| 주 기준 통과 | 못 넘을 것으로 예상 | 못 넘었다 | 🟢 |
| 부 기준 통과 | 못 넘을 것으로 예상 | 못 넘었다 | 🟢 |

중앙 백분위를 낙관했다. 조정용 111곳에서 50.7% 였는데 판정용 47곳에서는 61.4% 로
나왔다. 무작위 기준선도 조정용 52.5% → 판정용 65.2% 로 같은 방향으로 움직였으니
**판정용 47곳이 출발지 100곳에서 평균적으로 더 먼 곳에 흩어져 있다**는 뜻이다.
표본이 47곳뿐이라 이 정도 흔들림은 예상 폭을 더 넓게 잡았어야 했다.

## 용어

| 말 | 뜻 |
|---|---|
| **정답표 (ground truth)** | *"이건 맞다고 치는 목록"*. 우리 순위가 맞는지 재는 자 |
| **홀드아웃 (holdout)** | 고칠 때 절대 안 보고 아껴 두는 몫. 마지막에 한 번만 연다 |
| **과적합 (overfitting)** | 정답을 외워서 맞히는 것. 조정용에서는 잘하고 판정용에서 무너진다 |
| **Recall@K** | 상위 K 위 안에 정답이 몇 % 들어왔나 |
| **순위 백분위 중앙값** | 정답들이 전체에서 위에서 몇 % 지점에 있나. 50% 면 무작위와 같다 |
| **AUC** | 아무 정답 하나와 아무 비정답 하나를 뽑았을 때 정답이 더 위에 올 확률. 0.5 = 동전 |
| **순열 검정 (permutation test)** | 정답 자리를 무작위로 바꿔 놓고 같은 값이 몇 번 나오는지 세는 것 |
| **씨앗 (seed)** | 같은 씨앗이면 언제 돌려도 같은 순서가 나오게 하는 수 |
| **POI · NDJSON** | 지도에 점으로 찍히는 지점 · 한 줄에 객체 하나씩 적는 형식 |
| **상가정보 (상권정보)** | 소상공인시장진흥공단이 분기마다 공개하는 전국 상가·업소 목록. 상호·업종·주소·좌표가 들어 있다 |
| **로지스틱 회귀** | 여러 신호에 무게를 곱해 더한 뒤 0~1 확률로 눌러 담는 가장 단순한 지도학습 모델 |
| **교차검증 (cross-validation)** | 조정용을 다시 여러 조각으로 나눠, 일부로 배우고 나머지로 재 보는 것. 판정용을 안 열고 과적합을 가늠하는 방법 |
| **규제 (regularization)** | 가중치가 너무 커져 정답을 외우는 것을 막는 벌점 |
| **원핫 (one-hot)** | 업종·구군 같은 범주를 칸마다 0/1 로 펼치는 것 |
| **누출 (leakage)** | 정답에서 나온 값을 몰래 신호로 쓰는 것. 조정용에서만 잘 맞고 판정용에서 무너진다 |
| **이항검정** | 무작위로 찍었을 때 이만큼 맞을 확률을 세는 것 |
| **기저율 (base rate)** | 아무 데나 찍었을 때 맞을 확률 |
| **TSV** | 탭(Tab)으로 칸을 나눈 표 파일. 쉼표 대신 탭이라 상호에 쉼표가 들어가도 안 깨진다 |
| **자카드 지수 (Jaccard)** | 두 목록이 얼마나 같은가. 교집합 ÷ 합집합. 1이면 같은 표, 0이면 겹치는 것이 없다 |
| **해안선 (natural=coastline)** | OSM 에서 바다와 육지의 경계를 그린 선에 붙는 태그 |
| **대조군 (control group)** | 학습에도 판정에도 안 쓰고, **비교만 하려고** 따로 둔 정답 집합 |
| **정답의 강도 (sample weight)** | 정답마다 다른 무게. *"이 정답을 얼마나 중요하게 배울 것인가"*. 점수를 매길 때는 안 쓰인다 |
| **선등록 (preregistration)** | 판정용을 열기 **전에** 최종안·예상 성적·기준을 적어 두는 것. 나중에 말을 바꾸지 못하게 한다 |
| **합집합 (union)** | 두 목록을 겹치는 것 하나로 세면서 합친 것 |
| **후보 상한 (candidateLimit)** | 채점 대상으로 삼을 후보 수의 상한. 🔴 점수가 아니라 **거리순**으로 자른다 |
| **실효 반경** | 후보 상한에 걸려 실제로 보게 되는 거리. 설정한 반경보다 훨씬 짧을 수 있다 |
| **경계상자 (bounding box)** | 원 모양 반경을 감싸는 네모. DB 는 네모로 긁고 원은 코드가 다시 잰다 |
