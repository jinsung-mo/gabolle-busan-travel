## 변경 목적

### 지금 구조의 한계 — 데이터를 잘 모을수록 앱이 느려진다

지금까지는 **요청이 오면 그때 계산**했다. 홈 화면을 열 때마다 온톨로지(**장소·조건·관계를
기계가 읽을 수 있게 적어 둔 사전**)를 훑고, 제약을 판정하고, 순위를 매긴다 — 사람이 화면을
여는 바로 그 순간에.

문제는 온톨로지에 인스턴스(**등록된 개별 사물 하나하나 — 장소 한 곳, 노선 하나**)가
늘어날수록 **읽기가 같이 느려진다**는 것이다. 빅데이터 파트가 데이터를 잘 모을수록 앱이
느려진다. **노력이 벌을 받는 구조다.**

### 이 MR 이 바꾸는 것: 계산이 일어나는 시점

|  | 지금 | 이 MR 이후 |
|---|---|---|
| **쓸 때** (글이 올라올 때 · 취향이 바뀔 때 · 밤에 한 번) | 아무것도 안 한다 | **무겁게 계산해서 줄로 저장한다** |
| **읽을 때** (사람이 앱을 켤 때) | 온톨로지를 훑고 판정하고 정렬한다 | **저장된 줄을 그대로 낸다** |

이 방식을 **fan-out on write**(**쓰기 시 미리 뿌려두기** — 내용이 생기는 순간 그것을 볼
사람들의 목록에 미리 꽂아 넣는 것)라고 한다. 트위터·인스타그램 피드가 이렇게 돈다.

읽기는 **표 2개, 쿼리 2번**이 전부다. 조인 0회, 정렬 0회, 판정 0회.
이 비용은 **사용자가 몇 명이든 온톨로지가 얼마나 크든 안 변한다.**

## 🔴 설계에서 판단이 갈렸던 자리 넷 — 다음 사람이 알아야 하는 것

### ① 다시 만드는 동안 사람이 반쪽을 보는 문제 → **세대를 통째로 바꾼다**

미리 계산의 진짜 어려움은 "언제 계산하나" 가 아니라 **"다시 계산하는 동안 어떻게 하나"** 다.

순진한 방법은 이렇다:

```sql
DELETE FROM user_feed WHERE user_id = ?;   -- ← 이 사이에 앱을 켜면
INSERT INTO user_feed ...;                 --    빈 화면이나 반쪽을 본다
```

밤에 도는 배치라도 시차가 다른 사용자에게는 한낮이다.

**그래서 지우고 다시 쓰지 않는다.** 새 세대를 옆에 통째로 만들고, 다 만든 뒤에 "현재는
이것" 이라는 표시만 옮긴다. 배포에서 쓰는 **blue-green**(**새 판을 옆에 다 띄운 뒤 접속만
옮기는 방식**)과 같다.

```
1) BUILDING 으로 세대를 연다
2) 줄을 다 넣는다              ← 이 동안 읽기는 옛 세대를 본다. 영향 0
3) 한 트랜잭션에서:  옛 READY → SUPERSEDED,  새 BUILDING → READY
4) 옛 세대는 나중에 지운다 (줄은 함께 사라진다)
```

**3)에서 둘이 동시에 READY 인 순간이 없어야 한다.** 그것을 조건부 UNIQUE 색인
(**조건에 맞는 행들 사이에서만 중복을 막는 색인**)이 **DB 에서** 막는다:

```sql
CREATE UNIQUE INDEX uq_feed_build_ready
    ON feed_build (user_id, surface) WHERE status = 'READY';
```

애플리케이션의 조심성에 안 맡긴 이유 — 이걸 코드로만 지키면 언젠가 누가 순서를 바꾸고,
그 버그는 **재현이 거의 안 된다.** 사람마다 어느 세대를 볼지가 우연에 달리기 때문이다.

> 조건부 UNIQUE 색인은 PostgreSQL 에 있고 **MySQL 에는 없다.** ERD 초안이 MySQL 기준이라
> 이 자리가 원래 없었다 — S15P21E201-554 가 같은 상황을 겪었고 같은 결론을 냈다.

### ② 미리 만든 것은 낡는다 → **낡음을 숨기지 않고 알린다**

미리 계산의 대가는 **반드시 낡는다**는 것이다. 그래서 `feed_build` 에 무엇으로 만들었는지를
전부 박아 둔다 (취향 판 · 제약 스냅샷 · 온톨로지/정책/데이터셋/서비스 판 · 만료 시각).
**안 적어 두면 낡았다는 사실 자체를 알 수 없다.**

판단이 갈렸던 지점: **낡으면 안 보여줄 것인가?**

→ **보여준다.** 낡은 화면이 빈 화면보다 낫다. 어제 추천이라도 본 사람은 앱을 쓰고, 빈
화면을 본 사람은 앱이 고장 났다고 생각한다. 대신 응답에 `stale: true` 를 실어 보내
앱이 "새로고침" 을 띄울 수 있게 한다.

🔴 **다만 안전 제약은 이 논리가 안 통한다.** 알레르기가 걸린 추천이 낡은 피드로 나가면
안 된다. 그건 **읽을 때 검사하는 것이 아니라 제약이 바뀌는 그 순간에 세대를 만료시켜야**
한다 — 읽을 때 검사하면 조회가 늘어 이 MR 의 목적이 사라진다. **그 무효화 코드는 이 MR 에
없다** (아래 "안 한 것" 참고).

### ③ 화면 값을 어디까지 복사할 것인가 → **틀리면 헛걸음하는 값은 안 담는다**

`payload` 칸에 카드 하나를 그리는 데 필요한 값(이름·사진·한 줄 설명)을 **복사해** 둔다.
그래서 읽을 때 장소 표를 조인하지 않는다. 이게 "읽을 때 서버는 보여주기만 한다" 의 실제
구현이다.

이런 사본을 두는 것을 **비정규화**(**빠르게 읽으려고 같은 값을 일부러 두 곳에 두는 것**)라
한다. 대가는 명확하다 — **원본이 바뀌면 사본이 낡는다.**

🔴 **그래서 무엇을 넣지 않을지가 더 중요하다.** 가격·영업시간처럼 **틀리면 사람이 헛걸음하는
값은 안 넣는다.** 그건 상세 화면에서 그때 조회한다. 피드는 원래 "지금 이 순간의 진실" 이
아니라 "최근에 고른 추천" 이고, 그 선을 넘는 값을 사본에 담는 순간 이 설계는 거짓말을
하기 시작한다.

### ④ 취향 벡터를 기존 `preference_snapshot` 에 넣을 것인가 → **아니다. 다른 물건이다**

`preference_snapshot` / `preference_answer` 가 이미 있다(S15P21E201-554). 처음엔 거기
칸을 더하려 했는데, **층이 다른 물건**이다.

| | `preference_snapshot` (이미 있음) | `user_taste_vector` (이 MR) |
|---|---|---|
| 담는 것 | 사람이 화면에서 **고른 답 그대로** | 그 답 + 행동을 **숫자로 접은 것** |
| 있는 이유 | **재현** — 그때 뭘 보고 추천했나 | **속도** — 온톨로지를 다시 안 훑으려고 |
| 바뀔 때 | 사람이 설문을 다시 낼 때 | 접는 규칙이 바뀌거나 행동이 쌓였을 때 |

**원본을 대신하는 것이 아니라 둘 다 있어야 한다.** 접는 규칙은 앞으로 여러 번 바뀔 텐데,
그때마다 원본에서 다시 접어야 한다. **원본이 없으면 다시 접을 수가 없다.**

## 🔴 이 MR 이 **일부러 안 한 것** — 다음 사람이 할 일

### 1. 피드를 실제로 채우는 코드가 없다 (가장 큰 것)

표와 규칙만 만들었다. **무엇을 어떤 순서로 넣을지는 추천 엔진이 붙어야 정해진다**
(S15P21E201-543 이 `RecommendationEnginePort` 로 자리를 만들어 뒀다).

지어낸 점수로 채워 두지 않은 이유 — 그 값이 계약처럼 굳어서, 나중에 진짜 엔진이 붙을 때
**무엇이 임시값이었는지 아무도 모르게 된다.**

> **그래서 지금 이 API 는 모든 사용자에게 `NOT_BUILT_YET` 을 답한다.** 그게 정상이고,
> 프론트는 그 상태 화면을 먼저 그리면 된다.

### 2. 세대를 무효화하는 코드가 없다

다음 셋 중 하나가 일어나면 세대를 만료시켜야 하는데, 그 코드가 없다.

- 취향 판이 바뀌었다 → 새 취향으로 다시 만들어야 한다
- **제약(알레르기·휠체어)이 바뀌었다 → 🔴 안전 문제다. 가장 먼저 붙여야 한다**
- 만료 시각이 지났다 → 배치가 찾아서 다시 만든다 (`ix_feed_build_expiry` 가 그 조회용이다)

### 3. 커뮤니티 글 표(`post`)가 아직 없다

그래서 `community_feed.post_id` 에 FK(**다른 표의 행을 가리키는 제약**)를 **못 걸었다.**
없는 표를 가리키는 FK 는 만들 수 없고, 가짜 글 표를 여기서 만들면 커뮤니티 담당자와
**주인이 둘이 된다.**

S15P21E201-543 이 `preference_snapshot_id` 를 같은 이유로 FK 없이 두었던 것과 같은 판단이고,
그때처럼 **이름을 맞춰 뒀으므로** 글 표가 생기면 `ALTER TABLE` 한 줄이면 된다.

### 4. 옛 세대를 지우는 정리 배치가 없다

`SUPERSEDED` 세대는 지금 쌓이기만 한다. 사용자 수 × 세대 수 × 줄 수라 **저장 공간이 곱해진다.**
정리 기준(몇 세대까지 남길 것인가)은 운영 판단이라 정하지 않았다.

### 5. 인터랙션을 어디서 측정할지 안 정했다

취향 벡터를 행동으로 갱신하려면 "어느 화면에서 무엇을 셀 것인가" 가 필요하다.
**받는 창구는 이미 있다** — `POST /api/v1/events` 와 Outbox(S15P21E201-352). 없는 것은
**어떤 이벤트를 보낼지에 대한 합의**다. 화면 설계와 함께 정해야 한다.
