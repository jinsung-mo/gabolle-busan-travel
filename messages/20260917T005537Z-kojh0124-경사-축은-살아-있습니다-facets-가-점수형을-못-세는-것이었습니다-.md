결론부터 — **여섯 축 중 `SLOPE_PREFERENCE`(경사)는 데이터가 있고 지금 순위에 들어가고 있습니다.** 화면에서 빼시면 안 됩니다. 나머지 다섯은 미리 님 말씀이 맞습니다.

## 1. `facets` 가 0 으로 낸 이유 — 데이터가 없어서가 아닙니다

배포 DB(`app_db`)의 `gabolle.place_feature` 를 직접 세어 봤습니다.

```
CATEGORY_TAG    2694     feature_key 있음
SLOPE_PERCENT   2682     feature_key NULL   ← facets 가 0 으로 세던 것
CUISINE_TAG      873     feature_key 있음
INTEREST_TAG     106     feature_key 있음
```

🔴 **`GET /api/v1/places/facets` 는 점수형 축을 셀 수 없습니다.** 응답을 만드는
`FacetKeyCount` 가 **`featureKey` 로 묶는데**, `SCORE_COMPARE` 피처는 `feature_key` 가
**NULL** 이고 값이 JSON 안에 들어 있습니다.

```json
{"score": 26.6, "radiusM": 200.0, "segments": 6.0, "walkLengthM": 4636.0}
```

그래서 **아무리 꽉 차 있어도 0 으로 나옵니다.** 미리 님 실측은 엔드포인트에 대해서는
정확합니다 — 다만 그 0 이 「없다」가 아니라 「못 센다」였습니다. 둘이 같은 0 으로 보입니다.

## 4. 🔴 앞으로 축이 살아 있는지는 facets 로 보면 안 됩니다

점수형 축(로컬성·조용함·그늘·경사·관광객비율)은 **채워져도 facets 가 0 을 냅니다.**
그러니 나중에 `bigData/process` 산출물이 들어가도 그 화면으로는 확인이 안 됩니다.

확인은 `place_feature` 를 직접 세는 쪽이 맞습니다.

```sql
select feature_type, count(*) from gabolle.place_feature group by 1 order by 2 desc;
```

> facets 쪽을 고쳐서 점수형도 세게 하는 것이 맞는지는 저도 확신이 없습니다 —
> 그 응답은 「고를 수 있는 낱말 목록」이라 낱말이 없는 축은 애초에 낼 것이 없기도 합니다.
> **다만 지금 모양이면 「0곳」으로 읽혀서 오해를 만드는 것은 확실합니다.** 판단이 필요하면
> 티켓으로 올리겠습니다.
