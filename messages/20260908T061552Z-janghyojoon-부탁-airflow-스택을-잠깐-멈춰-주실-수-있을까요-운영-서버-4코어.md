## 부탁부터 — **아직 진짜 파이프라인이 안 붙었다면, 잠깐 멈춰 주실 수 있을까요**

만들어 두신 것을 지우자는 게 아닙니다. **`docker compose stop` 으로 잠깐 재우고,
쓸 때 다시 켜자**는 이야기입니다. 왜 그런지 오늘 서버에서 잰 것을 그대로 적습니다.

## 무엇을 쟀나

운영 서버(`j15e201`)에 SSH 로 들어가 `docker stats` 로 컨테이너별 CPU·메모리를
직접 봤습니다. 실측이고 추정이 아닙니다.

| | |
|---|---|
| 이 기계 | **4코어 · 15GB.** 컨테이너 **17개**가 떠 있습니다 |
| 개인화 스택 | Airflow 4개(api-server·scheduler·worker·dag-processor) · MLflow · MinIO · Postgres · Redis · 브로커 = **9개, 메모리 2.7GB** |
| 🔴 같은 기계에 | **GitLab CI 러너**가 systemd 로 돌고 있습니다 (`concurrent = 4`) |

## 🔴 그래서 무슨 일이 생기나

CI 잡이 동시에 4개가 되면 **서로를 2~3배 느리게** 만듭니다 (실측: `mr:gates`
3초→9초, `version` 7초→19초). 그때 **운영 서비스도 같이 느려집니다.**
4코어를 CI·서비스·개인화 스택이 나눠 쓰기 때문입니다.

## 그런데 개인화 스택이 지금 하는 일이

DAG 폴더에 파일이 **하나**뿐이고, 그 파일 첫 줄에 이렇게 적혀 있습니다.

```
수동 트리거 전용이다 (schedule=None) — 정기 실행용 DAG이 아니라
```

`sample_personalization_pipeline` — **사람이 눌러야 한 번 도는 본보기**입니다.
즉 **자동으로는 아무것도 안 돌고 있습니다.** 컨테이너 9개와 2.7GB 는 계속 잡고서요.

## 🔴 정정 — 제가 팀장께 과장해서 말씀드린 게 있습니다

처음에 *"`dag-processor` 가 코어 하나를 쉬지 않고 먹는다"* 고 말씀드렸는데,
**한 번 잰 값으로 판단한 것이었고 틀렸습니다.** 4초 간격으로 다시 재니 이렇습니다.

| 잰 순서 | dag-processor | scheduler |
|---|---|---|
| 1 | 0.79% | 3.57% |
| 2 | 1.27% | **102.30%** |
| 3 | 0.78% | 1.45% |

**상시 100% 가 아니라 30초마다 2~3초씩 튀는 것**입니다. 평균은 10% 안팎이고,
이건 DAG 파일 하나를 다시 읽는 정상 주기입니다. **바로잡습니다.**

## 그래도 봐 주셨으면 하는 것 둘

**1. 🔴 `airflow-api-server` 메모리가 942MB / 1GB — 한도의 94%입니다.**
조금만 더 쓰면 컨테이너가 죽습니다. 이건 지금도 위험합니다.

**2. 파일 하나 다시 읽는 데 2.26~3.11초 걸립니다.**
9KB 짜리 파일 하나치고는 깁니다. `lightgbm` · `mlflow` · `pandas` · `psycopg2` 를
파일 맨 위에서 불러오고 있어서로 보입니다 — Airflow 는 그 파일을 30초마다 다시
읽으므로, 그때마다 그 무거운 라이브러리를 전부 불러옵니다.
**함수 안으로 옮기면** 파싱은 빨라지고 실행에는 지장이 없습니다.

## 정리하면 부탁이 셋입니다

| | |
|---|---|
| **① 잠깐 멈추기** | 진짜 파이프라인이 붙기 전까지 `docker compose stop`. 4코어 서버에서 CI·서비스와 자리를 다투는 것을 줄입니다 |
| **② api-server 메모리 한도** | 1GB → 1.5GB 나 2GB. 지금 94%라 곧 죽습니다 |
| **③ 무거운 import 를 함수 안으로** | 급하진 않습니다. ①을 하면 자연히 미뤄집니다 |

🔴 **①은 이예승 님이 정하실 일입니다.** 곧 진짜 DAG 을 붙이실 계획이면 켜 두는
게 맞고, 그러면 대신 ②만 먼저 해 주시면 좋겠습니다. **이틀에 걸쳐 세우신 것이고
배관이 다 이어져 있는 걸 봤습니다 — 만든 것의 문제가 아니라 시점의 문제입니다.**
