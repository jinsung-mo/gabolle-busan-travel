## 지금 무슨 일이 일어나고 있나 (2026-09-16 운영 실측)

계정 삭제 기능은 **잘 만들어져 있다.** 그런데 **계정 줄 자체를 못 지운다.**

```
itinerary_versions.created_by   UUID  NOT NULL
CONSTRAINT fk_itinerary_version_created_by
    FOREIGN KEY (created_by) REFERENCES app_user (user_id)     ← ON DELETE 규칙이 없다
```

동행자가 있는 일정이면 그 사람의 판을 지우는 것이 **남의 편집 이력을 지우는 것**이 되므로 지울 수 없다. 그래서 개인정보만 비우고 계정 줄은 남긴다 — **옳은 판단이다.**

🔴 **그런데 그 결정이 안전망을 통째로 무력화한다.** `app_user` 를 가리키는 외래키 29개 중 **19개가 `ON DELETE CASCADE`** 인데, 계정 줄을 안 지우니 **한 번도 안 터진다.**

**결과: 탈퇴해도 표 14개가 남는다.**

| 남는 것 | 행수 |
|---|---|
| **저장한 장소** · 저장 모음 · 리뷰 · 방문 인증 · 팔로우 · 차단 | 1 · 1 · 0 · 0 · 0 · 0 |
| 공동작성 · 신고 · 초대 · 공유링크 | 0 · 1 · 확인 못 함 |
| 가입 티켓 · 메뉴판 사용량 · 중복요청 방지 | 12 · 0 · 45 |

행수가 작은 건 사용자가 28명이라 그렇다. **늘어나는 건 사람 수가 아니라 「한 사람이 남기는 종류」다** — 9/15 저장한 장소, 9/16 여행 이름.

## 부탁하는 것 — 새 마이그레이션 파일 하나

```sql
ALTER TABLE itinerary_versions ALTER COLUMN created_by DROP NOT NULL;

ALTER TABLE itinerary_versions DROP CONSTRAINT fk_itinerary_version_created_by;
ALTER TABLE itinerary_versions ADD  CONSTRAINT fk_itinerary_version_created_by
    FOREIGN KEY (created_by) REFERENCES app_user (user_id) ON DELETE SET NULL;
```

**이게 팀이 이미 고른 방식이다.** 9/7 협업 마이그레이션 주석에 그대로 적혀 있다:

> 계정 삭제가 여행 행을 직접 DELETE 하는데, **2026-09-05 에 새 외래키 하나가 그 삭제를 통째로 깨뜨린 적이 있다**(`itinerary_versions.created_by`). 그 자리를 여기서 다시 만들지 않는다 — 여행에 매달린 것은 CASCADE, **사람을 가리키는 보조 칸은 SET NULL**.

**9/7 에 만든 표들은 그 교훈을 적용해 피해 갔고, 9/3 에 만든 이 칸만 옛 방식으로 남았다.**
