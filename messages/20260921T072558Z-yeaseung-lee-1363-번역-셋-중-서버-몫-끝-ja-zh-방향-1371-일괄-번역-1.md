■ ② 서버 데이터(장소·축제·기록) — 일괄 번역 MR !1372

응답마다 Accept-Language 로 번역하는 쪽은 안 했습니다. 이유: 앱이 Accept-Language 로 ko/en 만
보내서(client.ts 의 apiLanguage) 서버가 ja 를 받을 일이 없고, 목록마다 LLM 을 수십 번 부르게 됩니다.

    POST /api/v1/tools/translate/batch
    { "direction": "KO_TO_JA", "texts": ["해운대", "광안리"] }
    → { "items": [ { "translatedText": "...", "cached": true, "status": "TRANSLATED" }, ... ] }
      items[i] 가 texts[i]

- 한 번에 20개까지. 목록을 20개씩 잘라 부르시면 됩니다
- status 가 TRANSLATED 가 아니면 translatedText 는 null → 원문을 보여 주세요
    SKIPPED = 시간 예산(20초)을 넘겨 안 불렀음. 실패가 아니니 나중에 다시 부르면 됩니다
    FAILED  = 업체 실패
- 전부 업체 실패면 502
- 같은 문장은 한 번만 옮기고, 단건 번역과 캐시를 나눠 씁니다(7일)
- 🔴 **로그인한 사람만 됩니다(단건과 같음).** 캐시에 없는 문장은 업체 비용이 나가서 익명
  출입증으로는 안 엽니다. 손님에게도 열지는 비용 판단이라 따로 정해야 합니다

■ ③ 동백이 답변 — 서버는 이미 됩니다. 앱이 ko/en 만 보내서 영어로 답하고 있습니다

서버(AssistantChatService.normalizeLanguage)는 ja · zh-Hans(zh-CN) · zh-Hant(zh-TW·zh-HK) 를
알아듣고, 각각 일본어·간체·번체로 답하라는 지시가 이미 있습니다.

그런데 앱이 Accept-Language 를 apiLanguage('ko' | 'en')로 보냅니다 —
OnboardingPreferences.tsx 가 setApiLanguage(resolveTextLanguage(language)) 로 ja·zh 를 en 으로
접어서 넘깁니다(「서버에 일본어 오류 문구가 없다」는 이유가 주석에 있습니다).

그래서 **동백이를 부를 때만이라도 실제 언어(ja · zh-Hans · zh-Hant)를 Accept-Language 에
실어 주시면** 바로 사용자 언어로 답합니다. 전체를 바꾸지 않고 그 호출만 바꾸면 오류 문구
걱정도 없습니다.
