## 무엇을

`recommendation_requested` **하나만으로는 실패한 추천이 이벤트에 안 남습니다.** 그래서 `recommendation_failed` 를 하나 더 만들었습니다. S15P21E201-543 브랜치에 구현과 테스트까지 들어가 있습니다.

## 왜 하나 더 필요한가

P0 데이터 명세 8.1 이 `recommendation_requested` 의 필수 데이터로 **전체 버전**(model·feature·ontology·dataset)을 요구합니다. 그런데 추천이 **버전을 알기도 전에** 죽는 경우가 있습니다.

- 추천 엔진이 꺼져 있음
- 엔진이 응답은 했는데 버전을 안 보냄

이때 버전 칸이 비어 있어서 그 이벤트를 만들 수가 없습니다. 그래서 **그런 요청은 이벤트 스트림에서 통째로 사라졌습니다.** 실패율을 재면 **서비스가 제일 안 좋았던 순간이 통계에서 빠집니다.**

반쪽짜리 envelope 을 내보내는 것(소비자는 그게 반쪽인지 모릅니다)보다, 버전을 요구하지 않는 이벤트를 하나 두는 쪽을 골랐습니다.

## 계약

| | |
|---|---|
| eventType | `recommendation_failed` |
| 생산자 | **BE Outbox** (업무 저장과 같은 트랜잭션) |
| aggregate | `recommendation` / `request_id` |
| partitionKey | `user_id` |
| occurred_at | **실패한 시각** |
| 멱등 | `event_id` 가 PK — 재처리해도 행이 하나 |

payload:
```
request_id · job_id · job_type · user_id · trip_id · itinerary_id
requested_at                                       ← 요청 시각
error_code · failure_stage · timeout_occurred · retryable · retry_count
total_latency_ms · generated_candidate_count · eligible_candidate_count
model/feature/ontology/policy/dataset/service/app_version · deployment_environment   ← 🔴 nullable
```

🔴 **`occurred_at`(실패 시각) − `requested_at`(요청 시각) = 얼마나 버티다 죽었는가.** 타임아웃 분석에 그 값이 필요해서 둘을 나눠 뒀습니다.

## 언제 무엇이 나가는가

| 상황 | requested | failed |
|---|:-:|:-:|
| 성공 | O | — |
| 버전 확보 **뒤** 실패 | O | O |
| 반환 후보 0건 | O | O |
| 버전 확보 **전** 실패 | — | O |

둘은 서로를 대체하지 않습니다. 하나는 "이 버전으로 요청이 있었다", 다른 하나는 "그 요청이 이렇게 끝났다" 입니다 — P0 명세 2.3 의 "원자 이벤트를 보존한다" 그대로입니다.
