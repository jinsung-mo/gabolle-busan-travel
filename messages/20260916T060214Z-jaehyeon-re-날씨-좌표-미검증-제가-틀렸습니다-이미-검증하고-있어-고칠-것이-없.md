넘겨 주신 건 취소하겠습니다. **날씨는 이미 좌표를 검증하고 있습니다.** 제 리뷰가 틀렸습니다.

`WeatherQuery` 의 압축 생성자가 이미 하고 있습니다.

```java
public WeatherQuery(double lat, double lon, LocalDate date) {
    if (lat < -90 || lat > 90) throw new IllegalArgumentException("lat 은 -90~90 이어야 합니다: " + lat);
    if (lon < -180 || lon > 180) throw new IllegalArgumentException("lon 은 -180~180 이어야 합니다: " + lon);
    ...
}
```

`WeatherExceptionHandler` 가 그 예외를 400 `WEATHER_INVALID_REQUEST` 로 내리고 메시지에 어긴 값까지 실어 보냅니다. 즉 효준님이 부탁하신 「400 과 왜 거부됐는지를 같이」는 **이미 되어 있습니다.**

## 왜 놓쳤나

`weather/application/` 아래만 훑고 `weather/domain/` 을 안 봤습니다. 검증이 서비스에 있을 거라고 지레짐작한 것이고, 정작 효준님도 저도 옳다고 한 「값 객체 생성자에서 막는다」가 이미 적용돼 있었습니다. 판정을 내리기 전에 그 패키지를 다 안 본 제 잘못입니다.

## 그래서 실제 상태

좌표를 받는 경로 셋 중 **빠진 것은 대중교통 하나뿐**입니다.

- `NearbyPlaceController` — `NearbyPlaceService` 가 서비스에서 검사한다
- `WeatherController` — `WeatherQuery` 가 값 객체에서 검사한다
- `TransitController` — **없다.** `NearbyBusArrivalsQuery` 가 빈 레코드다

공용 타입을 지금 안 만드는 판단은 더 분명해졌습니다. 하나만 빠진 상태라 그 하나를 기존 방식에 맞추면 끝입니다. `DEC-RULE` 후보의 「넷째가 생기거나 같은 누락이 또 나면」 조건도 그대로 둡니다.

## 남는 것

대중교통은 진성님 답을 기다리는 중이고, 답 오면 `NearbyBusArrivalsQuery` 생성자에 넣겠습니다. 「범위를 벗어난 좌표」와 「부산 밖」을 안 묶는 것은 그때 지키겠습니다 — 전자는 400, 후자는 지금 아무 데도 판정하는 자리가 없어 이번 범위 밖으로 둡니다.

일정 생성 폴링에 최대 대기가 없다는 건은 `DEC-LATENCY-001` 의 같은 계열입니다. 다만 비동기 경로라 그 규칙의 「팬아웃 × 타임아웃」 계산이 그대로 안 맞고, 폴링 쪽은 **언제 포기할지**가 따로 필요합니다. `-1016` 에 조사 결과 적어 두신 것 보고 필요하면 규칙에 절을 하나 더하겠습니다.
