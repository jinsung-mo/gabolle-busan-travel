Follow-up to your fix for issue 7 (1781). I fixed the remaining half myself, since it's in the same file you worked on.

**What was still wrong (English UI)**
- 1781 adds English names to **search results** only. The **suggestion lists** shown before typing are hard-coded (`MAJOR_BUSAN_ORIGINS`, `RECOMMENDED_LODGING_AREAS` in `origins.ts`) and had no `nameEn`. So From showed "부산역 (Busanyeok)", even though the DB has "Busan Station".
- The lodging-area description lines ("바다 앞 호텔·리조트가 모여 있어요") were Korean on every screen.
- Picking "Busan Station" from search still gave the chip "From 부산역". `pickOrigin` kept only the Korean name.

**What MR !1806 does** (merged into front/dev as `3ad045544`)
- Adds `nameEn` to the preset constants. 부산역, 해운대해수욕장 and 광안리해수욕장 use the same spelling as `place.name_en`.
- The 4 description lines now go through `tx` + `translations.ts`, with ja / zh-Hans / zh-Hant added.
- When a place is picked, its English name is kept in a separate display-only field (`originEnglish`, `lodgingEnglish`), stored together with the Korean name it belongs to. If the Korean name changes elsewhere, the old English name is ignored automatically.
- Chips and field labels use `stopNameForLanguage`. The one-line summary pill uses the English name alone ("Busan Station · Haeundae · 9.28…"): with the parentheses, the dates got cut off at 375 px.
- **Unchanged:** the request sent to the server (a test checks the JSON is byte-identical), the Korean screen, and the Korean addresses under search results.

**Checked:** typecheck, all 3 translation/button checks, build:web and full jest all exit 0 (2,161 tests), and the MR pipeline passed. Screenshots at phone and wide widths are in the MR. **Not checked on a real device.** It won't be in the Play/iOS builds until the next build.
