B5(비로그인 홈 날씨 404) 끝났다. 운영 서버에 직접 들어가 재서 확정했다. **코드는 한 줄도 안 고친다.**

## 잰 것

```
운영 로그 00:05  ERROR  날씨 미리받기가 99칸 전부 실패했습니다
컨테이너 안에서 기상청 직접 호출 → SERVICE_KEY_IS_NOT_REGISTERED_ERROR (코드 30)
```

키 두 개를 서비스 두 개에 교차로 걸어 봤다.

| | 기상청 단기예보 | 관광공사 |
|---|---|---|
| 젠킨스에 든 키 (63자) | ❌ 등록 안 됨 | ❌ 등록 안 됨 |
| 팀이 실제로 쓰는 키 (88자, `bigData/.env` 의 `DATA_GO_KR_KEY`) | ❌ 등록 안 됨 | ✅ **`resultCode 0000 OK`** |

## 결론 — 고장이 둘이다

1. **팀의 진짜 키는 살아 있는데 「기상청_단기예보 조회서비스」에 활용신청이 안 돼 있다.** data.go.kr 은 서비스마다 따로 신청해야 한다(자동승인 10~30분)
2. **젠킨스 자격증명 `gabolle-kma-service-key` 에는 아예 다른 63자짜리 죽은 값이 들어 있다.** 어느 서비스에서도 인식이 안 된다

배제한 것: 환경변수 전달(컨테이너 안에 들어가 있다) · 이중 인코딩(인코딩해서 불러도 같은 답) · `@EnableConfigurationProperties` · `@EnableScheduling` · 캐시 열쇠 불일치. **백엔드 코드는 전부 정상이고 바깥에서 거절당하는 것뿐이다.**

## 할 일 (둘 다 콘솔 작업, 내가 못 한다)

1. `data.go.kr` 에서 **기상청_단기예보 조회서비스 활용신청** — 계정 주인이 누른다
2. 젠킨스 자격증명 `gabolle-kma-service-key` 를 **88자 키로 교체** → 백엔드 재배포

그러면 다음 정시 5분 미리받기에서 캐시가 차고 404 가 사라진다.

## 🔴 덤 — 호출량이 문서보다 두 배다. 한도에 여유가 적다

소스 주석과 인수인계 문서는 **격자 51칸 · 하루 408회**라고 적고 있는데, **운영 로그의 실제 숫자는 99칸**이다. 하루 8회 발표니까 **792회**다.

data.go.kr 개발계정은 **오퍼레이션당 하루 1,000건**이다. 792/1,000 — 넘지는 않지만 **여유가 20%뿐**이고, 여기에 사람이 로그인해서 부르는 몫이 더해진다.

줄이려면 **설정만 바꾸면 된다** (`gabolle.weather.prefetch.lat-min/lat-max/lon-min/lon-max` 를 좁히거나 `enabled=false`). 코드 수정 없다. **다만 키가 살아난 뒤에 재고 정하는 게 맞다** — 지금은 전부 실패라 실제 소모량을 모른다.
