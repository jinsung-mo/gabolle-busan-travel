# 산출물 형식 — 기존 모양에 맞추는 게 낫다

`PlaceFeatureNdjsonReader` 가 지금 읽는 한 줄은 이렇다.

```json
{"placeId":"MA0101…","raw":"mid","band":"MID"}
```

**칸 이름이 `placeId` 다** (상가업소번호가 들어간다). 그리고 `Fact(storeId, featureType, value)` 로 접는데, **`featureType` 을 파일에서 읽지 않고 리더가 `"PRICE_LEVEL"` 로 박는다.**

그래서 네 형식을 이렇게 맞추는 걸 권한다.

```json
{"placeId":"126508","slopePercent":16.4,"segments":37,"walkLengthM":4820,"radiusM":200}
```

- 🔴 **`contentid` 대신 `placeId` 로.** 리더가 이미 그 이름을 읽고, 출처 구분은 `sourceType` 인자가 한다 — 파일이 그걸 또 말할 필요가 없다
- **`featureType`·`evidenceStatus` 는 파일에서 빼도 된다.** 리더가 박고 로더가 ESTIMATED 로 넣는다. 파일에 있으면 두 곳이 같은 것을 말하게 되고, 어긋나면 어느 쪽이 진짜인지 모르게 된다
- **`segments`·`walkLengthM`·`radiusM` 은 꼭 남겨라.** 가격대가 `{"band":..,"raw":..}` 로 원본을 같이 남기는 것과 같은 이유다 — **접는 것은 나중에도 하지만 펴는 것은 못 한다.** 「이 장소가 왜 16.4% 인가」를 되짚을 유일한 근거다

**내가 읽는 쪽이지만 이건 네 판단이 우선이다.** 위 이유가 안 맞으면 네 형식대로 가고 나한테 알려만 줘라.

# 네 계획 넷에 대한 의견

1. **place id 를 `sourceType` 으로 가르기** — 맞다. 다만 🔴 **모르는 `sourceType` 이 오면 조용히 넘기지 말고 터뜨려라.** 기본값으로 SBIZ 를 쓰면 엉뚱한 UUID 가 만들어지고, **그 행은 존재하지 않는 장소를 가리킨 채 아무 오류도 안 낸다**
2. **경사 매퍼 추가** — 맞다
3. **`PlaceSlopeLoaderRunner`** — 맞다. `@ConditionalOnExpression` 으로 안 도는 것까지 기존 모양과 같게
4. **시험** — 🔴 **TOURAPI·SBIZ 두 출처가 서로 다른 UUID 를 만드는지**를 못 박아라. 이게 이번 변경의 핵심이고, 틀려도 컴파일되고 서버도 뜬다

**경사는 안전 속성이 아니라 `ESTIMATED` 가 허용된다** — 계단·알레르기·식이·접근성은 DB 제약이 추정을 금지하니 그 넷은 이 경로로 넣지 마라.
