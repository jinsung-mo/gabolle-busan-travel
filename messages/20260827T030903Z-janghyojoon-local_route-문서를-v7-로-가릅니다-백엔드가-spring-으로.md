## 1. 무엇이 정해졌나 — 셋

### (1) 디자인 — 처음부터 간다 (예승 님 판단대로)

기획자이신 예승 님이 **"처음부터 가자"** 고 하신 걸 그대로 따랐습니다.
다른 세션에서 **Astryx**(메타가 2026-06 에 공개한 디자인 시스템 — 색·간격·글꼴·컴포넌트를
우리가 정의하지 않고 그대로 가져다 쓰는 완성품. MIT 라이선스)를 실제로 설치해서
여행 홈 화면을 만들고 빌드까지 통과시킨 기록이 `docs/DESIGN_SYSTEM.md` 에 있습니다.

**그래서 기존 프론트 코드(`ref/local-route/web`, 7,347줄)는 안 씁니다.**

### (2) 백엔드 — Node/Express 가 아니라 **Spring** 입니다

이유가 셋입니다.

| | |
|---|---|
| **사람** | **모진성 님이 Node.js 를 못 씁니다.** 6명 중 한 명이 첫날부터 못 들어오는 스택은 고를 수 없습니다 |
| **취업** | Spring 이 취업 관점에서 훨씬 잘 쓰입니다. 이건 프로젝트가 끝난 뒤에도 남는 이득입니다 |
| **속도** | **우리가 이미 익숙합니다.** 9월 마감이 있는 판에서 배우면서 만드는 건 두 배로 비쌉니다 |

그리고 저장소가 이미 그렇게 선언돼 있었습니다 — `backend/README.md` 에
"Spring Boot + Gradle · Java 18 · MySQL". 재현 님이 8/25 초기 구조 커밋에서 적어 둔 것입니다.

### (3) 앱 — Expo 를 쓸지 조사했습니다

**왜 조사했나.** 계획서 v6 이 Expo 를 전제로 쓰여 있는데, Expo 에는 오래된 평판이
하나 있습니다 — *"쓰기는 편한데 네이티브 기능이 필요해지면 결국 걷어내야 한다"*.
우리 앱은 지도·카메라·음성·위치를 다 씁니다. **그 평판이 지금도 맞다면 Expo 는
초반만 빠르고 후반에 일정을 통째로 날립니다.** 그래서 확인이 필요했습니다.

**결과: 그 평판은 이제 틀렸습니다.**

- Expo SDK 53 부터 **CNG**(Continuous Native Generation — 네이티브 프로젝트를
  설정에서 그때그때 만들어 내는 방식)가 들어가면서, **Expo 가 안 싸 주는 네이티브
  모듈도 걷어내지 않고 그대로 붙일 수 있습니다**
- Swift·Kotlin 코드를 Expo 프로젝트 안에서 직접 쓸 수 있습니다
- 2026 기준 정리 글들이 공통으로 *"예전의 '네이티브가 필요하면 bare 로 가라'는
  판단 기준은 더 이상 적용되지 않는다"* 고 말합니다

→ **Expo 로 갑니다.** 다만 이건 웹 조사 결과라, 우리 요구(카카오 지도 네이티브 SDK ·
한국어 STT/TTS)로 **실제로 한 번 돌려보고** 확정하는 게 맞다고 봅니다. 문서에는
`[확인함]`(공식/공개 문서 확인) 표기로 넣고, 실기기 확인 전까지는 `[미정]` 으로 둡니다.
