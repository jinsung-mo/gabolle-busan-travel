## 🔴 다만 말씀하신 그 형태로는 안 막힙니다

```sql
UNIQUE (place_id, feature_type, feature_key)   -- ← 이것만으로는 부족합니다
```

`feature_key` 가 nullable 이라서요. **PostgreSQL 은 NULL 을 서로 다른 값으로 봅니다.**
그래서 키가 없는 피처 — 점수형·참거짓형 전부(`SHADE_SCORE`·`LOCALITY_SCORE`·
`STAIRS_PRESENT` 등 여덟) — 가 **제약을 그냥 빠져나갑니다.** 같은 장소의 그늘 점수를
열 번 넣어도 다 들어갑니다.

태그형(`INTEREST_TAG` 등 여섯)만 막히고 나머지는 안 막히는, **절반만 동작하는 제약**이
됩니다. 그리고 안 막히는 쪽이 "현재 값 하나" 가 제일 중요한 쪽입니다.

`preference_snapshot` 에서 제가 같은 함정을 밟았습니다. `UNIQUE (trip_id, version)` 을
걸었더니 `scope='USER'` 행(`trip_id IS NULL`)이 전부 빠져나갔습니다. 같은 방법으로 막았습니다.

```sql
CREATE UNIQUE INDEX uq_place_feature_keyed
    ON place_feature (place_id, feature_type, feature_key) WHERE feature_key IS NOT NULL;
CREATE UNIQUE INDEX uq_place_feature_unkeyed
    ON place_feature (place_id, feature_type) WHERE feature_key IS NULL;
```

**부분 색인**(**조건이 붙은 UNIQUE 색인. MySQL 에는 없습니다**) 둘로 나눠야 양쪽이 실제로
막힙니다. `-554` 에도 같은 것이 들어가 있고 `docs/DB-STANDARD.md` 3절에 적어 뒀습니다.

테스트로 양쪽을 따로 확인했습니다 — 키 있는 것(`INTEREST_TAG`/`SEA` 두 번)과 키 없는 것
(`SHADE_SCORE` 두 번) 각각 거부되는 것을.

## !156 이 그쪽 쪽에 영향 주는 것 하나

```

    → feature_key 가 반드시 없어야 합니다
```

섞이면 위의 유일성이 무의미해져서 같이 못 박았습니다. 장소 피처를 넣는 코드를 쓰실 때

안쪽 코드값(어떤 관심 태그가 있는지 등)에는 **CHECK 를 안 걸었습니다** — 명세 4.3 이
