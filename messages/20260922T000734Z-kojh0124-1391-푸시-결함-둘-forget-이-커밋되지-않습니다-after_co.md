## 1. `PushTokenService.forget()` 이 커밋되지 않습니다

`@TransactionalEventListener(AFTER_COMMIT)` 안에서 `@Transactional`(기본 REQUIRED)을 부르면 **이미 커밋된 트랜잭션에 합류**합니다. DELETE 는 실행되고 예외도 안 나지만 다시 커밋되지 않아 행이 그대로 남습니다.

경로: `TripPushNotifier.push()` → `pushTokens.forget(gone)` → `PushTokenService:117 @Transactional`

**이 저장소가 이미 아는 함정입니다.** `LoginAttemptGuard:49` 와 `PlaceFacetViewWriter` 가 정확히 같은 이유로 `Propagation.REQUIRES_NEW` 를 씁니다. `LoginAttemptGuard` 주석에 *「세는 일은 반드시 REQUIRES_NEW 여야」* 라고 적혀 있고요.

- 증상: Expo 가 `DeviceNotRegistered` 를 줘도 토큰이 안 지워집니다. 죽은 기기로 영영 헛발송이 계속됩니다
- 고침: `forget()` 에 `REQUIRES_NEW`. `tokensOf()` 도 같은 모양이라(읽기라 덜 위험하지만) 같이 보시는 게 좋겠습니다

## 2. `actorUserId` 가 null 이면 알림 전체가 버려집니다

`TripPushNotifier:70`(그리고 `:113`)이 이렇게 돼 있습니다.

```java
this.actorNames.resolve(List.of(event.actorUserId() == null ? "" : event.actorUserId()))
        .get(event.actorUserId());
```

null 을 **빈 문자열로 바꿔서** 넘기는데, `ActorNames.resolve` 는 `filter(Objects::nonNull)` 만 하고 빈 문자열은 그대로 `UUID.fromString` 에 넘깁니다 → `Invalid UUID string: ""` 로 터집니다. 그 예외를 이 메서드의 `try/catch(RuntimeException)` 가 먹어서 **그 변경에 대한 알림이 통째로 안 갑니다.**

(UUID 파싱을 넘겨도 다음 줄 `.get(null)` 이 `Map.of()` 에 대해 NPE 입니다 — 자바로 직접 돌려 확인했습니다.)

🔴 **null 을 막으려고 넣으신 방어가 오히려 그 예외를 만듭니다.** `ActorNames` 는 null 을 이미 걸러 주도록 만들어져 있고(그 javadoc 이 *「null 이 섞여 들어온다 … 거르지 않고 UUID.fromString 에 넘기면 그 자리에서 터지고」* 라고 적어 두었습니다), **값을 그대로 넘기면 됩니다.**

```java
this.actorNames.resolve(Collections.singletonList(event.actorUserId())).get(event.actorUserId());
```

`singletonList` 는 null 을 담을 수 있고, `resolve` 가 걸러 빈 맵을 주며, `HashMap.get(null)` 은 null 을 돌려줍니다. `personBody` 가 이미 `actorName == null` 을 처리하고 있어서 문구도 그대로 동작합니다.

**언제 null 인가**: `ItineraryDraftService:982` 가 `saved.createdBy()` 로 이벤트를 만드는데, 그 칸은 `ON DELETE SET NULL` 입니다(`ActorNames` javadoc). 사람이 직접 편집하는 동안은 안 비겠지만, null 을 막는 코드를 넣으셨다는 건 그 경우를 보셨다는 뜻으로 읽었습니다.

## 3. 검사가 이 둘을 못 잡습니다

`TripPushNotifierTest` 가 `PushTokenService` 와 `ActorNames` 를 **둘 다 목으로** 바꿔서, 트랜잭션 의미도 `UUID.fromString("")` 도 한 번도 안 지납니다.

*「이름이 없는 사람(탈퇴)의 편집은 여행 이름만 남는다」*(181행)가 있어서 이 경우가 덮인 것처럼 보이는데, 그 검사는 `resolve` 결과만 빈 맵으로 두고 **`actorUserId` 는 정상값**입니다. **이름 없음**과 **식별자 없음**은 다른 경우인데 앞의 것만 보고 있습니다. `actorUserId` 를 null 로 주는 사례 하나면 2번이 잡힙니다.

1번은 목으로는 못 잡습니다 — 진짜 DB 를 쓰는 검사에서 「보내고 나서 토큰이 정말 지워졌나」를 보셔야 합니다.
