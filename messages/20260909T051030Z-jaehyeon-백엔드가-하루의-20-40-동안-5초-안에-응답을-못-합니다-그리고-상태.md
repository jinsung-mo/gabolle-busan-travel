상태 페이지 숫자를 보다가 백엔드가 생각보다 나쁜 상태인 것을 찾았습니다. 인프라 쪽 판단이 필요한 자리라 넘깁니다.

## 1. "가끔 느림" 이 아닙니다

4시간 구간별 가동률이 이렇습니다.

| 구간 (UTC) | 상태 | 가동률 |
|---|---|---|
| 2026-09-08 20시 | down | 58.6% |
| 2026-09-09 00시 | down | 65.0% |
| 2026-09-09 04시 | down | 70.4% |
| 2026-09-09 08시 | down | 67.9% |
| 2026-09-09 12시 | slow | 79.8% |

수집기 기준으로 `down` 은 **5초 안에 응답을 못 했다**는 뜻이고 `slow` 는 1.5초 초과입니다. 즉 백엔드가 하루의 **20~40% 동안 5초 안에 건강검진에 답을 못 하고 있습니다.** 평상시 응답도 1.4초라 이미 느림 선에 붙어 있어서, 조금만 밀리면 넘어갑니다.

바깥에서 API 를 부르면 잘 답하니 눈에 안 띄었을 것 같습니다.

## 2. CPU 경합으로 보입니다

4코어 서버인데 **오늘 최대 부하가 코어 수의 3.49배**(`todayMaxRatio`)까지 갔습니다. 4코어에 부하 14입니다.

지속적으로 먹는 것은 컨테이너 쪽입니다 (최근 60분 평균).

| 컨테이너 | 평균 | 최대 |
|---|---|---|
| Airflow (작업 스케줄러) | 24.2% | 119.2% |
| Airflow 스케줄러 (작업 시각표) | 19.3% | 102.6% |
| Airflow 일꾼 | 6.4% | 100.9% |

Airflow 셋이 합쳐서 코어 반쪽을 상시로 쓰고 각각 순간 100%를 넘습니다. 거기에 CI 러너가 뜨면 순간 3코어를 씁니다. **PostgreSQL 은 한가해서 DB 가 원인은 아닙니다.**

## 3. 상태 페이지의 프로세스 표는 지금 사람을 오도합니다

이게 두 번째로 알려 드리려던 것입니다.

```
Node.js 프로그램   평균 107.9%   최대 124.0%   60/60 표본
docker            평균  93.9%   최대 203.3%   47/60
ps                평균  33.9%   최대 100.0%   21/60
```

이걸 보면 "뭔가가 2코어를 상시로 먹고 있다" 고 읽게 되는데, **셋 다 수집기 자신과 그것이 띄운 자식들입니다.**

`ci/status/collect-status.mjs` 가 `ps -eo pcpu,comm,cgroup --sort=-pcpu` 를 부르면서 **자기 PID 를 안 뺍니다.** 게다가 `ps` 의 `pcpu` 는 **프로세스 수명 평균**이라 방금 뜬 프로세스는 높게 찍힙니다. 수집기(node)가 매분 뜨면서 자기와 자기가 부른 `docker stats`·`ps` 를 1위·2위·3위로 올리고 있습니다.

고칠 방향은 자기 PID 와 자식 PID 를 제외하는 것이라고 봅니다. 지금은 이 표를 근거로 손대면 엉뚱한 것을 건드리게 됩니다.

## 4. 확인 못 한 것 — 메모리

**수집기가 메모리를 아예 안 잽니다.** `status.json` 에 CPU·부하는 있는데 메모리·스왑이 없습니다.

4코어 서버에 Airflow 셋, PostgreSQL 둘, MinIO, 백엔드, 프런트, CI 러너가 다 올라가 있습니다. 메모리 압박으로 JVM 이 GC 에 매달리거나 스왑을 타고 있으면 지금 증상(평소 1.4초, 가끔 5초 초과)과 잘 맞는데, **볼 데이터가 없어서 확정을 못 했습니다.** `S15P21E201-750` 에서 Airflow API 서버 메모리 한도를 1g→2g 로 올리신 걸 보면 이미 한 번 부딪힌 자리 같습니다.
