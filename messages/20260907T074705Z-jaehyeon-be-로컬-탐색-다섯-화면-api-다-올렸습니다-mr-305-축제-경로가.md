축제 응답의 각 항목에 `startDate`·`endDate` 와 여행 기간과의 교집합인 `overlapDates`(날짜 배열)가 옵니다. "여행 3일차에 열린다" 를 화면에서 계산하지 않으셔도 됩니다. `title`(회차 이름, 예: "2026 진주 남강유등축제")은 없으면 키 자체가 빠지고, 그때는 `nameKo` 를 쓰시면 됩니다.

`/facets` 는 이제 **여덟 갈래를 항상 다 돌려줍니다.** 데이터가 없는 갈래는 `count: 0` 이고 `labelKo`(한국어 이름)도 함께 옵니다. 갈래 목록을 화면 코드에 박지 않으셔도 되고, 이름이 바뀌어도 앱을 다시 배포하지 않아도 됩니다.

장소 상세에 여섯 칸이 늘었습니다 — `addressEn` · `photoUrl` · `photoSource` · `openingHours` · `priceLevel` · `resolvedLanguage`. **기존 열 개 칸의 이름·자리·타입은 하나도 안 바꿨습니다.**

`Accept-Language` 를 보내시면 상세와 택시 카드가 영문 이름·주소를 우선합니다. 영문 값이 없으면 한국어로 되돌리고 `resolvedLanguage` 가 `ko` 로 옵니다 — 그걸로 "이 장소는 아직 영문 정보가 없습니다" 안내를 하실 수 있습니다. 다만 q값 순위는 아직 안 봅니다. `ko;q=0.1,en;q=0.9` 처럼 뒤쪽 선호도가 높은 형태는 지금 한국어로 읽으니, 영어를 원하시면 `en` 을 앞에 두세요.

일정에 더하기는 **두 번 부르셔야 합니다.**

```
1) POST /api/v1/itineraries/{id}/items   → 201, 새 판 번호가 응답에 옵니다
2) POST /api/v1/itineraries/{id}/recalculate  본문 {baseVersion: 새 판 번호, dayIndex: 넣은 날}
```

한 번에 묶지 않은 이유가 있습니다. 더한 항목은 **시각이 비어서** 들어갑니다(`startTime`·`endTime`·`stayMinutes` 가 `null`, `dataStatus` 가 `UNKNOWN`). 이동 시간을 모르는 상태에서 서버가 시각을 만들면 화면에 확정된 값처럼 보이니까요. 시각은 재계산이 정합니다. 그런데 재계산 접수는 실패할 수 있습니다(제약을 하나도 답하지 않은 여행이 그렇습니다) — 두 일을 한 응답에 묶으면 판은 이미 만들어졌는데 "더하기 실패" 로 답하게 되고, 화면이 저장된 편집을 없는 것으로 다루게 됩니다.

그래서 화면은 이렇게 만드시면 됩니다. 1번이 201 이면 **항목은 이미 저장된 것**입니다. 2번이 실패해도 그 항목은 남고 시각만 비어 있으니, "시간은 아직 계산 중" 같은 표시로 두고 재계산을 다시 부르실 수 있습니다.

더한 항목은 **고정(locked) 상태**로 들어갑니다. 재계산이 그 날을 다시 채우면서 방금 고른 축제를 빼면 안 되니까요. 화면에 자물쇠 표시를 하실지는 판단에 맡깁니다 — 사용자가 직접 고정한 것과 구분하고 싶으시면 `reasonCodes` 에 `USER_ADDED` 가 들어 있습니다.

`dayIndex` 는 0 이 첫날입니다. 여행 기간을 벗어나면 400 `ITINERARY_DAY_OUTSIDE_TRIP` 입니다.
