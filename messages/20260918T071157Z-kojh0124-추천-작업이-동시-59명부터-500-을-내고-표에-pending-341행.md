## 실측 — 400명 동시 요청

```
POST /api/v1/trips/{tripId}/recommendation-jobs   × 400 동시

접수 응답:   202 → 59건   |   500 → 341건
표에 남은 행: SUCCEEDED 59 |  PENDING 341   (총 400)
```

**341건이 HTTP 500 을 받고, 341개 행이 `PENDING` 으로 남습니다.**

원인은 `RecommendationJobRunner.enqueue` 의 순서입니다 — 효준님도 아실 그 javadoc 이 *「저장이 완전히 커밋된 뒤에 비동기로 넘겨야 한다」* 고 적어 둔 그 순서입니다. 그 자체는 맞는데, 넘기는 쪽이 터질 때의 처리가 없습니다.

1. `jobRepository.save(job)` 커밋
2. `worker.execute(...)` 가 `TaskRejectedException` 을 던진다
3. **잡는 곳이 저장소에 0곳** (`grep TaskRejectedException` → 없음)
4. 컨트롤러까지 올라가 500, 행은 `PENDING` 으로 남는다

**그리고 정리하는 장치가 없습니다.** `@Scheduled` 는 메뉴판·개인정보·날씨 셋뿐이고 `recommendation_job` 을 보는 것이 없습니다. `expires_at` 칸은 저장만 하고 아무도 읽지 않습니다. 개인정보 정리도 이 표를 안 봅니다.

## 문턱이 왜 59인가

`recommendationJobExecutor` 가 core 2 / max 8 / queue 50 입니다. 8 + 50 = 58~59 가 상한이고 그 위는 기본 `AbortPolicy` 로 튕깁니다.

🔴 **부하 중 스레드 덤프를 10번 떠서 확인했는데 `rec-job-` 스레드가 매번 정확히 2개였습니다.** core 2 + 큐 50 이 50건을 다 삼켜서 **`maxPoolSize=8` 은 평소에 한 번도 안 깨어납니다.**

## 🔴 제가 앞서 계산으로 낸 것 중 틀린 부분

「50명이 동시에 누르면 16초」라고 했는데, 동기·비동기를 갈라 재 보니 구조가 달랐습니다. **접수 구간은 N 과 무관하게 평평합니다**(p95 71→140ms, N=1→50). Tomcat 스레드 200개가 나눠 받으니 거기는 병목이 아니고, 직렬화되는 건 비동기 꼬리뿐입니다.

그리고 **로컬 숫자를 운영으로 옮기면 안 됩니다** — 로컬은 장소가 79곳이라 엔진이 22ms 에 끝나고(서버 자기 측정), 운영은 2,762곳에 631ms 입니다. 29배 차이입니다. 16초는 *운영 지연 × 동시성 2* 로 계산한 값이고, 두 입력은 각각 확인됐지만 **그 곱을 로컬에서 재현한 것은 아닙니다.**

## 상의하고 싶은 것 넷

**① 지금 고칠 일인가요?**
운영에 `PENDING` 이 0건입니다 — 동시 59명에 도달한 적이 없어서 안 터진 겁니다. 사용자가 35명이니 평소엔 안 옵니다. 다만 **심사·시연에서 여러 명이 동시에 누르면** 그때 한 번에 드러나는 종류입니다. 시연 계획을 아시면 그게 판단 근거가 될 것 같습니다.

**② 붐빌 때 무엇으로 답해야 할까요?**
저는 **503 + `pollAfterSeconds`** 를 생각했습니다 — 그 칸이 이미 `RecommendationJobResponse` 에 있어서 새로 만들 게 없습니다. 대안은 (가) 행을 `FAILED`+`retryable=true` 로 표시하고 202 를 유지 (나) 큐를 키워서 거부를 미루기.

🔴 `CallerRunsPolicy` 는 아니라고 봅니다 — 작업이 **웹 요청 스레드에서** 돌아 Tomcat 스레드를 붙잡고, 비동기 Job API 의 약속을 깹니다.

**③ `corePoolSize` 를 올릴 거면 커넥션 풀이 같이 가야 합니다.**
`spring.datasource.hikari.maximum-pool-size` 가 **설정 자체가 없어서 기본값 10** 입니다(운영 DB 에 물린 커넥션을 세 보니 정확히 10개). 추천을 8개로 늘리면 웹에 2개만 남습니다. 효준님이 -1217 에서 **로컬 여유와 컨테이너 천장이 다르다**는 걸 먼저 겪으셨으니, 이쪽도 같은 함정이 있을 것 같습니다 — 커넥션을 20으로 올리면 Postgres `max_connections` 와 개인화 스택 몫도 같이 봐야 하지 않을까요.

**④ 표에 이미 쌓인 `PENDING` 은 어떻게 하나요?**
운영엔 없지만, 고치기 전에 한 번이라도 터지면 남습니다. 청소 스케줄러를 하나 두는 게 맞을지, 아니면 애초에 안 남게 하는 것으로 충분할지 — 후자면 「고칠 것」이 하나 줄어듭니다.
