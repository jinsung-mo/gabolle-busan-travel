## 결론 먼저

인수인계에 「운영 피드 사진 업로드 안 됨 — 출시 차단」으로 적혀 있던 건은 **원인이 확정됐고, 이미 고쳐져 있습니다.** 다만 고친 뒤로 아무도 다시 올려본 적이 없어서 아무도 그것을 모르고 있었습니다.

## 원인 — nginx 의 기본 업로드 한도 1MB

운영 접근 로그 전수 조사 결과, `POST /api/v1/uploads/story-image` 요청은 **딱 8건**뿐이었고 실제 파일이 실린 6건은 **전부 413(Payload Too Large)** 입니다.

```
13/Sep 11:38:38  401   ← 비로그인 시도 (정상 거절)
13/Sep 11:41:07  413
13/Sep 11:47:05  413
13/Sep 11:49:31  401
13/Sep 11:49:32  413
13/Sep 11:49:32  413
13/Sep 11:49:56  413
13/Sep 11:50:08  413
```

**413 을 낸 것은 백엔드가 아니라 nginx 입니다.** 요청이 Spring 에 닿지도 못했습니다. 그래서

- 백엔드 로그에 오류가 하나도 안 남았고 (그래서 「로그를 봐도 원인이 없다」가 됐습니다)
- MinIO `gabolle-photos` 버킷이 **객체 0개**이고
- 프론트·백엔드 코드 계약은 아무리 봐도 맞았습니다 — **실제로 맞습니다**

nginx 의 `client_max_body_size` 기본값이 **1MB** 입니다. 1600px·JPEG 0.85 로 줄여도 사진은 보통 그보다 큽니다.

## 이미 고쳐진 지점

`/etc/nginx/conf.d/upload-size.conf` 가 **2026-09-13 11:49:18** 에 만들어져 있습니다.

```
client_max_body_size 5m;
```

마지막 413 이 11:50:08 이니 **그 직후에 누군가 넣은 것**이고, 그 뒤로 413 은 한 건도 없습니다. 동시에 **업로드 시도도 한 건도 없습니다.** 버킷이 빈 것은 「고장나 있어서」가 아니라 「고친 뒤 아무도 안 올려봐서」입니다.

## 지금 실제로 뚫려 있는지 — 데이터 안 만들고 확인함

인증 없이(=데이터가 안 생기는) 요청으로 크기별 응답을 쟀습니다. 413 이 아니라 **401 이 오면 nginx 를 통과해 백엔드까지 갔다는 뜻**입니다.

| 보낸 크기 | 결과 |
|---|---|
| 2.2MB | **HTTP 401** — 2,200,199바이트 전부 전송됨 (통과) |
| 4MB | **HTTP 401** — 4,194,503바이트 전부 전송됨 (통과) |
| 5MB | HTTP 413 — 0바이트 (nginx 가 미리 끊음) |
| 6MB | HTTP 413 — 0바이트 |

## 현재 한도 사슬

| 층 | 값 | 출처 |
|---|---|---|
| 앱(클라이언트) | 1600px 로 축소 + JPEG 0.85 + **3MB** 하드 검사 | `src/social/imageResize.ts` (`MAX_UPLOAD_BYTES`) |
| nginx | **5MB** | `/etc/nginx/conf.d/upload-size.conf` |
| Spring | 파일 **3MB** / 요청 **4MB** | `application.properties` 110~111줄 |

세 층이 서로 모순되지 않습니다. 실효 상한은 **사진 1장 3MB** 이고 nginx 에 여유가 있습니다. **앱을 새로 빌드할 필요가 없습니다** — 고친 것이 서버 쪽이라 이미 설치된 빌드에도 그대로 적용됩니다.

## 남은 확인 한 가지

인증이 필요한 구간(MinIO 실제 기록 + 공개 URL 노출)은 제가 계정 없이 확인할 수 없었습니다. **앱에서 사진 한 장 올려보는 30초**면 끝납니다. 참고로 공개 경로 자체는 살아 있습니다 — 9/8 에 `/photos/e2e-test.txt` 가 200 으로 서빙된 기록이 있습니다.

## 덤 — 로그에서 같이 본 것

운영 nginx 로그에 외부 스캐너가 계속 두드리고 있습니다. `GET /image?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/`(**AWS 인스턴스 메타데이터를 훔치려는 SSRF 시도**)가 15회, `/.env`·`/.bash_history`·`/wp-content/uploads/` 탐색도 있습니다. 전부 인터넷 배경 소음 수준이고 우리 응답은 404 였지만, **`/image?url=` 같은 프록시 엔드포인트를 앞으로 만들 때는 사설/링크로컬 주소를 반드시 막아야 한다**는 점만 기록해 둡니다.
