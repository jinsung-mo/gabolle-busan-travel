아침에 보낸 `-830`(모바일 웹 팝업 차단) 말고 하나 더 만들었습니다. **`S15P21E201-832` — 설정에서 소셜 계정 연결.** 미리 님께 뒀습니다.

사용자가 애플 로그인을 해 보다가 짚은 것에서 나왔습니다. 계정을 `(provider, provider_subject)` 로 찾기 때문에 **같은 사람이 제공자를 바꿔 로그인하면 계정이 하나 더 생깁니다.** 애플로 만든 여행과 구글로 만든 여행이 서로 안 보입니다. 이메일로 두 소셜 계정을 잇는 일은 안 하기로 한 결정(`DEC-AUTH-010`)이 있어서 그 자체는 맞는데, **사용자가 스스로 이을 길이 화면에 없습니다.**

애플은 특히 나쁩니다. 기존 이메일/비밀번호 계정이 있을 때 "비밀번호 확인하고 연결" 을 제안하는 경로가 provider 이메일로 찾는데, 애플은 이메일을 아예 안 줘서 **그 제안조차 안 뜹니다.** 카카오도 기본 동의에서는 같습니다.

**서버는 이미 있습니다.**

```
POST /api/v1/auth/oauth/{provider}/link
```

`-690` 에서 만들어 뒀습니다. **로그인한 상태**에서 소셜 신원을 그 계정에 붙이고, 이메일을 전혀 보지 않으므로 애플·카카오에도 통합니다. 그 신원이 다른 계정에 붙어 있으면 409 `OAUTH_IDENTITY_TAKEN` 입니다.

`src/auth/authApi.ts` 에 이 경로를 부르는 함수가 없습니다. 거기 있는 `completeOAuthLink` 는 다른 것입니다 — 로그인 전에 409 받고 비밀번호로 붙이는 `POST /auth/oauth/link` 쪽입니다.

필요한 건 설정(마이페이지)에 연결된 소셜 목록과 "연결하기" 를 두고, 누르면 지금 로그인 흐름과 같은 제공자 인증을 지나 위 경로를 부르는 것입니다. 서버 쪽은 제가 더 만들 것이 없습니다.

**순서는 이게 애플 이메일 받아오기(`-833`, 제가 맡았습니다)보다 먼저입니다.** 애플 이메일을 받아와도 사용자가 "이메일 숨기기" 를 고르면 전달용 주소가 와서 구글 이메일과 안 맞습니다. 이 화면은 이메일을 안 보니까 그 경우에도 통합니다.

급한 순서로는 `-248`(추억 지도) 다음, `-830`(모바일 웹 팝업) 과 비슷한 자리로 봅니다. 다르게 보시면 말씀해 주십시오.
