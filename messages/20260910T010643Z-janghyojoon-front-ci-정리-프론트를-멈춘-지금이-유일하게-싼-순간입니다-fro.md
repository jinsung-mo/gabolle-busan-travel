## 1. 지금 무엇이 어긋나 있나 — 실측입니다

어제 CI 설정을 파트별 파일로 가르는 뼈대를 놓았습니다(S15P21E201-786). 그런데 **아직 한 파트도 자기 잡을 안 옮겼습니다.**

```
뿌리 .gitlab-ci.yml            873줄 · 최상위 18개   ← main·common·back·bigData·ai·map 전부 동일
뿌리 .gitlab-ci.yml (front)   1067줄 · 최상위 21개   ← front 만 셋 더
ci/parts/*.yml  여섯 개         각 3줄               ← 전부 자리표시자. 짐이 하나도 안 옮겨졌습니다
```

front 에만 있는 셋은 `workflow` · `frontend:dependency-scan` · `frontend:smoke` 입니다. 나쁜 뜻으로 넣은 게 아니라 **9월 3일·7일에 넣은 것이라 가르기 전**입니다 — 그때는 옮길 자리가 없었습니다.

**그대로 두면**: MR !476(`front/dev` → `front/main`)이 머지되고 다음에 `front/main` → `main` 이 올라가면, 프론트 전용 검사 둘이 **모두가 쓰는 파일**에 자리를 잡습니다. 망가지지는 않지만, 가르기로 한 이유가 한 발짝 뒤로 갑니다 — 다음에 여섯 파트를 올릴 때 사람이 손으로 풀 자리가 그만큼 남습니다.

## 2. 🔴 왜 하필 지금인가 — 표가 이미 0장이기 때문입니다

**표는 커밋 하나에 묶여 있어서, 그 브랜치에 커밋이 하나라도 더 올라가면 앞서 모인 표가 전부 효력을 잃습니다**(거버넌스 규칙 G3). 그래서 평소에는 "잡 옮기기" 같은 정리가 비쌉니다 — 표를 다 모아 놓고 커밋을 하나 더 올리면 처음부터 다시입니다.

그런데 지금은 **잃을 표가 없습니다.**

- `!476` 은 지금 `governance` 잡이 **실패**, 유효 찬성 **0 / 2** 입니다
- `front/dev` 헤드가 오늘만 세 번 움직였습니다 — `1a1c23f1` → `13f82101` → `fb2293b6`. 표가 그때마다 죽었습니다
- 그리고 **프론트 작업을 다 같이 멈추기로 했습니다.** 헤드가 안 움직이는 창이 열린 겁니다

**정리하고 → 그 위에서 표를 모으면, 이번엔 표가 삽니다.** 순서를 바꾸면 또 죽습니다.

## 3. 누가 하나 — front 담당 한 분만

**진미리 님**(front 담당)이 하시면 됩니다. 🔴 **다른 파트는 지금 같이 하지 마세요.** 동시에 하면 선점(같은 파일을 동시에 고치는 것을 막는 장치)에서 서로 거부당합니다. front 가 먼저 길을 내면 back·bigData·ai·map 이 같은 절차로 따라갑니다. 제가 옆에서 봐 드릴 수 있습니다.

## 4. 절차 — `docs/CI-SPLIT.md` 그대로입니다

```bash
npx -y axmap-cli@latest claim "ci/parts/frontend.yml" ".gitlab-ci.yml" \
  --task S15P21E201-786 --intent "frontend 잡을 파트 파일로 옮긴다"
```

**① 옮길 것은 잡 블록 둘, 117줄입니다.** (`front/dev` 의 `fb2293b6` 기준)

| 잡 | 뿌리 파일에서 | 줄 수 |
|---|---|---|
| `frontend:dependency-scan` | 271~322 | 52 |
| `frontend:smoke` | 323~387 | 65 |

통째로 잘라 `ci/parts/frontend.yml` 에 붙이고, 뿌리에서는 지웁니다. **파일 머리의 안내 주석은 지우지 마세요** — 그 아래에 둡니다.

**② 자리표시자 한 줄을 지웁니다.** 지금 `ci/parts/frontend.yml` 에 있는 `.frontend-part-placeholder` 는 *"파일이 비면 CI 전체가 죽는다"* 를 막으려고 넣어 둔 버팀목입니다. 진짜 잡이 들어오면 지워도 됩니다.

**③ 🔴 `workflow:` 는 옮기지 마세요.** 이건 프론트 잡이 아니라 **파이프라인 전체 규칙**입니다(새 커밋이 오면 돌던 파이프라인을 취소한다는 설정, 3줄). `default`·`stages`·최상위 `variables` 와 같은 자리라, 파트 파일에 넣으면 그 파트만 다른 규칙을 쓰게 되어 조용히 어긋납니다. **뿌리에 그대로 두시면 됩니다** — 오히려 `main` 으로 올라가면 모두에게 이롭습니다.

**④ 개수로 확인합니다.** 이 작업에서 가장 무서운 실패는 **잡이 조용히 하나 사라지는 것**입니다. 파이프라인은 초록인데 검사가 빠진 채로 통과합니다.

```bash
grep -c '^frontend:' .gitlab-ci.yml        # 옮긴 뒤 → 0 이어야 합니다
grep -c '^frontend:' ci/parts/frontend.yml # 옮긴 뒤 → 2 여야 합니다
```

**⑤ 🔴 CI Lint 는 `ref` 를 줘야 합니다.** 파일 내용만 보내면 GitLab 이 `include` 가 가리키는 파일을 **안 가져옵니다.** 그래서 `valid: true` 가 나오고, 실제 파이프라인에서 죽습니다 — MR !462 가 정확히 그렇게 잡 0개로 죽었습니다. **push 한 뒤에 `ref` 를 주고** 검사하세요.

**⑥ push → !476 파이프라인이 초록인지 먼저 보고 → 그 다음에 표를 부탁하세요.** 순서를 지켜야 표가 삽니다.
