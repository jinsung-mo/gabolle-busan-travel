## 🔴 그러면 왜 facets 가 0 인가 — 이름이 다릅니다

DB 에 있는 것은 `feature_type = 'SLOPE_PERCENT'` 입니다. `SLOPE_PREFERENCE` 라는 이름은 **DB 에 한 행도 없습니다.**

```sql
select feature_type, feature_key, count(*) from gabolle.place_feature
 where feature_type like 'SLOPE%' group by 1,2;

 SLOPE_PERCENT |  (null)  | 2682
```

그리고 백엔드 코드를 보면 둘은 **원래 다른 것**입니다.

```java
// BaselineCandidateScorer.java:174
applyAlignmentDimension(candidate, preferenceSnapshot, preferenceCodeMap,
    "SLOPE_PREFERENCE",   // ← 사용자의 취향 축 (TasteDimension)
    "slopePercent",       // ← 장소의 속성 (SLOPE_PERCENT 에서 온다)
    ...);
```

`SLOPE_PREFERENCE` 는 **사람이 경사를 어떻게 여기는가**(취향 축)이고, `SLOPE_PERCENT` 는 **그 장소가 얼마나 가파른가**(장소 속성)입니다. 추천 점수는 이 둘을 맞대어 계산합니다.

그러니 **facets 가 `SLOPE_PREFERENCE` 를 장소 수로 세고 있다면 그건 애초에 셀 수 없는 것**입니다 — 장소에는 그 이름의 특성이 없으니까요. 0 이 나오는 게 당연합니다.

## 확인 못 한 것 — 여기서 갈립니다

`GET /api/v1/places/facets` 를 직접 못 불렀습니다. 비회원 토큰 발급 응답 모양이 제가 예상한 것과 달라 `AUTHENTICATION_REQUIRED` 로 떨어졌습니다. 그래서 **facets 가 정확히 무엇을 세는지는 코드를 보셔야 합니다.**

제가 보기엔 둘 중 하나입니다.

1. **facets 가 취향 축 이름으로 장소를 세고 있다** → 세는 대상이 틀린 것. `SLOPE_PERCENT` 를 세도록 고치면 2,682 가 나옵니다
2. **facets 는 원래 취향 축 목록을 내는 것이고, 0 은 「이 축에 값을 넣은 사용자가 없다」는 뜻이다** → 그러면 장소 데이터와 무관하고, 온보딩에서 그 축을 안 묻고 있다는 뜻입니다

**1번이면 장소 쪽은 이미 다 준비돼 있습니다.** 2번이면 -1108(「온보딩 취향 여섯 중 넷은 붙을 장소가 없다」)과 같은 자리를 보는 셈이고요.
