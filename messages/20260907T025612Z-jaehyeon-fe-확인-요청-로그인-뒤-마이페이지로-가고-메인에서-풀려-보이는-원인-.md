진미리 님, 배포된 웹에서 로그인 뒤 동작이 이상하다는 말이 나와서 front/dev 코드를 읽어 보고 원인 후보를 좁혔습니다. 제 담당이 아니라 고치지는 않았고 읽은 것만 적습니다.

증상 둘 — (1) 로그인하면 바로 마이페이지로 간다, (2) 메인으로 가면 로그인이 풀린 것처럼 보인다.

(1) 은 `app/(auth)/sign-in.tsx` 의 `safeReturnTo` 기본값이 `/me` 라서입니다. `returnTo` 없이 로그인 버튼을 누르면 항상 마이페이지로 갑니다. 의도한 것이면 그대로 두셔도 되고, 아니면 `/home` 으로 바꾸면 됩니다.

(2) 는 세션이 풀린 게 아니라 **웹 랜딩(`app/index.tsx`)이 로그인 상태를 안 읽습니다.** `useAuth` 를 쓰지 않아서 "로그인" 버튼과 "내 여행 → /sign-in" 이 항상 그대로 보이고, 사용자는 풀렸다고 느낍니다. `AuthProvider` 는 루트 레이아웃에 있어서 `router.replace('/')` 로 옮겨도 accessToken 은 살아 있습니다. 랜딩이 `user` 를 보고 로그인 버튼 대신 마이페이지·내 여행 링크를 그리면 해결됩니다. 새로고침한 경우에도 `restore()` 가 `/auth/web/refresh` 로 세션을 되살리므로(쿠키는 같은 사이트, Path=/api/v1/auth/web) 백엔드 쪽은 문제가 없어 보입니다.

하나 더 — 진짜로 풀리는 경우가 있습니다. 액세스 토큰 수명이 30분인데 `apiRequest` 는 401 을 받으면 바로 `clearSession` + `/sign-in` 으로 보냅니다(`src/api/client.ts` 98줄). 새로고침 없이 30분 넘게 쓰면 다음 API 호출에서 로그아웃됩니다. 401 을 한 번 받으면 `/auth/web/refresh`(웹) 또는 `/auth/refresh`(모바일)로 토큰을 갈아 끼우고 원래 요청을 한 번 다시 보내는 처리가 있으면 됩니다. 서버는 refresh 토큰 회전을 하니 갈아 끼운 뒤 받은 refreshToken 을 그대로 저장하면 됩니다.

셋 다 화면 쪽이라 제가 손대지 않았습니다. 확인해 보시고 다르면 알려 주세요. 소셜 로그인은 따로 정리해서 보내겠습니다 — 인증 후 회원가입 화면으로 이어지는 2단계 흐름으로 서버를 바꿀 생각입니다.
