## 3. 🔴 UUID 지적 — 제가 틀렸습니다

`UUID.nameUUIDFromBytes()` 는 **v3(MD5)** 이고 v5(SHA-1)가 아닙니다. 제 앞선 쪽지가
"UUIDv5" 라고 쓴 것이 틀렸습니다. -544 에서는 v3 라고 정확히 적거나 SHA-1 로 v5 를
직접 계산하겠습니다. 파생 원본 문자열을 payload 에 남기라는 것도 그대로 하겠습니다.

## 4. 축을 못 정한 이벤트 둘 — API 명세 7장이 이미 답을 줍니다

명세의 이벤트 표에 중복·순서 기준이 적혀 있고, 그것이 곧 aggregate 입니다.

| 이벤트 | 명세의 중복/순서 기준 | PII 경계 | → `aggregate_id` |
|---|---|---|---|
| `editorial_pick_published` | pick별 `contentVersion` | 콘텐츠 ID만 | **`pickId`** |
| `feed_candidate_precomputed` | `pickVersion`+`biasVersion`+target | user/cohort key | **피드 대상**(`userId` 또는 `cohortId`) |

뒤쪽은 `aggregate_type` 으로 `USER_FEED` / `COHORT_FEED` 를 갈라 두면 어느 쪽 키인지
읽는 사람이 헷갈리지 않습니다.

주신 `ALTER TABLE` 은 그대로 유효합니다 — `ix_event_outbox_pending` 도 실제로 있습니다

다만 **통합 뒤 `requestId` 는 이미 `aggregate_id` 에 실립니다** —
`OutboxAppendCommand` 주석이 *"그 대상의 ID. 예: request_id"* 라고 적고 있고,
그 칸은 타입이 있고 색인도 있습니다(`ix_event_outbox_aggregate`).

`request_id` 를 따로 두면 **추천 이벤트는 같은 값을 두 곳에 갖게 되고, 둘이 어긋날 수
있습니다.** 그래도 칼럼은 필요합니다 — `place_like` 는 `aggregate_id` 가 `placeId` 라서
requestId 가 갈 자리가 없습니다.

**그래서 정할 것: 둘 다 채워질 때 어느 쪽이 정본입니까?**

제 제안은 **`request_id` 를 정본으로 두고, `aggregate_id` 는 그 이벤트의 대상만 담는다** 입니다.
그러면 추천 이벤트의 `aggregate_id` 는 `job_id` 나 `place_id` 가 되고 중복이 사라집니다.
-542 14장의 조인 쿼리도 축이 하나여야 "후보 → 노출" 이 한 길로 읽힙니다.

🔴 이 제안은 이미 머지된 그쪽 코드를 다시 건드리게 만듭니다(`OutboxAppendCommand` 호출부).
더 싼 길은 **추천 이벤트에서는 `aggregate_id` 를 정본으로 두고 `request_id` 는 aggregate 가
다른 것일 때만 쓰는 것**입니다. 그쪽 손이 덜 가는 대신 14장 조인이 `aggregate_type` 에
따라 `CASE` 로 갈립니다. 저는 조인 축을 하나로 두는 쪽을 골랐지만, 되돌리는 비용을

동의하시는 쪽을 알려 주시면 그 규칙을 컬럼 주석에 박고 `ALTER TABLE` 을 올리겠습니다.
