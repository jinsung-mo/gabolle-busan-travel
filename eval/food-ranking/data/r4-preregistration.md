# 라운드4 선등록 — 판정용을 열기 **전에** 적는다

**Jira** `S15P21E201-712` (후보 풀) · `S15P21E201-713` (배포 채점기 첫 채점) · **2026-09-07**

선등록(preregistration — *"판정용을 열기 전에 최종안·예상 성적·기준을 적어 두는 것"*)은
열어 본 뒤에 말을 바꾸지 못하게 하려고 쓴다. 라운드2·3 과 같은 자리다.

🔴 **이 파일을 쓴 시점에 `r4-holdout-access.log` 는 0줄이다.** 판정용 47곳은 한 번도
열지 않았다. 아래 예상 숫자는 전부 **조정용 111곳**(`r4-05-score.mjs`)에서 나온 것이다.

---

## 1. 무엇이 라운드3 과 달라졌나 — 두 가지다

| | 라운드3 | 라운드4 |
|---|---|---|
| 후보 풀 | 상가정보 "음식" **53,716곳** | **상가정보 ∪ OSM = 55,392곳** |
| 채점 대상 | 로지스틱 회귀 `m3` (우리가 맞춘 모델) | 🔴 **`BaselineCandidateScorer`** — 실제로 서버에 배포되는 코드 |

🔴 **두 번째가 이 라운드의 핵심이다.** 라운드1~3 의 성적은 전부 참고 구현
(`ref/local-route/recommend.ts`, SQLite)을 잰 것이다. 실제로 배포되는 것은 Spring 의
`BaselineCandidateScorer`(PostgreSQL) 이고, **그건 한 번도 채점된 적이 없다.**
지금까지 우리는 배포되지 않을 것을 재고 좋다 나쁘다 말해 온 셈이다.

## 2. 성공 기준 — 라운드1 에서 못 박은 값 **그대로**다

| | 지표 | 넘어야 하는 선 |
|---|---|---|
| 주 | Recall@200 (상위 200위 안에 정답이 몇 %) | **≥ 20%** |
| 부 | 순위 백분위 중앙값 (정답들이 위에서 몇 % 지점) | **≤ 33%** |

**둘 다 넘어야 성공이다.** 🔴 결과를 보고 낮추지 않는다.

## 3. 채점 대상 — 옮겨 적은 것이지 새로 만든 것이 아니다

`lib/baseline-scorer.mjs` 는 자바 `BaselineCandidateScorer` 를 그대로 옮긴 것이다.

```
총점 = 0.30·거리 + 0.20·관심태그 + 0.15·분위기태그 + 0.15·음식태그
     + 0.10·취향정렬(다섯 차원 가중평균) + 0.10·인기
     − 0.05 × 이동 경고 수                        (마지막에 max(0, ·))
거리항 = clamp01(1 − 거리m / 5000m)
```

🔴 **구할 수 없는 항은 0 이 아니라 아예 빠진다.** 그래서 피처가 하나도 없는 장소의
총점은 거리 항 하나뿐이고 최대 **0.30** 이다.

### 시나리오 넷

| 이름 | 무엇 |
|---|---|
| `무작위` | 기준선 — 아무 순서나 |
| **`asis`** | 🔴 **지금 배포하면 실제로 이렇게 된다.** `place_feature` 가 비어 있다 |
| `cuisine-한식` | 피처를 채웠다면 — 상가정보 업종을 음식 태그로 넣고 사용자가 "한식" 을 고른 경우 |
| `cuisine-일식` | 같은 조건, "일식" |

🔴 **`asis` 가 이 라운드의 주인공이다.** 나머지 셋은 그 옆에 두는 자다.

### 출발지

거리 항이 있으니 출발지가 있어야 점수가 나온다. 사용자가 0명이라 실제 분포를 모른다.
그래서 후보 풀 좌표에서 **씨앗 7054026 으로 100곳**을 뽑아 출발지로 쓴다.
🔴 관광지 몇 곳을 손으로 고르면 그 선택이 곧 결론이 된다. 그래서 안 고른다.

## 4. 🔴 판정용을 열기 전 예상 — 이 줄을 나중에 고치지 않는다

조정용 111곳에서 실제로 나온 값이 근거다.

| 시나리오 | 조정용 실측 R@200 | **판정용 예상 R@200** | 조정용 실측 중앙 | **판정용 예상 중앙** |
|---|---|---|---|---|
| 무작위 | 0.0% | 0 ~ 1% | 52.5% | 45 ~ 58% |
| **`asis`** | **0.2%** | **0 ~ 2%** (중심 0.3%) | **50.7%** | **44 ~ 58%** (중심 51%) |
| `cuisine-한식` | 0.3% | 0 ~ 2% | 41.2% | 33 ~ 50% |
| `cuisine-일식` | 0.7% | 0 ~ 3% | 45.4% | 38 ~ 54% |

| 판정 | 예상 |
|---|---|
| 주 기준(R@200 ≥ 20%) | 🔴 **못 넘을 것으로 예상한다** |
| 부 기준(중앙 ≤ 33%) | 🔴 **못 넘을 것으로 예상한다** |
| **최종** | 🔴 **실패로 예상한다.** 예상하고도 그대로 연다 — 예상이 맞는지도 기록이다 |

**왜 이렇게 낮을 것 같은가.** 지금 배포 상태에서 이 채점기가 실제로 쓰는 신호는
**거리 하나뿐**이다. 나머지 다섯 항은 곱할 상대가 없어서 빠진다 (5절). 거리는
"가까운 곳" 을 골라 주지 "맛있는 곳" 을 골라 주지 않는다. 무작위보다 나을 이유가 없다.

## 5. 🔴 왜 다섯 항이 빠지나 — 재기 전에 알아낸 것

| 항 | 왜 안 도나 | 근거 |
|---|---|---|
| 관심·분위기·음식 태그 (0.50) | ① `place_feature` 에 행을 넣는 코드가 **저장소에 없다.** 표·제약·대조표는 다 있는데 운영 코드·배치·시드·DAG 어디에도 INSERT 가 없다. 유일한 INSERT 는 테스트 픽스처 | 마이그레이션 `V20260907160000` 주석이 스스로 그렇게 적어 두었다 |
| " | ② 설령 채워도 — 앱은 취향 코드를 **맨 배열** `["SEA_BEACH"]` 로 보내는데 서버는 `{"codes":[...]}` 를 기대한다. `PreferenceJson.parseCodes` 가 `path("codes")` 로 읽으므로 **항상 빈 목록**이 나온다 | `frontend/src/api/tripApi.ts` ↔ `PreferenceJson.java` |
| " | ③ 설령 모양이 맞아도 — 앱 코드(`SEA_BEACH`·`CITY`…)와 서버 `InterestTagCode`(`FESTIVAL`·`NIGHT_MARKET`…)가 **아예 다른 어휘**다 | `taste.tsx` ↔ `InterestTagCode.java` |
| 취향 정렬 (0.10) | 앱은 1~5 정수를 보내는데 채점기는 0~1 을 가정한다. `1 − \|장소−취향\|` 에 3 이 들어가면 `clamp01` 이 0 으로 뭉갠다. 변환하는 코드를 **못 찾았다** | `Scale` 컴포넌트 ↔ `PreferenceJson.parseScore` |
| 인기 (0.10) | `POPULARITY_SCORE` 를 채우는 것이 없고, 채울 자료(방문수·리뷰수)도 우리에게 없다 | 위와 같다 |

🔴 **이 다섯 가지는 이번 라운드에서 고치지 않는다.** 넷은 백엔드·프론트 코드이고
(다른 파트라 별도 MR 이 필요하다), 하나는 없는 자료다. **여기서는 재기만 한다.**

## 6. 🔴 재기 전에 이미 알아낸 구조적 사실 — 채점기가 R@200 을 못 건드린다

서버는 후보 전부를 채점하지 않는다. `PlaceCandidateQueryService` 가

1. 경계상자로 최대 2,001행을 긁고 (🔴 이 쿼리에 `ORDER BY` 가 **없다** — 상한에
   걸리면 어느 행이 잘리는지 정해져 있지 않다)
2. 반경 5km 로 거르고
3. **거리순으로 정렬해서 앞 200곳만 남기고** (`candidateLimit` 기본 200)
4. **그 다음에** 채점기를 부른다

즉 `candidateLimit` 은 *"채점한 뒤 상위 200"* 이 아니라 *"거리순 200곳만 채점 대상으로
삼는다"* 는 뜻이다. **거리순 200위 밖의 정답은 점수가 아무리 높아도 영원히 안 보인다.**

조정용 실측: 반경 5km 안에 평균 **9,422곳**이 있는데 그중 200곳만 본다. 그래서
**실효 반경이 평균 502m · 중앙 304m** 다. 반경을 5km 로 잡아 놓고 실제로는 300m 를 본다.

그래서 이번 판정에서는 **두 가지를 따로 적는다.**

| | 무엇 | 성공 기준을 적용하나 |
|---|---|---|
| ① 전체 줄 세우기 | 후보 55,392곳을 점수순으로. 라운드1~3 과 같은 눈금 | 🟢 **이쪽에 적용한다** |
| ② 실제 배포 흐름 | 거리순 200곳 → 채점 → 상위 20곳 | 참고로만 적는다 |

②의 "후보 200 안에 든 정답" 은 **채점기와 무관하다.** 시나리오를 바꿔도 값이 같으면
그것이 곧 증거다 — 조정용에서 네 시나리오 모두 **0.20%** 로 같았다.

## 7. 판정용을 연 뒤에 **하지 않을 것**

- 채점기를 고치지 않는다 (고쳐야 할 것은 문서에 적기만 한다)
- 기준을 낮추지 않는다
- 정답표를 다시 만들지 않는다
- 분할 씨앗·출발지 씨앗을 바꾸지 않는다

## 8. 어떻게 여나

```bash
node --max-old-space-size=8192 r4-08-final.mjs --dry   # 예행. 조정용. 기록 안 남김
node --max-old-space-size=8192 r4-08-final.mjs         # 🔴 진짜. r4-holdout-access.log 에 1줄
```

**판정용과 함께 전체 158곳 성적도 같이 적는다.** 이번 라운드는 **맞추는 것이 없어서**
(채점기 가중치가 설정값으로 고정돼 있다) 조정용/판정용을 가르는 이유가 과적합 방지가
아니라 앞 라운드와의 눈금 맞추기다. 둘이 크게 다르면 표본이 작다는 뜻이지 과적합이 아니다.
