# 버스 온톨로지 — 지금 뼈대에 **타는 물건**이 없다

이것은 새 온톨로지가 아니라 [`ONTOLOGY.md`](ONTOLOGY.md) 의 **버스 쪽 확장 설계**다.
합쳐질 자리는 `config/ontology.jsonld` 하나이고, 이 문서는 **무엇을 왜 더하는지**다.

**온톨로지**(ontology — *"이 분야에 무엇이 있고 서로 어떤 관계인가"* 를 기계가 읽게
적어둔 것). 그리고 그 파일은 **스키마이지 데이터가 아니다** — 3절이 이것을 다시 말한다.

---

## 🔴 0. 선은 이미 그어져 있다. 다시 긋지 않는다

기존 원칙 그대로 간다 — **가능/불가만 담고, 좋다/싫다는 안 담는다.**

*계단이 있으면 휠체어는 못 지나간다* 는 누가 물어도 같은 답이라 담는다.
*12% 오르막 200m 와 평지 500m 우회 중 어느 쪽이 나은가* 는 사람마다 달라 안 담는다 —
짝 비교 실험이 정한다(`FIELD-STUDY.md`). 계수 자리는 `coefficientStatus: "미추정"`
이고 숫자를 넣으면 `test/verify-ontology.mjs` 가 **종료 코드 1** 로 막는다.

버스에서도 똑같다. *저상버스가 아니면 휠체어는 못 탄다* 는 담고,
*버스를 두 번 갈아타느니 20분 더 걷겠다* 는 안 담는다.

## 1. 빠진 것 하나 — 차량(Vehicle)

지금 뼈대는 `BusRoute`(노선)와 `BusStop`(정류장)이 있다. 그런데 **사람이 타는 것은
노선이 아니라 그 순간 온 차 한 대**다. 그리고 판정을 가르는 값이 전부 거기 붙어 있다.

어젯밤 실측으로 확인한 것 — BIMS 실시간 응답이 이것을 준다.

| 필드 | 뜻 |
|---|---|
| `seat1` · `seat2` | 빈 좌석 수 (앞차 · 뒷차) |
| `lowplate1` · `lowplate2` | **저상버스**(**바닥이 낮아 계단이 없는 버스**) 여부 |
| `bustype` | 급행 여부 |
| `carno` | 차량번호 — 같은 차를 시간에 걸쳐 잇는 열쇠 |

## 2. 다리 규칙 — 사람의 말을 관측값으로 번역한다

**사람에게는 정체성으로 묻고, 판정은 성분으로 한다.** 사용자는 *"캐리어 끌어요"*
한 번 말하고, 시스템이 그것을 아래로 번역한다. 화면에서 옵션이 폭발하는 자리를
규칙으로 옮기는 것이다.

| 사람이 말하는 것 | 필요한 능력 | 그것을 주는 관측값 | 출처 등급 |
|---|---|---|---|
| 캐리어를 끈다 | 짐 둘 공간 | `seat > 0` | **관측** (BIMS 실시간) |
| 휠체어다 | 계단 없음 | `lowplate = 1` | **관측** (BIMS 실시간) |
| 유모차다 | 계단 없음 | `lowplate = 1` | **관측** |
| 〃 접어야 하는가 | — | ❌ 없다 | 🔴 **운영기관 규정 — 미확인** |
| 시각장애 | 안내 방송·점자 | ❌ BIMS 에 없다 | **없음 → 모름** |

**좌석 0 을 왜 "짐 둘 곳 없음" 으로 읽나** — 좌석 수는 입석 혼잡을 안 알려 준다.
그런데 캐리어를 끄는 사람에게는 *좌석 0 = 통로에 서야 함 = 짐을 발 앞에 세워야 함*
이라, 우리가 던지는 질문에는 **오히려 더 정확한 신호**다. 이 해석 자체를 규칙 옆에
적어 둔다 — 안 적으면 다음 사람이 "혼잡도" 로 잘못 읽는다.

### 🔴 규칙마다 출처 등급을 박는다

| 등급 | 뜻 | 화면에서 |
|---|---|---|
| **관측** | 우리가 받은 실시간 값 | 그냥 보여준다 |
| **기관분류** | 부산시가 붙인 값 (`stoptype="관광"` 등) | 그냥 보여준다 |
| **법령** | 규정에 적힌 것 | 근거를 링크한다 |
| **추정** | 우리가 계산으로 만든 것 | 🔴 **추정이라고 화면에 쓴다** |

등급이 없으면 다음 사람이 추정을 관측으로 읽는다. 그게 이 파트가 지는 방식이다.

## 3. 🔴 개체를 넣지 않는다 — 온톨로지는 스키마다

*"오늘 14시 03분에 남포동에 온 5200호 차의 좌석은 3석"* 은 온톨로지에 **안 들어간다.**
그건 폴링 원자료(`data/raw/transit/*.ndjson`)에 있다.

온톨로지가 담는 것은 **"차량이라는 것이 있고, 그것에는 빈좌석수라는 속성이 있고,
그 값이 0보다 크면 짐공간이라는 능력을 준다"** 는 문장뿐이다.

섞으면 파일이 매일 커지고, 어느 줄이 규칙이고 어느 줄이 관측인지 아무도 못 가린다.

## 4. 🔴 모름을 1급 상태로 — 이 설계에서 제일 중요하다

`lowplate` 를 **모르는 차가 대부분**이다. 폴링을 안 한 노선, 응답에 필드가 빈 차,
아직 안 지나간 시간대. 여기서 두 가지 유혹이 있고 **둘 다 서비스를 거짓말하게 만든다.**

| 모름을 이렇게 처리하면 | 무슨 일이 나나 |
|---|---|
| **"아니오"로 친다** | 탈 수 있는 버스가 지도에서 **사라진다.** 휠체어 사용자에게 갈 길이 없다고 말한다 |
| **"예"로 친다** | 못 타는 차를 추천한다. **정류장에 나가서야 안다** — 제일 나쁜 실패다 |

그래서 값은 끝까지 **셋**이다 — `예` · `아니오` · **`모름`**.
JSON-LD 에서는 각 속성에 `nullable: true` 와 `codeList` 에 `모름` 을 명시한다.

> 어젯밤 만든 식이 제약 화면 설계안이 *"모름을 흐린 회색이 아니라 나머지 둘과 같은
> 크기의 목소리로"* 라고 한 것과 **같은 원리**다. 성분 자료가 0% 인데 모름을 안전
> 쪽에 붙이면 화면 전체가 거짓말을 한다.

## 5. 형식 — 기존 파일에 그대로 얹는다

```json
{
  "@id": "bm:LowFloorFlag",
  "@type": ["skos:Concept", "rdf:Property"],
  "inScheme": "bm:MobilityScheme",
  "onClass": "bm:BusVehicle",
  "prefLabel": { "ko": "저상버스 여부", "en": "Low-floor flag" },
  "definition": { "ko": "바닥이 낮아 계단 없이 오를 수 있는 차량인가." },
  "codeList": ["예", "아니오", "모름"],
  "codeListOpen": false,
  "nullable": true,
  "kind": "가능판정",
  "sourceField": { "dataset": "bims-realtime", "field": "lowplate1" },
  "evidenceStatus": "관측",
  "status": "미수집"
}
```

`status` 는 **`미수집`** 으로 시작한다. 정류소 도착정보 수집기가 아직 없기 때문이다
(`config/bims-assign.json` 이 그것을 "안 한다" 가 아니라 **"다음"** 이라고 적어 두었다).
**있는 척하지 않는 것**이 이 필드의 목적이다.

## 6. 검사 — 규칙을 문서가 아니라 코드에 둔다

`test/verify-ontology.mjs` 에 셋을 더한다. 어기면 **종료 코드 1**.

1. 가능판정 속성에 **`evidenceStatus` 가 없으면 실패** — 출처 없는 규칙을 막는다
2. `nullable: true` 인데 `codeList` 에 **`모름` 이 없으면 실패** — 4절이 무너지는 자리
3. `sourceField` 가 가리키는 데이터셋 이름이 **`config/sources.json` 에 없으면 실패** —
   지어낸 출처를 막는다

## 7. 아직 안 정한 것

| 무엇 | 왜 |
|---|---|
| 유모차를 **접어야 하는가** | 운영기관 규정을 안 봤다. 추정으로 채우지 않는다 |
| 시각장애 관련 값 | BIMS 에 없다. 다른 출처를 찾을지, 범위 밖으로 둘지 사람이 정한다 |
| `seat` 가 **없는 차량**의 비율 | 정류소 도착정보를 아직 안 받아서 모른다. 이 비율이 높으면 캐리어 판정 자체가 거의 `모름` 이 된다 |
