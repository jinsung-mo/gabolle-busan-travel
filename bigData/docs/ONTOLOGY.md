# 온톨로지 — 무엇을 담고 무엇을 담지 않았나

**2026-08-28 작성.** 산출물은 [`config/ontology.jsonld`](../config/ontology.jsonld) 이고,
이 문서는 **왜 그렇게 갈랐는지**다. 검사는 `node test/verify-ontology.mjs`.

**온톨로지**(ontology — *"이 분야에 무엇이 존재하고, 그것들이 서로 어떤 관계인가"* 를
기계가 읽을 수 있게 적어둔 것). 여기서는 부산에서 걷고 버스 타는 일에 등장하는
것들의 목록과, 각각이 어떤 값을 갖는지, 그 값으로 무엇을 판정할 수 있는지다.

---

## 🔴 0. 이 작업의 전부는 한 줄을 긋는 것이다

|  | 담당 | 온톨로지가 담나 |
|---|---|---|
| **가능 / 불가** (feasibility — 지날 수 있나 없나) | 딱딱한 규칙(hard rule) | ✅ **담는다** |
| **좋다 / 싫다** (preference — 얼마나 싫은가) | 짝 비교 실험 → 조건부 로짓 계수 | ❌ **담지 않는다** |

**계단이 있으면 휠체어는 못 지나간다.** 이건 누가 물어봐도 같은 답이고, 취향이 아니다.
그래서 온톨로지에 적는다.

**12% 오르막 200m 와 평지 500m 우회 중 어느 쪽이 나은가.** 이건 사람마다 다르다.
[FIELD-STUDY.md](FIELD-STUDY.md) 가 이미 정했다 — **이 가중치는 손으로 정하지 않고
사람에게서 추정한다.** 해운대·광안리에서 짝 비교(선택 실험)로 받은 응답에
**조건부 로짓**(conditional logit — 여러 대안 중 하나를 고른 기록에서 "각 속성이
선택에 얼마나 영향을 줬는가" 를 계수로 뽑아내는 통계 모델)을 적합시킨다.

> 🔴 **선호 가중치 숫자를 온톨로지에 박으면 그 결정을 뒤집는 것이다.**
> 그래서 계수 자리는 `coefficientStatus: "미추정"` 으로 비워 두고,
> 그 코드의 허용 목록에는 **`미추정` 하나밖에 없다.** 숫자를 넣으면 파일이 무효가 된다.
> `test/verify-ontology.mjs` 가 종료 코드 1 로 막는다.

담지 않는 이유는 순수함이 아니라 **고장의 종류가 다르기 때문**이다.
가능/불가를 잘못 적으면 갈 수 있는 길이 지도에서 사라진다 — 사용자가 알아챌 수 있다.
선호를 규칙으로 적으면 **길이 사라지는데 이유를 아무도 볼 수 없다.**
우리 제품은 *"왜 이 길인가"* 를 말해야 하는 제품이다.

## 1. 형식 — JSON-LD 위의 SKOS

**JSON-LD**(Linked Data 를 JSON 으로 쓰는 W3C 표준). 맨 위의 `@context` 가
`slopeP90` 같은 **짧은 이름을 전 세계에서 겹치지 않는 URI 로 펼치는** 사전이다.
그래서 백엔드는 짧은 이름으로 읽고, 나중에 다른 데이터와 합칠 때는 URI 로 맞춘다.

**SKOS**(Simple Knowledge Organization System — 어휘와 분류를 기술하는 W3C 표준).
개념마다 `skos:prefLabel`(대표 이름), `skos:definition`(뜻),
`skos:broader`(이것의 상위 개념은 무엇인가)를 붙인다.

세 가지를 지켰다.

| | |
|---|---|
| **이름은 한국어·영어 둘 다** | 팀은 한국어로 말하고 표준 도구는 영어를 읽는다. 하나만 있으면 한쪽이 못 쓴다 |
| **뜻이 없는 개념은 없다** | 이름만 있는 용어는 사람마다 다르게 읽는다. 그게 이 파트가 지는 방식이다 |
| **바깥 네트워크를 안 쓴다** | `skos:` · `qudt:` 는 **선언만 하고 가져오지 않는다.** 검사도 파일 안에서만 돈다 |

> 네임스페이스 URI(`bm:` 가 펼쳐지는 주소)는 **지금 브라우저로 열리지 않는다.**
> 이름이 겹치지 않게 하는 것이 목적이고, 어떤 스크립트도 그 주소를 부르지 않는다.

**단위 표기.** 값을 갖는 것에는 전부 `unit`(단위 코드) 또는 `valueRange`(값 범위)
또는 `codeList`(허용/관측 값 목록) 중 하나 이상이 붙어 있다. **단위 없는 숫자는
다음 사람이 반드시 잘못 읽는다.** QUDT(단위를 URI 로 적어둔 표준 어휘)의 IRI 는
확실히 대응되는 단위(m·min)에만 `unitIri` 로 붙였다 — **틀린 IRI 를 적는 것보다
비워 두는 것이 낫다.**

## 2. 뼈대

```
NetworkElement  경로 그래프를 이루는 것
├─ Segment          길 구간 ······ 지금 실제로 데이터가 있는 유일한 클래스
├─ BusRoute         버스 노선 ···· BIMS 폴링 중 (소급 불가)
├─ BusStop          버스 정류장
└─ Barrier          차단물 (계단·차단봉·문·턱)

EnvironmentFeature  구간 옆에 있어서 걷는 경험을 바꾸는 것
├─ Building         건물
└─ ShadeSource      그늘 원천
   ├─ StreetTreeSection   가로수 구간
   └─ BuildingShadow      건물 그림자 (계산으로 만든다)

UserProfile     이동 제약 프로파일
├─ Wheelchair  ├─ Stroller  ├─ Elderly  └─ Default
```

`UserProfile` 은 **무엇이 불가능한가만** 정한다. 무엇을 더 좋아하는가는 정하지 않는다.

### 🔴 그 위에 여행이 얹힌다 (2026-08-28 추가)

위의 뼈대는 전부 **길과 그 주변**이다. *"이 길이 어떤가"* 는 있는데
*"어디를 갈 것인가 · 언제 갈 것인가"* 가 한 칸도 없었다. 그래서 구간 단위로 만든 값이
**전부 떠 있었다** — 여행자의 하루에 붙일 자리가 없었다는 뜻이다.

```
Traveler        여행자 ······················ UserProfile 을 "갖는다" (대체하지 않는다)
   │
Itinerary       하루 일정 — 날짜를 갖는다
   │ (itineraryLegs)
Leg             이동 한 토막 — 출발→도착, 수단 하나, 🔴 시작 시각
   │ (legSegments)          (legMode)          (legFromWaypoint / legToWaypoint)
Segment ········ 이미 있던 것 ·· TravelMode ····· Waypoint
                                ├─ 걷기          ├─ Place ········ 갈 만한 지점
                                ├─ 버스          ├─ BusStop ······ 이미 있던 것
                                ├─ 도시철도      └─ StationEntrance
                                └─ 택시

Place ── placeCategoryOf ──▶ PlaceCategory
                             숙박 · 먹는 곳 · 전망/자연 · 문화/전시 · 상점/시장 · 여가/공원 · 여행 편의

Station          도시철도 역 ····· 호선 · 환승 여부 · (첫차막차는 아직 없다)
└─ StationEntrance  출입구 ······· 🔴 좌표를 갖는 단위는 이쪽이다
```

**이 층의 전부는 `Leg` 하나다.** 구간 값은 그것만으로 판정이 되지 않는다 —
사람이 고르는 것은 구간이 아니라 *"여기서 저기까지 어떻게 가느냐"* 이기 때문이다.
`Leg` 이 `Segment` 여럿을 묶어야 *"이 이동이 할 만한가"* 가 되고, `Itinerary` 가
`Leg` 을 묶어야 *"이 하루가 되는가"* 가 된다.

> 🔴 **그래서 그 사슬이 끊기면 검사가 실패한다.**
> `Itinerary → Leg → Segment` 로 내려가는 길이 없으면 `test/verify-ontology.mjs` 가
> 종료 코드 1 을 낸다. 접착제가 안 붙었다는 뜻이기 때문이다.

## 2.1. 🔴 장소와 정류장·출입구 — 왜 이렇게 갈랐나

정류장은 **길의 요소이면서 동시에 갈 수 있는 지점**이다. 이 둘을 어떻게 둘지가
이 층에서 가장 되돌리기 어려운 결정이라 여기 적어 둔다.

| 고를 수 있었던 것 | 왜 안 골랐나 |
|---|---|
| 정류장·출입구를 `Place` 의 **하위로** 넣는다 | 정류장이 관광지와 같은 것이 된다. *"오늘 갈 곳"* 목록에 정류장 수천 개가 섞인다 |
| 정류장·출입구와 `Place` 를 **완전히 나눈다** | *"역까지 걷는다"* 를 `Leg` 으로 적을 수 없다. 걷기의 끝점이 대부분 정류장·출구인데 그 자리가 없어진다 |
| ✅ **정체는 그대로 두고 역할만 공유한다** | 아래 |

고른 것은 세 번째다. **`Waypoint`**(경유 지점 — 이동 한 토막의 끝점이 될 수 있는 것)라는
역할 개념을 하나 만들고, 정체는 원래 자리에 남겨 두었다.

```
NetworkElement          (무엇인가 — 길의 요소)      Waypoint       (무엇을 할 수 있는가 — 끝점이 된다)
├─ BusStop ────────────────────────────────────────────┤
├─ StationEntrance ────────────────────────────────────┤
├─ Segment                                             │
└─ Station  ← 🔴 여기 없다                         Place
```

`BusStop` 과 `StationEntrance` 는 **상위를 둘 갖는다**(다중 상위 — SKOS 가 허용한다).
왼쪽은 정체이고 오른쪽은 역할이다. 그래서 정류장은 `Place` 가 **아니면서** `Leg` 의
끝점이 될 수 있다.

> 🔴 **`Station`(역 자체)은 일부러 `Waypoint` 가 아니다.**
> 역을 끝점으로 삼으면 거리를 **역 중심점**에서 재게 되는데, 서면·부산역은 출구끼리
> 수백 m 벌어져 있어 그 거리가 매번 틀린다. 걷기의 끝점은 언제나 **출입구**다.
> 같은 이유로 위도·경도 속성도 `StationEntrance` 에만 붙였고 `Station` 에는 안 붙였다.
> 이것도 검사가 붙잡는다 — `Station` 을 `Waypoint` 아래로 옮기면 종료 코드 1 이다.

## 2.2. 🔴 시각은 축이다 — `Leg` 이 갖는다

이미 만들어 둔 것 중 **시각에 따라 답이 달라지는 것**이 여럿이다.

| | 시각에 따라 무엇이 달라지나 | 지금 상태 |
|---|---|---|
| 건물 그림자 | 같은 구간이 정오에는 뙤약볕, 늦은 오후에는 그늘 | 시각별 칸이 이미 산출물에 있다 |
| 버스 소요시간 | 러시아워와 한낮이 다르다 | BIMS 관측이 쌓이는 중 |
| 장소 영업시간·휴무일 | 열려 있나 | **미수집** |
| 도시철도 첫차·막차 | 그 시각에 탈 수 있나 | **미수집** |
| 기온 | 그늘의 값어치가 달라진다 | **미수집** |

이것들을 하나로 묶을 자리가 없으면 **다섯 층이 전부 따로 논다.**
그래서 `Leg` 이 시작 시각을 갖는다 — 그러면 *"이 구간을 오후 2시에 걸으면 뙤약볕,
4시면 그늘"* 이라고 말할 수 있고, 그것이 [WALKABILITY.md](WALKABILITY.md) 2.2 가
이 성질을 강조한 이유다.

시각 속성에는 `isTemporal: true` 표시를 붙인다. **이름이 아니라 표시로 찾는 것**이
요점이다 — 속성 이름을 바꿔도 검사가 안 무너진다.
`Leg` 에 이 표시가 하나도 없으면 검사가 종료 코드 1 을 낸다.

> 🔴 **시각별 값 자체(몇 시에 그림자가 얼마인가)는 이 파일에 적지 않는다.**
> 그것은 산출물 JSON 이 갖는다. 여기 옮겨 적으면 계산 설정을 바꾸는 순간 낡는다 —
> 경사 기준선을 `_calibration.json` 이 정하게 한 것과 같은 이유다.

## 🔴 3. 기존 산출물과의 매핑 — 백엔드가 쓰는 표

`data/staged/segment-slope.ndjson`(NDJSON — 한 줄에 JSON 객체 하나씩 적은 파일)의
**한 줄이 `Segment` 하나**다. 아래는 **실제 파일을 읽어서 확인한 것만** 적었다.

| NDJSON 필드 | 온톨로지 용어 | 단위 · 값 | 쓰임 | 주의 |
|---|---|---|---|---|
| `id` | `bm:osmWayId` | 정수 (OSM way 번호) | 식별자 | 재수집해도 같은 구간을 찾는 유일한 열쇠 |
| `topic` | `bm:networkTopic` | `road` `walk` `stairs` | 가능판정 | 추출 단계가 붙인 값. OSM 태그가 아니다 |
| `highway` | `bm:osmHighwayClass` | OSM highway 값 (열린 목록) | 가능판정 | `null` 도 관측된다 |
| `name` | `bm:roadName` | 자유 문자열, `null` 가능 | 설명용 | 판정에 쓰지 않는다 |
| `length` | `bm:lengthM` | **m** | 비용 입력 | 좌표열의 지표면 거리 합 |
| `p90Slope` | `bm:slopeP90` | **무차원 비** (수직/수평) | 비용 입력 | 🔴 **대표 경사는 이것이다** |
| `p50Slope` | `bm:slopeP50` | 무차원 비 | 비용 입력 | p90 과 비교하면 "전체가 오르막인지 한쪽만 급한지" 가 보인다 |
| `maxSlope` | `bm:slopeMax` | 무차원 비 | 기록용 | 🔴 **판정에 쓰지 않는다** — 아래 |
| `ascent` | `bm:ascentM` | **m** | 비용 입력 | 방향이 있다. 반대로 지나면 내림과 바뀐다 |
| `descent` | `bm:descentM` | **m** | 비용 입력 | 〃 |
| `stepCount` | `bm:stepCountTagged` | **단**, `null` 가능 | 가능판정 | OSM `step_count` 원본. 보유율이 극히 낮다 |
| `stepEst` | `bm:stepCountEstimated` | **단**, `null` 가능 | 가능판정 | 고도차 ÷ 표준 단높이로 추정 |
| `inclineTag` | `bm:osmInclineTagRaw` | 자유 문자열, `null` 가능 | 설명용 | 🔴 **경사로 쓰지 않는다** — 아래 |
| `widthTag` | `bm:osmWidthTagRaw` | 자유 문자열, `null` 가능 | 설명용 | 🔴 **미터로 읽으면 안 된다** — 아래 |

파일에 없고 **위 필드에서 만들어 쓰는 것** 두 개:

| 온톨로지 용어 | 어떻게 만드나 | 단위 |
|---|---|---|
| `bm:stepCountTotal` | `stepCount` 가 있으면 그것, 없으면 `stepEst`, 둘 다 없으면 0 | 단 |

### 🔴 그대로 읽으면 안 되는 필드

번호는 이 절 전체를 관통한다 — ①②③ 은 구간, ④ 는 장소, ⑤ 는 도시철도다.
**개수를 제목에 적지 않는다.** 함정을 하나 더 찾을 때마다 그 제목이 낡는다.

**① `maxSlope` 를 판정에 쓰면 안 된다.**
DEM(**땅 높이를 격자로 적어둔 데이터**)의 수직 오차 한 점이 그대로 최댓값이 된다.
실제 데이터에 **1 을 넘는**(=수평 1m 에 수직 1m 이상) 값이 교량 구간에서 관측된다.
그래서 대표값을 p90(**표본을 크기순으로 세웠을 때 위에서 10% 지점의 값**)으로 바꿨다 —
`bigData/CLAUDE.md` 7절이 겪은 그것이다.

**② `inclineTag` 는 경사가 아니다.**
값에 방향(`up`/`down`)과 백분율과 `yes` 가 섞여 있어 숫자로 파싱할 수 없고, 보유율도
낮다. 경사는 태그가 아니라 **DEM 에서 계산했다.** 이 필드는 계산 결과를 눈으로
대조할 때만 쓴다.

**③ `widthTag` 를 미터로 읽으면 안 된다.**
단위 없는 맨 숫자와 **한국어 자유서식**(예: `약 60cm`)이 같은 컬럼에 섞여 있다.
그래서 폭 판정의 근거는 이 태그가 아니라 별도 용어 `bm:widthM` 이고,
그 입력인 **도로명주소 실폭도로는 아직 못 받았다** (5절).

### 버스 (BIMS)

`data/raw/transit/bims-*.ndjson` 은 한 줄이 **폴링 응답 하나**다.

| 어디 | 이름 | 온톨로지 용어 | 단위 |
|---|---|---|---|
| 줄 최상위 | `ts` | `bm:observedAtEpochMs` | **ms** (epoch 밀리초) |

| `config/routes.json` | `detail[].headway` | `bm:headwayMin` | **분** |

> 🔴 **`lowplate` 는 이름만 확인했고 값의 의미는 확인하지 못했다.**
> 휠체어 탑승 가능 여부(저상버스)로 보이지만 BIMS 규격 문서를 못 봤다.
> 그래서 이것을 참조하는 규칙은 `evidenceStatus: "검증필요"` 로 표시돼 있고,
> **확인 전에 이 값으로 사용자에게 "탈 수 없다" 고 말하면 안 된다.**

> 어느 갈래에도 안 걸리는 것은 **갈래 없는 `Place`** 로 남는다.

### 도시철도 (출입구·역)

`data/staged/subway-entrance.ndjson` 의 **한 줄이 `StationEntrance` 하나**이고,
그 줄에 **역 단위 값이 함께 실려 있다**(비정규화). `station*` 접두사가 붙은 것은
출입구가 아니라 **역**의 값이다.

> 이 파일은 `class` 필드에 이미 `StationEntrance` 라고 적고 있었는데
> **온톨로지에는 그 클래스가 없었다.** 이번에 정식으로 등록했다.

| NDJSON 필드 | 온톨로지 용어 | 어느 클래스 | 단위 · 값 | 쓰임 |
|---|---|---|---|---|
| `id` | `bm:entranceId` | StationEntrance | `osm:node/<번호>` | 식별자 |
| `lat` · `lon` | `bm:latDeg` · `bm:lonDeg` | StationEntrance | WGS84 십진도 | 설명용 |
| `exitRef` | `bm:exitRef` | StationEntrance | **개** (출구 번호), `null` 가능 | 식별자 |
| `exitLabel` | `bm:exitLabel` | StationEntrance | 자유 문자열 | 설명용 |
| `exitElevator` | `bm:exitElevatorAvailable` | StationEntrance | 참·거짓·**모름** | 가능판정 |
| `stationNo` | `bm:stationNo` · `bm:entranceStationOf` | Station | 문자열 | 식별자 |
| `stationName` | `bm:stationName` | Station | 자유 문자열, `null` 가능 | 설명용 |
| `stationLines` | `bm:stationLineNumbers` | Station | 정수 배열 (호선) | 설명용 |
| `stationIsTransfer` | `bm:stationIsTransfer` | Station | 참/거짓 | 설명용 |

🔴 **출구 번호가 이 데이터의 열쇠다.** 부산교통공사 엘리베이터 데이터에는 좌표가
없고 출입구번호만 있다. OSM 출구에 그 번호가 붙어 있어서 조인이 됐다 —
그 하나 때문에 승강기에 좌표가 생겼다.

**⑤ `exitElevator` 의 `false` 를 "승강기가 없다" 로 읽으면 안 된다.**
값이 셋이다 — 참·거짓·**모름(`null`)**. 산출물이 그 구분을 이미 지키고 있고
(*"엘리베이터가 없다" 와 "있는지 모른다" 는 다른 말이다*), 검사기가 아니라
수집기가 그렇게 만들었다. 그런데 **거짓의 의미는 아직 갈리지 않았다** —
출입구번호가 안 적힌 엘리베이터가 따로 세어져 있어서, 거짓이 *"승강기가 없다"* 인지
*"번호가 안 적혔다"* 인지 확인하지 못했다. 그래서 이 값을 쓰는 규칙은
`evidenceStatus: "검증필요"` 이고, **확인 전에 사용자에게 "이 출구로는 못 들어갑니다"
라고 말하면 안 된다.** `lowplate` 와 같은 처리다.

**칸은 열려 있으나 값이 하나도 없는 것 셋.**
`transferWalkMeters` · `stationFirstTrain` · `stationLastTrain` 이다.
이름은 실제 파일에서 확인했지만 **전 줄이 비어 있어 `sourceField` 로 올리지 않았다** —
값이 하나도 없는 칸을 출처로 적으면 있는 것처럼 읽히기 때문이다.
온톨로지에는 `미수집` 으로 선언되어 있고 `expectedFrom` 이 어디서 올 것인가를 말한다.

### 🔴 3.3. 짝 비교 문항의 속성 이름과의 대응 — 지금은 안 맞는다

**계수가 꽂힐 구멍과 문항이 다른 이름을 쓰면, 계수가 나와도 어디에 넣을지 모른다**
([ACCESS-ROUTE.md](ACCESS-ROUTE.md) 5절이 이미 경고한 것). `process/choice-design.mjs`
가 실제로 만드는 문항 속성 4개를 온톨로지 항목과 대조했다 — **실제 코드를 읽어서
확인한 것만** 적는다.

| 문항 속성(`choice-design.mjs` 의 `key`) | 단위 | 대응하는 온톨로지 항목 | 대응 상태 |
|---|---|---|---|
| `walkMin` | 분 | 없음 — `bm:` 항목 중 도보 소요시간(분)을 직접 담는 것이 아직 없다 | 🔴 **없음** |
| `slopePct` | % (가장 가파른 지점) | `bm:slopeP90` (무차원 비 — 값은 다르지만 같은 물리량: 구간의 대표 경사) | ⚠️ **이름만 다르다** — 단위 표기(`%` vs 비)를 맞추면 대응된다 |
| `stairs` | 단 | `bm:stepCountTotal` | ⚠️ **이름만 다르다** |
| `transfers` | 회 | 없음 — `bm:` 항목 중 "이 이동 안의 환승 횟수"를 세는 것이 아직 없다 (환승역 여부 `bm:stationIsTransfer`, 환승 도보거리 `bm:stationTransferWalkM` 은 있지만 **횟수**는 다른 개념이다) | 🔴 **없음** |

> 🔴 **더 심각한 것 — 문항이 묻는 경사와 예산 모델이 쓰는 경사가 다른 물리량이다.**
> [ACCESS-ROUTE.md](ACCESS-ROUTE.md) 4.1·5절의 `effortBudget.sustainedRunMax` 는
> **"쉬지 않고 얼마나 올라야 하나"(m)** 를 묻는데, 지금 문항은 `slopePct` —
> **"가장 가파른 지점이 몇 %인가"** 를 묻는다. 이 둘은 서로 다른 질문이고,
> `slopePct` 로 뽑은 계수로는 `sustainedRunMax` 자리를 채울 수 없다
> (ACCESS-ROUTE.md 가 "다른 물리량" 이라고 부른 바로 그 문제).
>
> `bm:slopeP90` 자체는 잘못이 아니다 — 구간의 "얼마나 가파른가" 를 재는 값으로는
> 맞다. 문제는 **예산 모델이 필요로 하는 입력(연속 오르막 길이)을 지금 문항이
> 아예 묻지 않는다**는 것이다.
>
> **아직 현장 실험 데이터가 없다** (`bigData/data/` 어디에도 응답 파일이 없다) —
> 그래서 지금 고쳐도 잃는 표본이 없다. 이것이 이 문서가 조용히 답을 지어내지 않고
> **다음 실행 전에 팀이 결정할 것**으로 남겨 두는 이유다:
>
> 1. `choice-design.mjs` 의 `slopePct` 를 `sustainedRunMax`(m, 연속 오르막 길이)로
>    바꾸고, 그 값을 위한 `bm:` 항목을 새로 온톨로지에 추가한다, **또는**
> 2. 지금 문항(`slopePct`)은 그대로 두어 `bm:slopeP90` 의 계수를 얻는 용도로 쓰고,
>    `sustainedRunMax` 는 **다음 실험**으로 미룬다 — 그동안 예산 모델은 그 항목의
>    계수를 `미추정` 으로 둔다
>
> `walkMin`·`transfers` 도 같은 이유로 이름만이 아니라 **온톨로지 항목 자체가
> 없다.** 이 셋은 `role: "cost"` · `coefficientStatus: "미추정"` 항목으로 새로 추가할
> 대상이지, 지금 있는 어떤 이름을 고쳐 붙일 자리가 아니다.

## 4. 가능판정 규칙 — 임계값이 왜 비어 있나

규칙은 이렇게 생겼다. 숫자가 규칙 안에 없고 **이름으로 가리킨다.**

```json
{ "property": "bm:slopeP90", "operator": "gte", "parameter": "bm:maxSlopeWheelchair" }
```

값이 바뀔 때 규칙을 건드리지 않기 위해서다. 지금 선언된 규칙과 각각이 **왜 아직
못 도는지**:

| 규칙 | 프로파일 | 상태 | 못 도는 이유 |
|---|---|---|---|
| 자동차 전용도로 보행 금지 | 전부 | ✅ 적용가능 | |
| 계단 → 통과 불가 | 휠체어 · 유모차 | ✅ 적용가능 | |
| 경사 상한 초과 | 휠체어 | ✅ 적용가능 | 임계가 설계기준으로 정해져 있다 |
| 저상버스 아님 | 휠체어 | ⚠️ 검증필요 | `lowplate` 의 의미 미확인 |
| 유효폭 미달 | 휠체어 · 유모차 | ⚠️ 입력미수집 | `bm:widthM` 자체가 없다 |
| 경사 상한 초과 | 유모차 · 고령자 | ⚠️ 임계미정 | 아래 |
| 계단 단수 초과 | 고령자 | ⚠️ 임계미정 | 아래 |
| **이동 안에 계단 구간** (`Leg`) | 휠체어 · 유모차 | ⚠️ 입력미수집 | `Leg` 산출물이 아직 없다 |
| **승강기 없는 출입구** (`StationEntrance`) | 휠체어 | ⚠️ 검증필요 | `exitElevator` 의 거짓이 무엇을 뜻하는지 미확인 (3절 ⑤) |

**아래 두 줄이 여행 상위 개념에 붙은 규칙이다.** 성격은 위와 같다 — 가능/불가뿐이고
점수가 아니다. 이동 단위 규칙이 따로 있는 이유는, **사용자가 고르는 것이 구간이 아니라
이동**이기 때문이다. 구간 하나가 불가여도 사람에게는 *"이 이동은 안 됩니다"* 로
말해져야 한다.

> 🔴 **`Leg` 에 비용을 매기는 규칙은 넣지 않았다.** *"12% 오르막 200m 와 평지 500m
> 우회 중 어느 쪽이 나은가"* 는 여전히 짝 비교 실험이 정한다. 새로 얹은 속성
> (환승 도보거리 · 기온)도 `coefficientStatus: "미추정"` 으로 계수 자리를 비워 두었다.

### 🔴 임계값을 지어내지 않은 이유

**휠체어 최대 경사**만 값이 있다. 근거가 **설계기준**(휠체어 경사로 1:12)이기
때문이다. 값과 근거는 `config/ontology.jsonld` 의 `bm:maxSlopeWheelchair` 에 있다 —
**여기 옮겨 적지 않는다.** 옮겨 적으면 그 줄이 낡는다.

나머지는 `valueStatus: "미정"` 이다. 유모차나 고령자에게 **몇 % 부터 "못 간다" 인지에
표준이 없다.** 여기서 숫자를 지어내면 **"많은 사람이 싫어한다" 를 "아무도 못 간다"
로 위장**하는 것이 된다. 그건 0절에서 긋기로 한 선을 넘는 것이고,
**짝 비교 계수로 이 값을 정하는 것도 같은 위반이다** — 그 실험이 재는 것은 선호다.

임계는 **설계기준·물리 한계**에서 와야 한다. 올 때까지 규칙은 선언된 채로 멈춰 있고,
`evidenceStatus` 가 무엇이 없어서 멈췄는지 말한다.

**`Default` 프로파일에 자기 규칙이 없는 것도 의도다.** 기본 이용자의 유일한 불가
조건은 모든 프로파일에 걸리는 자동차 전용도로 금지뿐이다 — 기본값에서는
**경사와 계단이 "못 간다" 가 아니라 "비싸다"** 여야 한다.

## 5. 아직 못 받은 것 — 필드 이름을 지어내지 않았다

`config/sources.json` 이 아직 못 받았다고 적은 출처들이다. 이것들은
**클래스와 개념만 선언하고 `status: "미수집"` 을 명시**했다.

| 개념 | 어느 출처를 기다리나 | 없으면 못 하는 것 |
|---|---|---|
| `bm:widthM` 유효 통행폭 | 도로명주소 실폭도로 (**신청 완료 2026-09-06 · 심사 중**) | 휠체어·유모차 폭 규칙 두 개 |
| `bm:StreetTreeSection` 가로수 구간 | 부산 구군 가로수 현황 (자동승인) | 그늘 점수 |
| `bm:BuildingShadow` 건물 그림자 | GIS건물통합정보 (nsdi 연결 실패) | 시각별 그늘 |
| `bm:shadeScore` 그늘 점수 | 위 둘 | 여름 경로 판정 |
| `bm:openingHoursNormalized` 영업시간·휴무일 | TourAPI 소개정보 (**승인 2026-09-06 · 아직 호출 안 함**) | *"닫힌 곳으로 안내하지 않기"* |
| `bm:stationTransferWalkM` 환승 통로 도보거리 | 🔴 **공개 데이터가 없다** — 손으로 재야 한다 | 환승 1회가 전부 같은 비용이 된다 |
| `bm:stationFirstTrainTime` · `bm:stationLastTrainTime` | 부산교통공사 열차시각표 (**승인 2026-09-06 · 아직 호출 안 함**) | 이른 아침·늦은 밤 일정의 성립 여부 |
| `bm:legTemperatureC` 기온 | 기상청 단기예보 — 🔴 `sources.json` 에 아직 없다 | 그늘 가중치가 상수로 굳는다 (4월에 8월 값) |
| `bm:placeWheelchairAccessible` 장소 휠체어 진입 | 무장애 여행 정보 (**승인 2026-09-06 · 아직 호출 안 함**) | 길을 다 통과하고 문 앞에서 막히는 경우를 말할 수 없다 |
| `bm:businessTenureQuarters` 영업 지속 분기 수 | 상가정보 — **분기 스냅샷 2벌 이상** (한 벌에는 개업일이 없다) | 리뷰 대신 쓸 신호가 없다 |

> 🔴 **영업시간이 다른 미수집과 다른 점.** 경사를 잘못 재면 *"생각보다 힘들었다"* 로
> 끝나지만, 닫힌 곳으로 안내하면 **여행자의 반나절이 날아간다.** 되돌릴 수 없다.
> 그래서 이것만은 자료형까지 미리 못박아 두었다 (3절).

> 🔴 **필드 이름을 지어내면 나중에 실제 응답과 어긋난다. 이 파트에서 가장 나쁜
> 실패다.** 그래서 미수집 개념에는 `field` 를 적지 않고 `expectedFrom`(어느 출처에서
> 올 것인가)만 적었다. 검사기가 이 규칙을 강제한다.
>
> 하나만 예외를 두되 이름을 달리했다. 가로수는 `docs/WALKABILITY.md` 2.1 이
> **포털 화면에서 보고 적어둔** 후보 이름들이 있어서 `fieldCandidate`(후보)로 남기고,
> 어디서 본 것인지를 `candidateSource` 에 함께 적었다. **`field` 와 다른 이름인
> 것이 핵심이다** — 확인된 것과 본 것을 같은 칸에 넣지 않는다.

`bm:Building` 과 `bm:Barrier` 는 **`부분수집`** 이다. OSM 원본에 태그가 있다는 것은
실측했지만 **구간에 붙인 staged 산출물이 아직 없다.** 그래서 규칙이 참조하지 않는다.

## 6. 검사

```bash
node test/verify-ontology.mjs
```

종료 코드가 판정이다 (0 성공 / 1 실패). 무엇이 어긋났는지 줄마다 출력한다.
붙잡는 것:

- `@context` 로 펼쳤을 때 **유효한 JSON-LD 인가** — 외부 라이브러리 없이 구조만 본다.
  이 파일이 실제로 쓰는 부분집합만 구현하고, 그 밖의 것이 나오면 **"펼칠 수 없다" 고
  실패시킨다.** 조용히 넘기지 않는다
- `@context` **원문의 중복 키** — `JSON.parse` 는 뒤엣것만 조용히 남긴다.
  접두사와 용어 별칭이 같은 이름을 쓰면 접두사가 사라지고 모든 URI 확장이 죽는데
  **눈으로는 안 보인다.** 이 검사는 실제로 이 작업 중에 그 사고를 한 번 잡았다
- 모든 `skos:Concept` 에 `prefLabel`(ko·en 둘 다) · `definition` · `inScheme` 이 있는가
- 값을 갖는 속성·파라미터에 **단위 또는 값 범위**가 있는가
- 규칙이 **선언된 속성·파라미터·프로파일만** 참조하는가. 없는 것을 가리키면 실패
- 네 프로파일이 전부 최소 하나의 규칙에 덮이는가 (상위 프로파일 상속 포함)
- 🔴 **선호 계수 숫자가 새어 들어왔는가**
- 🔴 **미수집 개념에 지어낸 필드 이름이 있는가**
- `수집됨` 이라고 적은 필드가 **실제 파일에 있는가**. 파일이 없으면 건너뛴다 —
  clone 직후에도 돌아야 하기 때문이다 (`test/verify.mjs` 가 DEM 에 쓰는 것과 같은 태도)

**여행 상위 개념을 얹으면서 늘린 것** (2026-08-28)

- 여행 상위 개념(장소·갈래·이동수단·여행자·일정·이동·역·출입구)이 **전부 있고**
  이름(ko·en)과 뜻을 갖는가. 하나라도 지우면 실패한다
- 🔴 **장소와 정류장·출입구의 관계가 정해 둔 대로인가** — 정류장·출입구가 `Waypoint`
  아래에 있고, `Place` 아래에는 **없고**, `Station` 은 `Waypoint` 가 **아닌가** (2.1)
- 🔴 **`Leg` 이 시각을 갖는가.** `isTemporal: true` 인 속성이 하나도 없으면 실패한다.
  이름이 아니라 **표시**로 찾으므로 속성 이름을 바꿔도 검사가 안 무너진다
- 🔴 **`Itinerary` → `Leg` → `Segment` 로 내려가는 길이 실제로 이어지는가.**
  `onClass` → `rangeClass` 를 간선으로 놓고 실제로 내려가 본다. 끊기면 접착제가 안
  붙은 것이니 실패한다
- 🔴 **장소 갈래의 태그가 실제로 관측되는가.** `poi.ndjson` 을 열어 `키=값` 을 한
  값씩 대조한다. 파일에 없는 태그를 적으면 실패한다 — *"상상하지 마라"* 를 문서가
  아니라 코드가 지킨다. 파일이 없으면 건너뛴다

**검사기 자신도 실패해 보였다.** 인자로 다른 파일을 줄 수 있게 해 두었다
(`node test/verify-ontology.mjs <경로>`). 라벨을 빼고, 계수에 숫자를 넣고, 없는
속성을 가리키고, 미수집에 필드 이름을 적고, 단위를 지우고, `@context` 키를 겹치게
하고, 필드 이름을 틀리게 한 판본을 각각 만들어 **전부 종료 코드 1 로 떨어지는 것을
확인했다.** 통과만 해본 검사기는 검사기가 아니다.

**늘린 검사도 같은 방식으로 확인했다** (2026-08-28). `Leg` 의 시각 표시를 지우고,
`Itinerary→Leg` 과 `Leg→Segment` 를 각각 끊고, 장소 갈래에 실제로 없는 태그를 넣고,
갈래의 `codeList` 를 비우고, 정류장을 `Waypoint` 에서 떼고, 출입구를 `Place` 아래로
옮기고, `Station` 을 `Waypoint` 아래로 옮기고, 여행자 클래스를 지우고, 새 속성의
계수에 숫자를 넣고, 미수집 속성에 필드 이름을 적고, 영문 이름을 지운 판본을 만들어
**전부 종료 코드 1 로 떨어지는 것을 확인했다.**

**개수를 이 문서에 적지 않는다.** 개념을 늘릴 때마다 그 줄이 낡고, 낡은 기준은
없는 기준보다 나쁘다.

## 7. 못 한 것

솔직하게 남긴다. 다음 사람이 같은 것을 다시 재보지 않게.

1. **`lowplate` 의 의미를 확인하지 못했다.** BIMS 규격 문서를 못 봤다. 저상버스
   여부로 보이지만 **추정이다.** 규칙에 `검증필요` 로 표시해 두었다
2. **임계값 다섯 개가 비어 있다** — 유모차·고령자 경사, 휠체어·유모차 유효폭,
   고령자 계단 단수. 표준을 못 찾았고, 지어내지 않는 쪽을 골랐다
3. **`Barrier` 를 구간에 붙이지 못했다.** 원시 수집분은 있지만 어느 차단물이 어느
   구간 위에 있는지 잇는 처리가 없다. 그래서 규칙이 참조하지 않는다
4. **`trunk` 를 보행 금지 목록에 넣을지 정하지 못했다.** 국내 OSM 에서 자동차전용
   도로와 일반 간선에 섞여 쓰인다. 넣으면 걸을 수 있는 큰길이 전부 막히고, 빼면
   못 걷는 길이 열린다. `foot`·`access` 태그를 함께 봐야 정해진다 —
   지금은 **빼는 쪽**을 골랐고 그 이유를 파일 안에 적어 두었다
5. **경치·보행우선구역은 아예 넣지 않았다.** [WALKABILITY.md](WALKABILITY.md) 3·4절이
   아직 방법을 정하지 못한 것들이라, 개념만 미리 만들면 나중에 실제 방법과 어긋난다

**여행 상위 개념을 얹으면서 새로 생긴 것** (2026-08-28)

6. 🔴 **캐리어가 계단을 "불가" 로 만드는지 "비싼 것" 으로 만드는지 정하지 못했다.**
   `bm:hasWheeledLuggage` 속성은 선언했지만 **그것을 참조하는 규칙이 없다.**
   고령자 계단 상한과 같은 자리에 멈춰 있다 — 몇 단부터 못 가는지에 표준이 없다.
   그런데도 지금 속성을 만든 이유는 자료형이 아니라 **실험** 때문이다. 짝 비교 문항에
   *"캐리어를 끌고 있다"* 조건이 없으면 그 계수는 영영 못 뽑고,
   **현장 실험은 한 번뿐이다** ([FIELD-STUDY.md](FIELD-STUDY.md) 5절).
   `process/choice-design.mjs` 가 문항을 만들기 전에 사람이 정해야 한다
7. **강수(비·눈)를 안 넣었다.** 기온만 넣었다. 비가 오면 경사·계단보다 **가림 여부**가
   결정을 지배해서 순위가 뒤바뀌는데, 값의 코드 목록을 지어내지 않으려고 비워 두었다
8. **`Place` 의 staged 산출물이 없다.** 원본 POI 는 있지만 구간·좌표계에 붙인 것이
   없어서, 지금 `Place` 는 선언만 있고 실제 개체가 없다. `Barrier` 와 같은 상태다
9. **도시철도 Leg 의 시간을 만들 수 없다.** 노선 형상(way)이 추출에 빠져 있고
   역간 소요시간·첫차막차가 없다. 출구까지 걷는 부분만 지금 계산할 수 있다
10. **`exitElevator` 의 거짓이 무엇을 뜻하는지 확인하지 못했다** (3절 ⑤).
    `lowplate` 와 같은 종류의 미확인이고, 같은 방식으로 `검증필요` 로 표시해 두었다
11. **환승 통로 도보거리는 공개 데이터가 없다.** 서울은 있고 부산은 없다.
    환승역이 손으로 잴 수 있는 수라서, 슬롯만 열어 두고 값은 나중에 채운다
12. **`Leg` 의 소요시간을 속성으로 만들지 않았다.** 걷기는 경사·계단에서, 버스는
    BIMS 관측에서, 도시철도는 시각표에서 나오는데 **셋의 근거가 서로 달라서**
    하나의 속성으로 묶으면 무엇으로 만든 값인지가 사라진다. 정해야 하는 것이다

## 용어

| 말 | 뜻 |
|---|---|
| **온톨로지** | 이 분야에 무엇이 존재하고 서로 어떤 관계인지를 기계가 읽게 적어둔 것 |
| **JSON-LD** | Linked Data 를 JSON 으로 쓰는 W3C 표준. `@context` 가 짧은 이름을 URI 로 펼친다 |
| **SKOS** | 어휘·분류를 기술하는 W3C 표준. 이름(`prefLabel`)·뜻(`definition`)·상위(`broader`) |
| **`@context`** | 짧은 이름 → URI 사전. 이게 없으면 이름들이 우리 팀 안에서만 통한다 |
| **feasibility (가능/불가)** | 지날 수 있나 없나. 답이 둘 중 하나이고 점수가 아니다 |
| **preference (선호)** | 얼마나 싫은가. 사람마다 다르고, 실험으로 추정한다 |
| **조건부 로짓** | 고른 기록에서 "각 속성이 선택에 얼마나 영향을 줬나" 를 계수로 뽑는 통계 모델 |
| **NDJSON** | 한 줄에 JSON 객체 하나씩 적은 파일. 스트리밍으로 읽을 수 있다 |
| **DEM** | 땅 높이를 격자로 적어둔 데이터. 경사를 여기서 계산했다 |
| **p90** | 표본을 크기순으로 세웠을 때 위에서 10% 지점의 값. 최댓값보다 잡음에 덜 끌린다 |
| **QUDT** | 단위를 URI 로 적어둔 표준 어휘 |
| **유효폭** | 실제로 지나갈 수 있는 폭. 도로 폭에서 전봇대·주차 차량 등을 뺀 값 |
| **Waypoint (경유 지점)** | 이동 한 토막의 끝점이 될 수 있는 것. 정체가 아니라 **역할**이다 |
| **Leg (이동 한 토막)** | 출발 지점에서 도착 지점까지 **수단 하나로** 가는 이동 한 번. 수단이 바뀌면 Leg 이 바뀐다 |
| **Itinerary (하루 일정)** | 한 여행자의 하루치 Leg 나열. 날짜를 갖는다 |
| **다중 상위** | 한 개념이 상위를 둘 이상 갖는 것. SKOS 가 허용한다. 여기서는 정체와 역할을 나눠 담는 데 썼다 |
| **POI** | Point Of Interest — 지도에 점으로 찍히는 지점. 여기서는 `Place` 의 원재료다 |
| **비정규화** | 한 줄에 서로 다른 것의 값을 함께 담아 둔 것. 출입구 파일이 역 값을 함께 갖고 있다 |
