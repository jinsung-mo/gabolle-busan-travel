# BIMS 수집을 서버에서 돌린다

**무엇** — 부산 시내버스의 실시간 위치를 계속 받아 쌓는다.
**왜 서버인가** — 노트북에서 돌리던 것을 옮겼다. 이유는 아래 1절.

---

## 1. 왜 옮겼나 — 기술 문제가 아니라 사람 문제였다

이 수집은 원래 **팀원 6명이 각자 노트북에서** 돌리는 구조였다. 한도가 계정(키)당
걸리므로 키 여섯이면 예산도 여섯 배가 되기 때문이다. 설계 문서
([`../docs/BIMS-FLEET.md`](../docs/BIMS-FLEET.md))가 그 계산을 다 해 두었다.

그런데 실제로 모인 것은 **2026-08-26 ~ 08-28 사흘치, 그것도 5노선뿐**이다.
로그의 마지막 줄이 08-27 23:48 이고, 그 시각은 노트북을 끈 시각이다.

> 🔴 **계획의 커버리지는 27% 였고, 실측 커버리지는 0% 다.**
> 실행되지 않은 계획은 커버리지가 없다. 그리고 실시간 데이터는 **소급 수집이
> 안 되므로** 그 사이 비어 있는 날은 영영 못 만든다.

문서 자신이 그 원인을 이미 적어 두었다 — *"문제는 이게 기술 문제가 아니라는 것이다.
밤에 노트북을 켜 두는 것은 사람의 생활 문제다."* 그리고 그 때문에 **야간 시간대를
"사람이 정할 문제"로 비워 두었다.**

서버에는 그 문제가 없다. 그래서 이 배포는 커버리지를 늘리는 일이 아니라
**비워 둔 자리를 채우는 일**이다.

---

## 2. 무엇이 달라졌나

|  | 노트북 (전) | 서버 (지금) |
|---|---|---|
| 켜는 사람 | 매일 아침 각자 | 없음 — 재부팅해도 알아서 뜬다 |
| 도는 시간 | 09–18시 (그나마 안 지켜짐) | **05–01시** |
| 퇴근 러시아워 | 비어 있음 | **덮는다** ← 소요시간 변동이 가장 큰 구간 |
| 노선 | 1인 13 × 6 = 78 (계획) | 1인 12 × 6 = **72** |
| 주기 | 60초 고정 | 러시아워 60초 · 그 밖 180초 |

`★ 왜 노선이 78 → 72 로 줄었나`
호출 예산이 고정이라 **"노선 수 × 켜 있는 시간" 이 상수**다. 하루 종일 켜면 노선이
줄어드는 것이 당연하다. 그래서 시간대마다 주기를 다르게 줬다 — 변동이 큰 러시아워만
촘촘히 보고 한산한 시간은 성기게 본다. 그 덕에 하루 종일 덮으면서도 노선을 72개까지
가져왔다. 그냥 24시간 60초로 돌렸다면 **30개**였다.

## 3. 시간표와 예산 — 🔴 두 곳을 같이 고친다

```
07–09시 · 17–20시  (5시간)    60초 →  300회/노선
05–07 · 09–17 · 20–01 (15시간) 180초 →  300회/노선
01–05시                        꺼짐 →    0회
                                    합 600회/노선

12노선 × 600 = 7,200회/키/일   (한도 10,000 의 72%)
```

시간표는 [`compose.yaml`](compose.yaml) 이 갖고 있고, 노선 배정은
[`../config/bims-assign.json`](../config/bims-assign.json) 이 갖고 있다.
**둘을 잇는 숫자가 "하루 600회" 하나다.**

시간표를 고치면 배정도 다시 만든다.

```bash
cd bigData
node process/bims-assign.mjs --members rleaderjoon,masdf13,yeaseung.lee96,jinmiri,모진성,고지혁 \
  --calls-per-route <새 값>
```

한쪽만 고치면 한도를 넘긴다. **한도를 넘긴 키는 그날 남은 시간 동안 아무것도 못 받는다.**
그래서 수집기 안에 `BIMS_DAILY_CAP` 이 마지막 방어선으로 들어 있다 — 산수가 틀려도
키를 태우지는 않는다.

## 4. 올리는 법

```bash
ssh -i <키> ubuntu@j15e201.p.ssafy.io

cd ~/bims/bigData/deploy
cp .env.example .env          # 팀원 6명 인증키를 채운다 (커밋되지 않는다)
docker compose up -d --build

docker compose ps             # 여섯이 다 Up 인가
docker compose logs -f --tail=20
```

멈추기 · 다시 시작하기:

```bash
docker compose stop           # 잠깐 멈춘다 (그 사이 데이터는 영영 없다)
docker compose up -d
```

## 5. 잘 돌고 있는지 보는 법

```bash
# 오늘 파일이 여섯 개 있고, 계속 커지고 있어야 한다
ls -l data/raw/transit/bims-$(TZ=Asia/Seoul date +%F)-*.ndjson

# 키마다 오늘 몇 번 불렀나 (한도 10,000 · 상한 7,200)
```

🔴 **오류가 0인지 꼭 본다.** 인증키가 막히면 HTTP 200 에 오류 XML 이 온다 —
수집기가 그것을 성공으로 세지 않지만, `errors` 만 조용히 올라간다.

```bash
docker compose logs --tail=200 | grep -i "⚠\|🔴" | tail -20
```

## 6. 아침 점검 — 매일 05:00 에 MatterMost 로

사람이 매일 확인하러 들어오지 않는다. 그래서 **하루에 한 번 먼저 말을 건다.**

```
0 20 * * *   /home/ubuntu/bims/bigData/deploy/run-morning-report.sh
```

> 🔴 **cron 은 20:00 인데 알림은 05:00 에 간다.** 서버가 UTC 라서 그렇다
> (05:00 KST = 20:00 UTC 전날). 이 환산을 잊고 "05 00" 으로 고치면 **한국시간
> 오후 2시에 온다.**

보내는 내용:

- 러너 6개가 떠 있는가
- **어제 실제로 얼마나 모았는가** — 키별 호출 수·노선 수·크기, 그리고 기대치 대비 %
- 24시간 오류 수, 디스크 여유

### 🔴 "떠 있다" 와 "모으고 있다" 는 다르다

인증키가 막히면 컨테이너는 **멀쩡히 Up 인 채로** 오류만 세면서 아무것도 안 쌓는다.
상태만 보면 초록이고 데이터만 비어 간다. 그래서 이 점검은 상태와 함께 **어제 쌓인
줄 수를 배정표의 기대치와 견준다.** 기대의 절반 아래면 이름을 짚어 알린다.

기대치를 여기 적어 두지 않고 `config/bims-assign.json` 에서 읽는 이유도 같다 —
배정이 바뀌었는데 점검이 옛 기준으로 판정하면, 그 알림은 초록일 때 가장 위험하다.

### 왜 컨테이너가 아니라 호스트에서 도나

점검을 7번째 컨테이너로 만들면 **컴포즈가 통째로 죽는 날 알림도 같이 죽는다** —
가장 알아야 할 순간에 조용해진다. 감시자는 감시 대상과 운명을 같이하면 안 된다.

### 손으로 돌려 보기

```bash
cd ~/bims/bigData/deploy
./run-morning-report.sh --dry-run                    # 보내지 않고 화면에만
./run-morning-report.sh --dry-run --date 2026-09-06  # 지난 날 다시 보기
```

웹훅 주소(`MATTERMOST_WEBHOOK`)가 비어 있으면 **종료 코드 2로 실패한다.**
조용히 성공한 척하지 않는다.

## 7. 아직 안 한 것

- **수집물을 서버 밖으로 내보내는 일.** 지금은 EC2 디스크에만 쌓인다. 하루 6개 파일씩
  늘어나므로 언젠가는 옮겨야 한다 (여유 246G, 당장은 문제 없다).
- **모아 놓은 것을 쓰는 일.** 구간 소요시간을 뽑는 처리기가 아직 없다.
  수집을 먼저 켠 이유는 *소급 수집이 안 되기 때문*이지 분석이 준비돼서가 아니다.
- **즉시 알림.** 아침 점검은 하루에 한 번이다. 새벽 1시에 여섯이 다 죽으면
  **아침 5시까지 아무도 모른다.** `restart: unless-stopped` 가 다시 띄우기는 하지만,
  키가 막혀서 계속 실패하는 경우는 못 살린다.
